## Payload

`{BYTE length; char resref[length]; DWORD nType; DWORD size; BYTE data[size]}` after the 3-byte
specific-message header. The resref length is a single byte; the type selects the CRes class
(1010 ARE / 1013 GAM / 1014 STO / 1015 WMP); the data is written to
`<filePath>/<resref>.<ext>` through `CRes::Write`.

## Notes

1. The guard is the client's again (session open, not hosting).
2. `bSaveToTemp` chooses `CInfGame::m_sTempDir`; otherwise `CInfGame::sub_5C0B30()` (the
   multiplayer save directory) — the same two paths the save/load code uses.
3. The per-type blocks are the inlined `CResHelper<T,nType>::SetResRef(cResRef, TRUE, TRUE)`
   followed by `GetRes()->Write(...)` and the helper's destructor; the 1014 case calls the
   out-of-line SetResRef (0x43E190). The original does not null-check `GetRes()` (the resource is
   expected to be in the key table); the port mirrors that.
4. The `dwSize` argument is unused (the payload is self-describing) — `(void)dwSize` in the port.
5. Follow-up when the box returns: the Ghidra decompile draft and the oracle case (a session plus
   a resource write is not honestly fixturable for the oracle; the unit test covers the guard and
   the parse/write on the private view).
