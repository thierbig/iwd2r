# 0x460D70 CGameAIBase::CreateCreatureObject

Member of CGameAIBase in the original's CGameAIBaseActions.cpp,
`__thiscall` `SHORT CreateCreatureObject(CGameObject* pTarget)`, 1,045
bytes (0x460D70-0x461185). Ghidra's CGameSprite_B3AUTO_00460d70 name is
wrong: the function reads `this` as a CGameAIBase (m_curAction at 0x476,
m_pArea, m_id) and its only caller loads the CGameAIBase pointer into
ecx and pushes the raw GetTargetShareType result as the parameter.

Ported in two ranges, one commit each: e274aee2 (0x460D70-0x460F49: the
null-target guard, the position from the target object, the (-1, -1)
fallback, the key-table probe for the CRE, and the CCreatureFile read),
and e23c36d2 (0x460F5A-0x461185: the CGameSprite construction, the resref
fixups, the GetNearestOpenSquare placement, the area add, and the
named-creatures registration), which also carries this file. The split is
at operator new 0x460F5A: the GetDataSize/GetData reads at 0x460F9D/0x460FA7
sit between the constructor's argument pushes, so they belong to the
construction range. The caller arm is 3306315d (the case 227 arm of
CGameAIBase::ExecuteAction, 0x44E23F-0x44E267).

## Callers

Exactly one, ported with the caller arm: the case 227 arm of
CGameAIBase::ExecuteAction. The exe's arm loads the TYPE_AIBASE constant,
calls GetTargetShareType, sets the share flag (bShare = TRUE) before the
call, and pushes the raw CGameObject* result straight into
CreateCreatureObject — no cast: the body only null-tests the pointer and
calls the GetPos virtual on it. Unlike CreateCreature's arm, the result
routes through the release tail (0x44E1DE), which drops the share the
arm took.

## Callees

No new callees: every call is in-tree — the CGameObject::GetPos virtual
(vtable 0x1C), CProjectile::GetSourcePosition (the (-1, -1) branch),
CDimm key-table FindKey, the CCreatureFile
ctor/SetResRef/GetDataSize/GetData/GetResRef/ReleaseData/dtor family,
operator new, CGameSprite::CGameSprite, CGameSprite::SetResRef,
CGameAnimationType::GetPersonalSpace and GetListType,

eax,[ecx+0x554]; ret` accessor) on the new sprite,
CString/strcmp traffic, and CVariable::SetName with the CVariableHash
AddKey. All were ported before this task.

## Notes

- Five differences from the sibling CreateCreature (0x4608A0):
  1. A null target returns ACTION_ERROR before the CVariable constructor
     runs — CreateCreature has no target at all.
  2. The position comes from the target object's GetPos virtual, not
     from m_curAction.m_dest; a (-1, -1) position still falls back to
     the caller's source position.
  3. There is no exact-square variant: every call runs
     GetNearestOpenSquare with the new sprite's personal space and the
     acting object's terrain table; the action id inside the handler
     selects nothing.
  4. There is no second-string script-name copy: the sprite is
     registered under whatever script name the CRE file left on it, even
     when the action's second string is non-empty.
  5. field_342 is not Set to the new sprite's AI type.
- At 0x461081 the exe pushes nPersonalSpace and then calls the
  GetTerrainTable virtual (vtable 0xA0) with that push still on the
  stack; the push is GetNearestOpenSquare's third argument staged before
  the table call, and GetTerrainTable itself takes no argument (the
  tree keeps the no-arg call, as the sibling does).
- The sprite is built before either resref is corrected: the constructor
  sees the raw CRE, SetResRef copies the file's own resref back, and a
  second SetResRef immediately overwrites it with the action's first
  string. Both calls are kept because the first keeps the sprite
  consistent with the file it was built from.
- m_curAction.m_specificID is the facing, passed straight through to the
  CGameSprite constructor as a WORD; the constructor's SetSequence mask
  rounds odd facings down to the next even direction, so 13 lands as 12
  while 6 survives (same as the sibling — see 4608A0.md).
- The handler returns ACTION_DONE; the null-target, missing-CRE and
  failed-allocation paths return ACTION_ERROR. The null-target and
  missing-CRE returns happen before the CCreatureFile constructor runs;
  every exit after it destroys the file object (the destructor sits in
  the epilogue at 0x461153).
