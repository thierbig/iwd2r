# 0x4688A0 CGameAIBase::BitGlobal

1,943 bytes (0x4688A0-0x469037), the CGameAIBase action handler for
script action 247 (BitGlobal), dispatched on `this`. No fork body
exists for it.

## Identification

Combines an integer mask into a script variable with a bitwise op —
the immediate-mask twin of 0x469040 (action 248, which takes the
source from a second variable). `m_curAction` string1 names the
variable as `SCOPE:NAME`, uppercased, split at the first colon;
`m_specificID` is the mask (0xB6) and `m_specificID2` picks the op
(0xBA): 1 AND, 2 OR, 3 XOR; any other value returns ACTION_ERROR
(0xFFFE) from every arm before any write.

The write arms: GLOBAL writes the game variables; LOCALS writes the
sprite's own variables, gated by GetObjectType() == TYPE_SPRITE (any
other object type ends the action silently, the SetGlobal gate);
anything else is an area scope — MYAREA is first replaced with the
acting area's own name — and an area that is not loaded ends the
action silently. A missing variable is created from 0 and combined in
one step. Every successful write posts a
CMessageSetVariable(scope, name, value, m_id, m_id).

Original quirks kept, each with a NOTE or comment in the body:

- The MYAREA arm replaces the scope with the area's name, so the
  lookup and the posted message carry the area name (as SetGlobal and
  0x469040 do).
- The area's name is read as a C string from the start of the area
  (its header's RESREF), as in SetGlobal.
- The not-found GLOBAL arm news its CVariable and leaks it on the
  invalid-op path; the not-found area arm news one and deletes it
  after the AddKey copy; the not-found LOCALS arm constructs on the
  stack in the original itself. All three render as stack CVariables
  that outlive the AddKey copy, the SetGlobal house style.
- The found-variable area arm's message fill shares the GLOBAL arm's
  fill code at 0x468A45 in the exe (0x468EA4 jumps into it).

- Sole exe caller: the action dispatch at 0x450694 (case 247), plain
  `mov esi,eax` return with `jmp` to the shared done path — the same
  arm shape as case 248, no bShare or target handling — wired to
  `returnValue = BitGlobal(); goto done;` in ExecuteAction.

## Tests

`tests/test_bit_global.cpp` drives the handler on the
finished-character probe through ExecuteAction with a real action
247: AND/OR/XOR on an existing GLOBAL variable, the create arm from 0,
the ACTION_ERROR return for an unknown op (existing value kept,
missing variable not created), the LOCALS write through the sprite's
own variables, and MYAREA plus a directly named area writing that
area's variables (with the no-area silent end and the bad-op tail).
The create arm asserts the combined value under XOR because from 0 an
AND reads as 0.

No existing scenario exercises action 247, and no script in the game
install uses it (see the exemption): the parked scenarios cannot run
it and nothing else in-tree calls the handler.
