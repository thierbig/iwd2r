# 0x5A04B0 CInfGame::CachingRequirements

Member of CInfGame in the original's InfGame.cpp, `__thiscall`
`LONG CachingRequirements(const CString& areaName)` (ret 4 — one by-
reference CString), 1181 bytes (0x5A04B0-0x5A0935).
Ported in commit 75f51fd2c.

## Body

Builds `CAreaFile` (CResHelper<CArea,1010>) from `CResRef(areaName)` with
SetResRef(..., TRUE, TRUE) and reads its data; NULL data returns 0. The
WED resref at area-header offset 8 goes through
`GetResID(CResRef(pAreaData + 8), 1003)` and `GetResFilePtr` (data is
released via `ReleaseData` between the two, before the NULL check on the
result). NULL BIF returns 0.

Single player (`cNetwork.m_bConnectionEstablished == FALSE`, CChitin
+0x1032): returns the WED BIF's own GetCachingRequirement (0x789A20).

Multiplayer: GetFileName fills the BIF name (return ignored; 0x78A0F0 is
a returning-FALSE stub this task — the Find that follows then misses and
falls back, which is why the test cannot drive past this point). Both
`m_tAreaLinkageCaching.Find` calls must return TRUE — the CPoint variant
(0x4037A0) yields the row, the label variant (0x403550) yields sXLabel/
sYLabel — else fall back to the WED BIF alone. Column 0 of the row
(bounds-checked: width < 1, row >= height, row < 0 → GetDefault) holds
the link count via atol; 0 falls back. `GetResFileID(sYLabel)` (one arg,
const CString&) seeds the walk: each iteration resolves that ID to a
CResFile, and a NULL file unwinds with the partial sum; otherwise the
BIF's GetCachingRequirement is accumulated, i advances, the next cell
(same bounds idiom, column i) names the next BIF. Loop exits with the
total.
