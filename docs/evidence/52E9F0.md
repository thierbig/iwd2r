# 0x52E9F0 CProjectileExplodingFlame::CProjectileExplodingFlame

The exploding flame arrow (vtable 0x84DCF4): DecodeProjectile's type 3.
The class builds the "SPFLMARR" exploding intermediate and then retunes it
for the flight, the same retuning its plain sibling CProjectileSPFLMARR
(type 4 family) applies to the BAM base. It carries the weapon missile's
two trail members minus its explosion colour byte: the decoder's
operator-new size is 0x4BA (Task 79's table row 53 confirms
0x52e9f0 / 0x4ba / store-tail), and 0x4B2..0x4B8 is the seven-byte trail
colour array with 0x4B9 the trail tick.

## Vtable check

0x84DCF4 sits in the contiguous exploding-family run in .rdata:
0x84DBDC (CProjectileExploding, 35 entries +0x00..+0x88 ending at
Explode) → 0x84DC68 (CProjectileExplodingWeapon) → **0x84DCF4** (this
class) → 0x84DD80 (CProjectileSkullTrap, starts with its deleting dtor
0x52F5E0). 0x84DCF4 against the base 0x84DBDC, slot by slot over the 35
entries: exactly THREE differ (verified by reading the exe's vtable
bytes).

- Slot 0x00: the scalar deleting dtor 0x52CE10 → 0x52EB10. Implicit
  ours — the class adds only the two trail bytes over the base, so the
  normal two-level destruction is exact.
- Slot 0x0C (AIUpdate, +0x0C): 0x52DD60 → 0x52EC80. Not in tree; left
  undeclared per the IcewindCProjectileScorcher precedent (a
  declared-but-undefined virtual becomes the key function and the
  vtable goes unemitted); ours inherits the base. (The fork carries a
  body for it; not needed for the ctor, per the seven precedents.)
- Slot 0x22 (Explode, +0x88): 0x78E730 → 0x52F1C0 — and this one IS
  ours: CProjectileExplodingFlame::Explode, already defined in tree
