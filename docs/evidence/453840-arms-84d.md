## Arm notes

- The three party arms are one walk spelled three ways, and the port
  spells all three with a comment saying so, no shared helper, per the
  house rule for byte-adjacent arms. 0x40AA is the 0x407A walk verbatim
  (retried GetShare, first failure fatal through the early epilogue)
  folding levels into 0xFF; 0x40D3 caches the party size once
  (0x45A27E, most arms re-read it every iteration), treats an
  unshareable member as skippable (0x45A39F) and a dead one as released
  and skipped (0x45A2FE); 0x40F7 drops the retry and makes a share
  failure fatal through UtilAssert and the raw return 0x45AE25, which
  bypasses the release tail -- dead code, ported faithfully.
- 0x40D6's NOONE path stores 0xFFFFFFFE (-2) and still reaches the
  release tail (0x45A5FE) -- truthy for the BOOL answer, the 0x40ED
  InTrap idiom; the test asserts != FALSE, not == TRUE.
- 0x40D6's GetUsageCount answer lands whole in esi (mov esi, eax at
  0x45A4C8) and each compare masks it to its low word (and esi, 0xffff
  at 0x45A4E8 / 0x45A505 / 0x45A522), so a charge count above 32767
  stays positive. The movsx at 0x45A4A5 sign-extends FindItemPersonal's
  slot index into the equipment indexing, not the count.
- 0x4013 squares two separate reads of GetSpecifics, each incremented
  first (inc 0x4546BF / 0x4546C5, imul 0x4546C6) -- the reads cannot
  differ, the port reads once and squares. Strictly greater than the
  squared range is out (signed jg 0x4546CB); the blocked and
  out-of-range answers both take the FALSE stub 0x45AB39 (xor esi,esi;
  jmp 0x45AD4C), which falls into the release tail, so the resolved
  share is released as usual.
- 0x4013's in-range path was not driven: CheckLOS runs on this object's
  area, and the harness has no loaded area (the 84c static vid-cell
  precedent); the test drives only the NOONE and out-of-range misses.
