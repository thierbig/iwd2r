## Notes

The switch on `nDualTileCode` handles 0, 1, 2 and 4 (the statics
`byte_851930/1/2` are 1/2/4 plus case 0); **anything else** falls to the
default at 0x5CB415, which the port was missing. The default is not
assert-only in the exe: it

- calls `CUtil::UtilAssert(0x23B, "C:\\Projects\\Icewind2\\src\\Baldur\\Infinity.cpp",
  "FALSE", NULL)` (0x5CB421/0x5CB426 — Infinity.cpp line 571), then
- if the assert returns, sets the tile (`CVidTile::SetRes`, 0x5CB441) and the
  add colour (`CVidImage::SetAddColor`, 0x5CB44B) and calls the **dual-tile
  fallback** `0x7B1F70` (0x5CB474; `SetRes`, the tile's `m_pDualTileRes` at
  +0x6C and `a6`), then jumps to the fog blit at 0x5CB479 instead of the
  `CVidTile::Render` pair below.

The fallback is dead code the #54 survey left unported (report-T96.md §2.1/§6:
`0x7B1F70` + `0x7B25E0` + `0x7CE3D0` + `0x7CE930`), so this port adds the
`default:` and its `UTIL_ASSERT(FALSE)` only, with a NOTE on where the exe goes
next. Our `CUtil::UtilAssert` aborts after `ShutDown`, so the flow after the
assert is unreachable either way; in the real engine an unknown dual-tile code
is a data error.

`tests/test_infinity.cpp` ("infinity: RenderToPrimary asserts on an unknown
dual-tile code") calls it on a zeroed tile set with a dummy surface for codes
3, 5 and 0xFF and expects `FailedAssert`; without the `default:` all three
assertions fail (the shared Render pair returns early on the empty tile set).
The render paths themselves stay unproven here: they lock a DirectDraw surface
and demand tile resources, which no runner fixture provides (the #49
`infinity` fixture covers `CheckTileState` and the scrolling walks only).
