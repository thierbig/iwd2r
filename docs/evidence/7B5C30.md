## Notes

The body is unchanged from the original; the port adds a file-lifecycle lock because the original's
call paths are not serialized:

- `CScreenConnection::EngineActivated` (0x5FA9B0) calls `CloseFiles` then `OpenOverride`, and it is
  reached (a) from the AI thread through `CBaldurProjector::PlayMovieInternal` →
  `CBaldurEngine::SelectEngine` → `CChitin::SelectEngine` (which holds `field_3AC`) and (b) from the
  **main thread** through `CChitin::OnAltTab` (0x7914D0), which calls
  `pActiveEngine->EngineActivated()` directly at 0x79159F, outside `CChitin::SelectEngine` and
  therefore without `field_3AC`.
- Both threads then test `m_bOpen` and call `CFile::Close` (which `fclose`s and only then nulls
  `m_hFile`). Interleaving the check and the `fclose` frees the same `FILE` twice: the issue #79
  `free(): double free detected in tcache 2` in the AI thread's `CTlkFileOverride::CloseFiles`.

The race is real in the port and was captured with a temporary widened-window build: main thread
`CChitin::OnAltTab → CScreenConnection::EngineActivated → CloseFiles` against AI thread
`CBaldurChitin::MainAIThread → CScreenConnection::TimerAsynchronousUpdate →
CBaldurProjector::PlayMovieInternal → CBaldurEngine::SelectEngine → CChitin::SelectEngine →
CScreenConnection::EngineActivated → Open`. The original has the same unlocked pair; the Windows
binary's scheduling just did not expose it. The fix is one file-static `CCriticalSection` taken by
`Open` (0x7B5A50) and `CloseFiles`; see `tests/test_tlk_override.cpp`, which aborted on the unfixed
code and passes with it.
