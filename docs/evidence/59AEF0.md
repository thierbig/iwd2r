## Notes

0x59AEF0-0x59B1B8. Bucket index = `(remoteObjectID >> 16) & 0x7FFF`; the
array grows when the index is past `m_nArraySize` (0x59AF1A). The
`Find(remotePlayerID, remoteObjectID)` duplicate test runs before the node is
linked (0x59AFD5) and refuses a hit unless the local id matches.

The node is linked at 0x59B063-0x59B07A: a non-empty bucket gets the new node
as its head with the old head in `pNext` (0x59B075-0x59B07A), and an **empty**
bucket is assigned the new node directly (`mov [edi], eax` at 0x59B071). The
ported body's `else` branch assigned NULL instead, so the first entry added to
every empty bucket was leaked and could never be found. This is a pre-existing
bug in merged code, not a message-layer one: `CGameObjectArray::Add` registers
every new object through this helper (src/CGameObjectArray.cpp:352, :358,
:372, :378, :388, :394), so a session that registers a second object whose
remote id falls in a fresh bucket loses that remote-object entry and the
object can never be found through `Find`. It went unnoticed because no test
registers a second object that lands in an empty bucket (the in-tree object
tests use one object or the same bucket), and the object-control receive
handlers (rows 4-6, 0x430910/0x430BE0) were the first code to exercise
`ChangeControl`'s add of a new remote pair with a different bucket index.

After the fix `Add` is exercised directly by
tests/test_message_object.cpp (empty-bucket insert, same-bucket chain,
duplicate refusal). Unverified against the original at run time: the
differential emulator needs our MSVC x86 build and its venv, neither of which
this box has; the shape above is read from the annotated disassembly.
