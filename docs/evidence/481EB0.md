# 0x481EB0 CGameContainer::RemoveItem

Member of CGameContainer in the original's GameContainer.cpp, `__thiscall`
`void RemoveItem(SHORT nSlotNum)`, 396 bytes (0x481EB0-0x481F03).
Ported in commit 482d8aee.

## Body

FindIndex(nSlotNum): when the position exists, the slot's item (if any)
goes to the game's disposable list via AddDisposableItem; then — still
inside the position check, outside the item check — `m_pArea->m_resRef ==
RESREF_AR6051` (no null check on m_pArea in the original) calls
sub_480480(nSlotNum, NULL) to clear the slot's render state, and
RemoveAt(pos) drops the slot. Unconditionally, a
CMessageContainerAddItem carrying a default-constructed CItem, slot
0x7FFF, TRUE, and the container's id twice is posted through the
chitin's message handler — the message goes out even when the slot
number found nothing, and it carries no trace of the removed item.

## Callers

Not in tree: both call sites (0x4C88E7, 0x4C89E1) are inside the
function at 0x4C83F0. Our tree's CGameObject::FloatText is 0x4C80E0, a
different function, so no TODO was placed — the caller does not exist
to carry one.

## Test

Driven directly in tests/test_ai.cpp [ai][data]: on a fresh two-item
container, RemoveItem(0) leaves the second item at slot 0, a second
RemoveItem(0) empties it, and a third call on the empty list still
queues its CMessageContainerAddItem (three queued after ClearMessages).
The AR6051 arm and the disposable-list handoff are not observable
headless: the test's area is not AR6051, and AddDisposableItem only
appends to the game object's list.
