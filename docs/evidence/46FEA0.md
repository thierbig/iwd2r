## Notes

IEex calls it `CGameArea_CheckRestEncounter` (cited in docs/evidence/5BFC40.md and
5C1350.md); Ghidra has no name for it, hence FUN_0046fea0 above. Its only caller
is `CInfGame::RestPartyPrivate` (0x5C1350, call at 0x5C151E), which ends the rest
when it answers TRUE. Size 2,744 bytes.

The decision is wholly `CAreaFileRestEncounter m_headerRestEncounter`
(CGameArea +0xEC) and the clock:

- `m_activated` (+0xA6) zero: FALSE, no draw.
- Otherwise one roll: `rand() % 100 <=` `m_probDay` (+0xA8) in the day band
  `TIME_DAWN (27000) <= (m_gameTime + offset) % 108000 < TIME_NIGHT (99000)`
  (the `div [0x84EC10]` 108000 at 0x46FEE7, `cmp [0x84EC34] 99000; jae` night at
  0x46FEED-0x46FEF3, `cmp [0x84EC1C] 27000; jae` day at 0x46FEF5-0x46FEFB: the
  27000 tick is the day side), else `<= m_probNight` (+0xAA). A miss at
  0x46FF33-0x46FF47 adds TIMESCALE_MSEC_PER_HOUR to the offset and returns
  FALSE: the retry counter (`bl`) goes 0 -> 1 and the back edge `cmp bl,1; jb`
  at 0x46FF3B-0x46FF3E is never taken, so a second hour's roll does not happen -
  the loop is only the shape the compiler kept.
- `m_randomCreatureNum` (+0x98) or `m_maxTypeNum` (+0xA4) zero: FALSE.
- `delay = offset + rand() % TIMESCALE_MSEC_PER_HOUR` (the original draws only
  when that constant is not zero; ours keeps the guard), then
  `CTimerWorld::AddCurrentTime(delay)` - which ignores a value of <= 900 - and
  `CInfGame::FeedBack(7 = FEEDBACK_TIMEPASSEDREST, delay, TRUE)`.

| 4 | `rand() % 10` | always, after the search (0x470309): the rarity |
| 5 | `rand() % m_randomCreatureNum` | the creature entry (0x470336) |
| 6 | `rand() % 5` | always, the count jitter `m_maxTypeNum + that - 2`, clamped at 1, plus one in nightmare mode (`m_cOptions.m_nNightmareMode`) (0x470342) |
| 7 | `rand() % 9` | once, the first creature's formation, when draw 4 was non-zero (0x4705BD) |
| 8 | `rand() % 2` | per creature, when draw 4 was 0 (0x470777): the spawn square's nudge |

The square search: the protagonist's search square (`m_characterPortraits` slot
whose sprite's m_id is `CInfGame::GetProtagonist()`), then 9 rays of up to
`m_visibility.field_E` cells in the 8 compass directions (ray 4 is the square
itself and is skipped). A cell must be inside `m_search.m_GridSquareDimensions`,
have `CSearchBitmap::GetLOSCost(cell, CGameObject::DEFAULT_VISIBLE_TERRAIN_TABLE
0x84C514, ...) != -1` and pass `CVisibilityMap::IsTileVisible(PointToTile(cell
centre))`. The farthest cell wins (`nSteps > best`), an equal one needs
`rand() % 7 == 0`; the ray ends at the first candidate, and a fully walked ray
offers its last cell the same way. Out of the grid counts one step less. The
winning ray is the index into the formation offsets.

Placement per creature, up to five tries: with draw 4 non-zero, the first
creature fetches `CAIGroup::GetOffsets(rand() % 9 + 1, direction * 360 / 16 % 360,
TRUE)` facing the protagonist and every creature takes
`offsets[ray % 12] / OFFSET_MULTIPLIER (1000)` (NOTE: the index is not bounded by
the array GetOffsets returned - max(members, 6) - so a party of six or fewer
reads past the block; the port reads (0, 0) there, as CGameSpawning::Spawn
does); with draw 4 zero the best search square goes through
`GetNearestOpenSquare` and is nudged back by `(1 - ray % 3, 1 - ray / 3)` when
`rand() % 2 == 0`. The pixel point is `square * 16/12 + 8/6`; a tile index past
`m_nWidth * m_nHeight` retries, and a fifth failure drops that creature.

Each CRE: `CCreatureFile::SetResRef`, `GetDataSize`/`GetData`, `new
CGameSprite(data, size, 0, 1, m_lifeSpan * TIMESCALE_MSEC_PER_SEC (15) +
m_gameTime, m_huntingRange, m_followRange, 0x7FFFFFFF, protagonist position, 0)`,
then two SetResRefs (the game's resref string, then the area's), `ReleaseData`,
`AddToArea(this, spawnPoint, 0, m_animation.GetListType())` and
`SetFacing(GetDirection(protagonist position))`.

Quirks kept and named in the port: the dead debug sprintf at
0x4708D7-0x4708F3 (a 200-byte buffer formatted with "Spawned creatures dropped
due to invalid positions: %d of %d" and freed unprinted; not ported); the
message's caller and target are the *last* party slot's id, because the scan for
the protagonist never breaks when it finds it (the last id stays in the local;
an empty party would read an unset stack point, ours starts (0, 0)); the offsets
over-read above; the scalar `operator delete` of GetOffsets' `new[]` block (ours
`delete[]`).

The message is `CBaldurMessage::DisplayTextRef(-1, m_randomCreatureString[entry],
0, 0x590A5, -1, caller, target)` (the marker -1 is the DWORD at 0x84C960).
