# 0x530010 CProjectile84DE94::Fire

The SPLightB searing-light shot's launch (class ctor and decoder cases in
docs/evidence/52FE90.md). It is the class's only Fire override: against the
CProjectileBAM vtable 0x84D9C4 the class differs in exactly two slots, and
this is slot 0x6C. The body allocates one rebounding-bolt child (so every
call spawns one child, whatever the bounce count), copies the shot's whole
effect list into the child, hands `m_nBounces` over, and launches the child
with the source id in **both** id argument slots.

Listing source (read-only): the pinned local vanilla copy
`~/.local/share/iwd2r/game/iwd2.exe`, MD5
`200f038bec3ed50a964d68b3f0f1f0e7`, through the tree's
`tools/parity/annotate.py` (pefile + capstone). The Linux parity host was
unreachable (`No route to host`) for this task, so no remote read, oracle
case or Frida trace backs this file: it is a static read plus the unit test
described at the end, not a trace claim.

## Instruction walkthrough

Signature. `ret 0x1c` = seven 4-byte slots, matching
`Fire(CGameArea* pArea, LONG source, LONG target, CPoint targetPos, LONG
nHeight, SHORT nType)` (the SHORT is widened in the call). At the body's
base stack pointer S (esp at 0x530090, after the seven frame dwords):
`[S+0x20]` pArea, `[S+0x24]` source, `[S+0x28]` target, `[S+0x2c]`
targetPos.x, `[S+0x30]` targetPos.y, `[S+0x34]` nHeight, `[S+0x38]` nType.

- 0x530010-0x53001e: the MSVC SEH registration record (trylevel -1,
  handler 0x81b45b, old `fs:[0]` saved). Nothing in it is a game call; it
  exists solely because the operator-new below can throw. The port spells
  the allocation as ordinary `new`.
- 0x530025-0x530028: frame dwords — the `this` save, ebp, esi, edi. The
  `this` save at `[S+0xc]` is never reloaded (ecx is set from ebp/edi
  instead); it belongs to the compiler's temp bookkeeping.
- 0x530029-0x530035: `operator new(0x2EC)` and `add esp,4`. 0x2EC is the
  rebounding bolt's native sizeof (docs/evidence/57D390.md), so the child
  is exactly that class.
- 0x530038-0x530051: the standard MSVC null check around the ctor. The
  pointer is held in the frame local at `[S+0xc]` (the cleanup state),
  trylevel is set to 0 for the construction, `CProjectileReboundingBolt::
  CProjectileReboundingBolt` (0x57D390) runs, and the result moves to edi
  (the child). The null arm (0x530053) sets edi = 0. The emitted null
  branch is the compiler's `new` shape, not a project choice.
- 0x53005d: trylevel back to -1, closing the cleanup region. There is no
  delete in the body: the child is owned by its Fire.
- 0x530055: `mov esi,[ebp+0x82]`. `ebp` is `this`. The shot's effect list
  begins at `this+0x7E` (`CProjectile::m_effectList`, a CGameEffectList,
  i.e. a CTypedPtrList); the CPtrList head node lives four bytes in, at
  +0x82. So this reads the first effect node, exactly what
  `m_effectList.GetHeadPosition()` walks.
- 0x53005b/0x530065: empty list skips the copy loop to the launch tail.
- 0x530067-0x530072: loop preamble. `ebx = child+0x7E` (the child's own
  effect list); `eax = node`; `ecx = node->data` (MFC CNode's data at +8,
  a CGameEffect*); `eax = [ecx]` (the effect's vtable); `esi = [esi]`
  (next node, advanced before the call).
- 0x530074: `call [eax+4]` — the effect's vtable slot 1, i.e.
  `CGameEffect::Copy`. The body never calls a concrete effect copy
  directly; each concrete effect supplies its own Copy. (Our port calls
  `pEffect->Copy()`.)
- 0x530077-0x53007e: `xor ecx,ecx; mov cx,WORD [edi+0x6e]` — the child's
  `m_projectileType` (WORD at +0x6E), **zero-extended** to a DWORD, then
  stored at `[copy+0x9c]`. `CGameEffect`'s vtable sits at offset 0 and
  `CGameEffectBase`'s members start at +4, so +0x9C is that base's
  `m_projectileType` (+0x98 base-relative, cf. the ctor 0x452C80's
  `[ebp+0x9c] = 0` and AddEffect 0x51EA90/0x51EAB0's identical store).
  The child is fresh from its ctor and no decoder tail has stamped it, so
  the value is 0 here — the original does not copy the parent's type. The
  port writes `pCopy->m_projectileType = pChild->m_projectileType`, which
  reproduces the WORD-to-DWORD zero extension.
- 0x530084-0x53008d: `CPtrList::AddTail` (0x7FBE4E) appends the copy to
  the child list at `ebx = child+0x7E`, then the loop continues while the
  saved next node is non-null. The **parent list is only read**: no
  RemoveHead/RemoveAll, and the copies are new objects. This is the same
  copy-the-effects shape as CProjectile84E030::Fire (0x530B60), except
  that the target list is the freshly constructed child and the stamped
  type is the child's.
- 0x530090-0x5300bc: the launch argument shuffle. `edx = [ebp+0x2a0]`
  (`this->m_nBounces`). Before the call the pushes read, in order:
  nType from `[S+0x38]`; targetPos.y from `[S+0x30]`; nHeight from
  `[S+0x34]`; targetPos.x from `[S+0x2c]`; then `[S+0x24]` (source)
  **twice**; then pArea from `[S+0x20]`. The target argument, `[S+0x28]`,
  is never read. With __thiscall's right-to-left order this is
  `child->Fire(pArea, source, source, targetPos, nHeight, nType)`.
- 0x5300b4: `mov [edi+0x2b2],edx` — the bounce hand-off, parent +0x2A0 to
  child +0x2B2 (`m_nBounces`). There is no branch on the value: the
  ctor's -1 and the decoder's 1/6 all copy verbatim. One child per call.
- 0x5300ba-0x5300bf: `edx = [edi]` (the child vtable), ecx = child,
  `call [edx+0x6c]`. Slot 0x6C of the child's vtable 0x85101C is
  0x57D700 (`CProjectileReboundingBolt::Fire`, parked in this tree —
  docs/wso/import-parked/57D700.json), so in the original the child runs
  its own rebound Fire. Ours does not declare that override, so the same
  call dispatches to the inherited CProjectileSingleTarget::Fire
  (0x5791D0); this is the same accepted structural deviation as the other
  parked row, not a change in the hand-off arguments.
- 0x5300c2-0x5300d3: epilogue. The child Fire is thiscall with `ret
  0x1c`, so it has already popped the seven arguments; `[esp+0x10]` is
  the saved `fs:[0]`, restored before the three frame pops and
  `add esp,0x10`. The parent is neither deleted nor removed: the original
  leaves the searing light in flight and only the child is registered by
  its own Fire.

## Callees

- `operator_new` 0x7FC95B — 0x2EC bytes for the CProjectileReboundingBolt
  child (the one non-inlined allocation).
- `CProjectileReboundingBolt::CProjectileReboundingBolt` 0x57D390 —
  CRESRef("LightnT") base, strike tracker, unbounced -1, 60-tick duration,
  doubled speed (docs/evidence/57D390.md).
- `CGameEffect::Copy` through the effect vtable (+4) — one per parent
  effect; the concrete body is effect-specific.
- `CPtrList::AddTail` 0x7FBE4E — append each copy to the child's effect
  list at child+0x7E.
- `CProjectileReboundingBolt::Fire` 0x57D700 through the child vtable
  (+0x6C) — parked; in our build the slot is the inherited
  CProjectileSingleTarget::Fire 0x5791D0.
- 0x81B45B — the compiler's SEH handler for the allocation; no game code.

No RNG: the body contains no call to the rand helper
(msvc_rand/iwd2r_rand), and it makes no branch on the bounce count. The
unit test therefore sets no seed.

## Vtable check

Read from the exe's .rdata (`CProjectileBAM` base = 0x84D9C4), slot by
slot over 34 entries (+0x00..+0x84):

- 0x84DE94 +0x00 = 0x52FED0 (deleting dtor; base 0x52B010)
- 0x84DE94 +0x6C = **0x530010** (Fire; base 0x52C050)
- every other slot equals the base, including +0x4C 0x52B190 (Render),
  +0x70 0x529FB0 (OnArrival), +0x74 0x5551B0 (RemoveSelf), +0x78
  0x52A1A0 (DeliverEffects) and +0x80/+0x84 0x5297D0/0x52BD20. The dword
  at +0x88 is 0x5301C0, slot 0 of the next vtable (0x84DF1C), not an
  entry of this one.

So Fire 0x530010 is genuinely this class's override and no other slot is
class-specific. The child's vtable 0x85101C +0x6C reads 0x57D700 as noted
above.

## What the unit test covers (actual, not an oracle claim)

`tests/test_visual_projectiles.cpp`, case "visual projectiles: the searing
light launches a rebounding bolt with its effects and bounces"
(`[visualprojectile][data]`; runs only with game data). For each bounce
arm 0, 1 and 6 it builds a CProjectile84DE94 directly, stamps
`m_projectileType = 205` (the type-206 decode's value) and two decoded AC
effects with distinct `m_effectAmount` (0x11, 0x22), then calls
`Fire(pArea, character, goblin, goblinPos, 7, 3)`:

- exactly one child: `AddedOne<CProjectileReboundingBolt>(pArea)` finds
  the single newly added projectile, with a valid object id and
  `m_pArea == pArea`;
- the argument hand-off: child `m_sourceId` and `m_targetId` both equal
  the character's id, and `m_targetId != goblin` — the parent's target
  argument was dropped as the listing shows;
- the bounce hand-off: child `m_nBounces` equals the parent's 0, 1 or 6
  (the body has no branch, so all three travel the same path);
- the child ctor's own stamps survive: `m_nDuration == 60`;
- the effect copies: child list count 2, distinct objects in the parent's
  order with the same effect ids and amounts, each stamped
  `m_projectileType == 0` (the child's type, proving the stamp source is
  the child and not the parent), while the parent keeps its two effects
  at `m_projectileType == 205` and its own head pointer;
- the parent is left unregistered: `light.GetId() == INVALID_INDEX`.

The test removes the child (`RemoveSelf`) and sorts the area between arms.
Result on this machine: 97 assertions pass. The full `[visualprojectile]`
suite ran 75 cases; the new case passed every time. Three other cases
failed across the full-suite runs: Cloudkill (test line 3675) and the
breath's secondaries (line 3745) pass when run alone (the suite's known
order-dependent flake family), and the short AScorcT beam (line 4411,
`direct.m_speed == pBeam->m_speed`, 28 vs 0) still fails alone — that
case touches no symbol this change modifies and is a pre-existing
data-dependent failure of this checkout, not a regression from this Fire.
The neighbouring `[projectile]` suite also passes: 15 cases, 359
assertions.
