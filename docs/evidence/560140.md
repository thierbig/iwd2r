# 0x560140 IcewindCGameEffectSummon::ResolveSourceSprite

The share-loop virtual the class is missing: the exe's vtable 0x84F0A8 has
twelve slots and +0x28 is this body, +0x2C `SpawnFromResRef`. Our class
declared only `SpawnFromResRef` as its extra virtual, so it compiled to
+0x28 -- one slot early, and with no +0x2C at all. The body is a
`GetShare` do-while on `m_sourceID` that retries while the array answers
SHARED or DENIED and writes the sprite straight into the +0x18C member,
returns silently on BAD_INDEX, asserts (line 2076) on any other
non-SUCCESS that then falls through to `ReleaseShare`, and releases the
share on SUCCESS.

## Slot evidence

- **+0x28 is this body.** The dword at 0x84F0A8+0x28 is 0x560140. The only
  caller is `IcewindCGameEffectSummon::ApplyEffect` 0x55F710, which issues
  `mov eax, [esi]` / `call dword ptr [eax+0x28]` as its first two
  instructions (0x55F72A-0x55F72D) and then reads `[esi+0x18c]` at
  0x55F730-0x55F738 -- i.e. it dispatches this virtual to resolve the
  source sprite and uses the member afterwards. There is no direct call
  site (the callgraph row `560140 599A50 599E70 780C00` is the body's own
  callees), so vtable dispatch is the whole reachability.
- **+0x2C is SpawnFromResRef.** 0x55FAD0; ApplyEffect calls it through
  `call dword ptr [edx+0x2C]` at 0x55F7B5 with the resref at +0x2C and the
  target CPoint at +0x84.
- **The three holes this row does not close.** The class carries no
  `/* 00NN */` slot comments at base, so `tools/parity/vtable_audit.py`
  reports `IcewindCGameEffectSummon declares no /* 00NN */ virtual slots in
  src/*.h` and skips it -- which is exactly why the off-by-one was
  invisible. The class's real vtable disagrees with our source at three
  slots besides this row's: +0x00 the scalar deleting dtor 0x55F6D0 (the
  body 0x55F6F0 is the compiler-generated base-vtable reset + CSound
  teardown, and our implicit dtor emits the same), +0x08 ApplyEffect
  0x55F710 (parked row, its docs/evidence/55F710.md was deleted by
  e9d3e4af when the import was parked), and +0x1C UsesDice 0x49FC40 (a
  6-byte `return TRUE`, unported). This row adds the trailing virtual and
  fixes the slot numbering; it deliberately does not annotate the class,
  because that would turn the audit red on those three pre-existing holes.
  A follow-up task tracks the annotation plus the three bodies.

## Tests

`tests/test_effects_iwd.cpp`, `effects-iwd: the summon class adds its share
loop at vtable slot 10, before SpawnFromResRef` (`[effects][vtable]`). A
pointer to a virtual member function stores 1 + its byte offset in the
Itanium C++ ABI (the tests build with gcc/clang), whose vtable puts a
D1/D0 destructor pair before the other virtuals and uses pointer-sized
entries; the test maps that back to the exe's one-destructor, 4-byte-slot
numbering and asserts Copy +0x04, base DisplayString +0x20 and OnRemove
+0x24, the derived Copy +0x04, ResolveSourceSprite +0x28 and
SpawnFromResRef +0x2C. A declaration order that moves either new virtual
(the parked header's Spawn-only shape, or a third virtual declared after
SpawnFromResRef) fails the test, and the declaration going missing
altogether is a compile error in it. No game data is needed (the test pins
the exe's slot table, not engine state).

## Notes

- The result constants are read through the byte globals the source names:
  SUCCESS 0x85186C, BAD_INDEX 0x85186F, SHARED 0x851870, DENIED 0x851871
  and THREAD_ASYNCH 0x851873 (`src/CGameObjectArray.cpp`).
- The exe's loop head is 0x560143 (after `push esi; mov esi, ecx`), so the
  reload of `g_pBaldurChitin` and of `[esi+0x10C]` happens on every retry;
  the port keeps the same shape.
- GetShare with THREAD_ASYNCH cannot in fact return SHARED/DENIED (its
  async path returns SUCCESS/BAD_INDEX/DELETED only), so the retry is dead
  on that thread; the port keeps it because the exe has it.
- The name `ResolveSourceSprite` is the WSO fork's (the import at
  fccecc9d used it); the exe export is `FUN_00560140` and the exact C++
  name is unresolved -- the behaviour is "resolve the caster sprite from
  m_sourceID into field_18C and drop the share".
- Not verified: the live share/retry/release behaviour. What is verified:
  the vtable slot order and count (test + image dump), the body's
  instruction-level shape (annotate.py listing), and the call path
  (ApplyEffect's `call [eax+0x28]`).
