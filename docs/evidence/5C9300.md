## Notes

Ported as `CGameObjectArray::AnySpriteIsDiseased` (IEex's label for 0x5C9300,
`CGameObjectArray_AnySpriteIsDiseased`; the states it tests are Mold Touch and
Shroud of Flame). The lock is `CSingleLock(&m_cs, FALSE)` then `Lock(INFINITE)`
- the original does not test the result (no `UTIL_ASSERT` here, unlike
FindObjectId) - and both exits unlock.

Entry checks by offset: +0x6 `m_objectId == -1` (free or deleted slot) and +0x8
`m_objectIntPtr == -1` (the deleted marker `Clean` writes); stride 0xC is
`sizeof(CGameObjectArrayEntry)`. Type test: vtable slot 1, `GetObjectType() ==
0x31` (`CGameObject::TYPE_SPRITE`). State test: `[esi+0xA10]` is
`CGameSprite::m_derivedStats` (+0x920) + `CDerivedStats::m_spellStates`
(+0xEC) + 4, i.e. bit 46 = 0x40 in AH and bit 47 = 0x80 in AH of a
`std::bitset<256>` at those offsets; the port tests
`m_spellStates[SPLSTATE_MOLD_TOUCH]` and `[SPLSTATE_SHROUD_OF_FLAME]`.

**Loop bound, kept as it is:** the original tests `index < m_nMaxArrayIndex`,
not `<=` (0x5C933A exits when it is `<= 0`, 0x5C9379 is `jl`), so the object in
the last used slot is not examined - while `FindObjectId` (0x59ABD0) and the
destructor (0x599960) scan it inclusively. The port reproduces the original's
loop with a NOTE beside it; do not "fix" it without a ruling that deviates from
the binary.
