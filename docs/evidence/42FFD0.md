### The wire payload

`CBaldurMessage::ObjectAdd` writes, and the ported
`CGameContainer::MarshalMessage` / `CGameSprite::MarshalMessage` produce:
`{PLAYER_ID remotePlayerID; LONG remoteObjectID; BYTE objectType;
DWORD objectDataSize; objectData[]}` after the 3-byte spec header. The exe
loads the type/size with the inlined SPEC_MSG_HEADER_LENGTH (0x85E670): the
pair at pData+3/+7, type at pData+0xB, size at pData+0xC (unaligned DWORD),
data at pData+0x10 (0x430081-0x4300A1). Guards: session open
(`g_pChitin + 0x1032`), then `nMsgFrom != (BYTE)m_nLocalPlayer` (0x8CF6D8 +
0x10DC, compared as a zero-extended byte, 0x430009); `m_bInOnObjectAdd` is set
at once and cleared before every normal return. A pair `Find` already maps is
dropped; a zero data size is accepted as a no-op (TRUE).

### The CCreatureFile demand inline (blocker 3)

0x43031F-0x4303EC is an inlined `CResHelper<CResCRE, 1009>::SetResRef`: it
compares the helper's resref with the new one (0x430324-0x430336), cancels a
pending request on the old one (0x43033C-0x430362, gated on `pRes != NULL &&
cResRef != "" && bLoading`), and for a non-empty new resref calls
`CDimm::GetResObject(resRef, 0x3F1, TRUE)` (0x430397 pushes the type 0x3F1 =
1009 and the warning flag TRUE), then on success sets `bLoading` and calls
`CRes::Request`. That is byte for byte the ported
`CResHelper<CCreatureFile, CResCRE, 1009>::SetResRef(cNewResRef,
bSetAutoRequest, bWarningIfMissing)` body, and the two flag constants
compiled into the exe are `TRUE, TRUE` (the success path unconditionally
requests, and the warning argument is a literal 1), so the port calls
`creatureFile.SetResRef(resRef, TRUE, TRUE)`. `CCreatureFile` itself is the
`CResHelper<CResCRE, 1009>` subclass, and `GetData`/`GetDataSize` are its
ported accessors.

### Constants and the AI-type stamp

The exe reads the object types and placement constants from rdata:
[0x84C502] = 0x11 (`TYPE_CONTAINER`), [0x84C507] = 0x31 (`TYPE_SPRITE`),
[0x84D6A0] = 16 and [0x84D6A1] = 12 (`CPathSearch::GRID_SQUARE_SIZEX/Y`),
[0x84C50C] = 0 (`CGameObject::LIST_FRONT`, the AddToArea list type),
[0x847C36] = 3 (`CAIObjectType::EA_FAMILIAR`) and [0x847C3C] = 15
(`CAIObjectType::EA_CONTROLCUTOFF`, the add-to-allies gate). The enemy/ally
byte is written to `m_nEnemyAlly` (CAIObjectType+4) of three AI types: the
current type (0x430506-0x4305AD, `SetAIType(typeAI, FALSE, FALSE)`), the
start type (copied from `m_liveTypeAI`, 0x430553-0x430591) and the live type
(copied from `m_liveTypeAI`, 0x43052B-0x4305C4). Enemies-or-allies at or
below EA_CONTROLCUTOFF become allies, and EA_FAMILIAR also becomes a
familiar and `MakeGlobal()`. The sprite is then added at
`{ptOpen.x * 16, ptOpen.y * 12}` with list type 0 (0x430609-0x430643).
The common tail calls
`CGameRemoteObjectArray::InitiateControl(remotePlayerID, remoteObjectID,
object->m_id)`, stamps the object's `m_remoteObjectID`/`m_remotePlayerID`
and answers TRUE (0x4306A7-0x4306F7).

### Quirk kept from the exe

A container whose area is not loaded returns FALSE **without clearing
`m_bInOnObjectAdd`**: 0x430150 jumps to 0x430700, past the clear at
0x4306FD. The port keeps that (and tests it) rather than silently fixing it;
if the maintainer wants it fixed it should be a separate decision with its
own commit. On the two early exits the port also frees the copied block with
`DestroyBuffer` where the exe jumps past its free (0x4306F9/0x430700); the
block is the static 0x8D8FE4 buffer for any realistic payload, so this only
avoids a >0x4000-byte leak and changes no engine state.
