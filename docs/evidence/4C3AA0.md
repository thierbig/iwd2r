# 0x4C3AA0 CGameEffectDisguise::~CGameEffectDisguise

The destroying body of the disguise effect (opcode 437): when an equipped
item's disguise is destroyed it undoes the disguise on the sprite the effect
names. The export calls it `CGameEffect_opcode_437_Destruct`; the class's
vtable fixes the identity below.

Read against the complete listing of 0x4C3AA0-0x4C3E17 (888 bytes,
`functions.tsv`: 888) produced by

    /Users/bartschneider/.local/share/iwd2r/parity-venv/bin/python -I tools/parity/annotate.py 0x4C3AA0

with the local vanilla `iwd2.exe` (MD5 `200f038bec3ed50a964d68b3f0f1f0e7`,
the pinned `oracle/loader/vanilla.json` value) and the tree's
`functions.tsv`/`callgraph.tsv` exports. The Linux host was unreachable
(`No route to host`), so the read-only parity rig was not run remotely; the
annotator, exe and exports it uses were the local pinned ones.

| 0x04 | 0x49D8A0 | CGameEffectDisguise::Copy |

0x4C3AA0 is therefore `~CGameEffectDisguise` (the non-deleting body), and
the class declares no `OnRemove`: the restore happens only in the
destructor. `CGameEffectList::RemoveAllOfType` calls `pEffect->OnRemove()`
then `delete pEffect` (0x4C08E0), so the normal removal path reaches the
restore exactly once, through the delete.

## Branch and member map

Prologue and vtable: the function writes its own vtable first
(`[ebx] = 0x84B520`, 0x4C3AC0) and the base's last (`[ebx] = 0x848848`,
0x4C3DFC) before chaining to the base destructor.

1. 0x4C3AC6-0x4C3AD6: `mov eax, [ebx+0x188]; test eax,eax; je 0x4C3DEE`.
   Member 0x188 is `CGameEffect::field_188`, the flag CItem::Equip sets to 1
   on the effects of an equipped item (CItem.cpp, `pEffect->field_188 = 1`).
   With 0, the whole restore is skipped and control falls straight to the
   base teardown. This is why a spell's disguise is not undone on removal in
   the original.
2. 0x4C3ADC-0x4C3AEF: `g_pBaldurChitin` (0x8CF6DC) -> `+0x1C54`
   (CInfGame*) -> byte `+0x1B93` is `CInfGame::m_bInDestroyGame`; nonzero
   skips the restore (0x4C3AEF -> 0x4C3DEE). The members match the source
   declarations `CInfGame.h` (`/* 1B93 */ BOOLEAN m_bInDestroyGame`).
3. 0x4C3AF5: `ebp = [ebx+0x10C]` = `CGameEffect::m_sourceID`; the sprite is
   the effect's *source*, not a parameter. Saved to a local at 0x4C3AFB for
   ReleaseShare.
4. 0x4C3AFF-0x4C3B3D: the object-array share loop:
   `GetShare(sourceId, THREAD_ASYNCH (0x851873 == 0), &pObject, -1)`, repeated
   while the result is `SHARED` (0x851870) or `DENIED` (0x851871); a result
   other than `SUCCESS` (0x85186C) jumps to the base teardown at 0x4C3DEE
   without a ReleaseShare. This is the tree's standard
   `do { ... } while (rc == SHARED || rc == DENIED); if (rc != SUCCESS) ...`
   shape (e.g. CAIGroup.cpp).
5. 0x4C3B43-0x4C3B4B: pObject is cast to CGameSprite and
   `UnequipAll(TRUE)` runs first (0x71B460, `push 1` at 0x4C3B49).
6. 0x4C3B50-0x4C3C48: if `pSprite->GetArea()` (sprite+0x12) is NULL, skip
   to 0x4C3C4C; otherwise, when `GetListType() != LIST_FLIGHT`
   (byte 0x84C50E == 2), `RemoveObject(gridPos, GetAIType().m_nEnemyAlly,
   GetPersonalSpace(), field_54A8, field_7430)` at 0x4C3C43. `gridPos` is
   `GetPos() / (GRID_SQUARE_SIZEX, GRID_SQUARE_SIZEY)` (bytes 0x84D6A0 and
   0x84D6A1, 16 and 12); the arguments are pushed in the order
   point, enemy-ally, personal space, 0x54A8, 0x7430, matching
   `CSearchBitmap::RemoveObject(const CPoint&, BYTE, BYTE, BOOL, BOOLEAN&)`.
   The ObjAnimation.h inline asserts (lines 0x826 and 0x82D, i.e. 2086 and
   2093) are the GetListType/GetPersonalSpace NULL checks.
7. 0x4C3C4C-0x4C3C62: `test ah, 8` on `[ecx+0x5BC]` tests
   `pSprite->GetBaseStats()->m_generalState & STATE_DEAD` (0x800;
   `CCreatureFileHeader::m_generalState` at baseStats+0x18, baseStats at
   sprite+0x5A4). Set: jump to 0x4C3D9F, skipping both the animation restore
   and the AddObject. Clear: continue.
8. 0x4C3C5B-0x4C3CA4: when `field_18C != -1`, delete the current animation
   type (`call [edx]` with `push 1` at 0x4C3C8C, the scalar deleting
   destructor) and call `CGameAnimationType::SetAnimationType(field_18C,
   pSprite->m_baseStats.m_colors (sprite+0x5C8), GetDirection()
   (sprite+0x5380))` at 0x4C3C91, storing the result at sprite+0x50F0. This
   is the inlined `CGameAnimation::SetAnimationType` (ObjAnimation.h). When
   `field_18C == -1` (never had an animation to go back to) the animation is
   left alone.
9. 0x4C3CA7-0x4C3D9B: the same area/list-type test, then
   `CSearchBitmap::AddObject` at 0x4C3D96 with the restored animation's
   personal space. It is inside the non-dead branch, so a dead sprite's
   footprint stays removed until step 10 puts it back.
10. 0x4C3D9F-0x4C3DCA: `JumpToPoint(GetPos(), TRUE)` (0x745950; the `push 1`
    at 0x4C3DA0 is JumpToPoint's spriteUpdate argument, scheduled before the
    GetPos virtual call), then `SetIdleSequence()` (0x707170) and
    `EquipAll(TRUE)` (0x71B5E0). All three run unconditionally for a
    successful share, including the dead and the `field_18C == -1` cases.
11. 0x4C3DCA-0x4C3DED: `ReleaseShare(sourceId, THREAD_ASYNCH, -1)` (0x599E70).
12. 0x4C3DEE-0x4C3E17: the base destructor inlined: `[ebx] = 0x848848`
    (CGameEffect's vtable), then `CSound::~CSound` on `this + 0x124`
    (`CGameEffect::m_sound`), then SEH/epilogue. This is the same body as
    0x499B10, CGameEffect::~CGameEffect.

No `operator_delete` appears in the body: the deleting destructor at
0x49D960 does it after the flag test.

## Notes

- Destructor versus OnRemove: because slot 0x24 of 0x84B520 is the base
  OnRemove (0x4A51D0) and the class declares no override, `OnRemove` does
  nothing for this effect. The restore is the destructor's only. The test
  states that with a compile-time assertion on the member-pointer type and
  then calls `OnRemove` on a live disguise and checks that nothing changed
  before the delete. There is no second restore site to guard.
- The restore reads the sprite from `m_sourceID`; for the item path
  `CItem::Equip` stores the *wearer's* id there. It never restores
  `m_baseStats.m_animationType`: only `ApplyEffect` writes that, and only
  for the permanent (duration type 1) case.
- The search map is bracketed around the animation change: remove with the
  disguising animation's personal space, change, add with the restored one.
  A dead sprite keeps its animation but still gets the remove (step 6),
  `JumpToPoint` (which re-adds with the animation it kept), `SetIdleSequence`
  and `EquipAll`.
- The sound member is freed by the base destructor, not by this body; the
  test checks the sound resource's key-table reference count drops by one
  after the delete.
- UnequipAll-first has no independently observable consequence on this
  fixture: the disguising 0x7100 monster animation does not override the
  equipment methods, so unequipping it is a no-op, and the pre-restore
  animation object is deleted by the restore anyway. The call is written
  first because that is where the original has it (0x4C3B4B, before the
  RemoveObject at 0x4C3C43); it is not reordered.
- Unsafe in the current layout: none found. Every member read (0x10C, 0x12,
  0x188, 0x18C, 0x50F0, 0x5380, 0x54A8, 0x5BC, 0x5C8, 0x7430) and every
  global (0x8CF6DC, 0x85186C/70/71/73, 0x84C50E, 0x84D6A0/A1) resolves to
  the source's declaration at the same offset; the entry is the documented
  CGameEffectDisguise vtable slot 0 body, and the class has no extra
  zero-initialisation the destructor has to undo.
