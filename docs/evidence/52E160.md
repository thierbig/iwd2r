# 0x52E160 CProjectileSparkleExplosion::Explode

Imported in batch i058. This is one of the batch's two "only-theirs"
requeues (it had no coverage in the previous batch's Frida phase), so
the body is imported, not parked.

## Decompiled

The port is anchored on the exe bytes (see exemption). The function
maps the projectile's sparkle colour (+0x9A) to a child projectile
type, decodes that child and fires it at the stored target:

| sparkle colour | child type |
| --- | --- |
| 1, 9, 10 | 0xC4 |
| 2 | 0xC5 |
| 3, 11 | 0xC8 |
| 4 | 0xC6 |
| 5 | 0xC7 |
| 6 | 0xC9 |
| 7, 8 | 0xCA |
| 12 | 0xCB |
| anything else | return without firing |

The exe compiles the map as a `dec`/`cmp $0xb`/`ja` range check plus a
12-entry jump table at 0x52E1F4 whose arms store childType-1 into %eax;
the shared tail at 0x52E1AD (`inc %eax; push $0; push $0; push %eax;
call 0x51eaf0`) reconstructs the type and calls DecodeProjectile with
(NULL, 0) for the sprite/unknown arguments. On a non-NULL result it
fires the child through vtable slot 0x6C (`CProjectile::Fire`) with
`Fire(m_pArea, m_sourceId, m_targetId, m_targetPos, 30,
m_nSparkleColour)` — the exe pushes, right to left: [esi+0x9a]
(nType), $0x1e (nHeight = 30), the CPoint at [esi+0xc8..0xcf]
(targetPos by value), [esi+0x76] (target), [esi+0x72] (source),
[esi+0xea] (pArea). The child is not deleted afterwards: the ret at
0x52E1F0 follows the Fire call directly.

## Fork comparison (rule 1)

WillScarlettOhara's body (@e8dd16a7) matches the exe statement for
statement: the same eight case groups with the same constants
(including 12 → 0xCB), the same `default: return`, the NULL guard
after DecodeProjectile, and the same Fire argument list with height 30
and the sparkle colour as nType. Differences are naming only, all
resolved toward our tree:

- `m_sparkleColor` → `m_nSparkleColour` (our +0x9A WORD).
- His `CPoint(m_targetX, m_targetY)` builds the point from two LONGs;
  ours is the single `m_targetPos` CPoint at +0xC8 that the exe pushes
  by value.
- His `USHORT type` local → `WORD nChildType` (our WORD typedef); his
  `DecodeProjectile(type, NULL, 0)` matches the exe's argument tuple.
- His `if (child)` → `if (pChild != NULL)`, same skip on NULL.

The exe pushes the raw word at +0x9A as Fire's SHORT nType; the port
passes `m_nSparkleColour` and relies on the ordinary WORD→SHORT
conversion, value-identical for the colours that reach it (0-0xFFF
stored by DecodeSpellHitProjectile-style writers).

## Notes

- In the current tree `DecodeProjectile` has no cases for 196-203 yet
  (unported types hit the documented DEVIATION fallback and return an
  instant `CProjectile84D8B8`), so until those cases are imported an
  in-tree Explode fires an instant projectile instead of the real
  child class. The ported switch and call shape are the exe's; the
  fallback is DecodeProjectile's existing documented behaviour, not
  something this function adds.
- No delete of the child after Fire — the exe leaves ownership with
  Fire (ret at 0x52E1F0 directly after the call), and the port does
  the same.
