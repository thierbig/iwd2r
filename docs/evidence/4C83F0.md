# 0x4C83F0 CGameObject::TransferInventory

Ghidra labels this function "FloatText" — a mislabel: the real
`CGameObject::FloatText` is 0x4C80E0 (ported above it), and this body never
touches a string or the screen. What it does is move every item from this
object (the giver) to a receiving object, which is why the caller
(ExecuteAction case 295, 0x451DB6) reaches it as `target -> actee`: the
action's target gives its whole inventory to the action's actee. The name
TransferInventory comes from that behavior. Member of CGameObject in the
original's GameObject.cpp, `__thiscall`
`SHORT TransferInventory(CGameObject* pReceiver)`, 1575 bytes
(0x4C83F0-0x4C8A17). Ported in commit d2e79d2a; the caller wired in commit
74b8ab1b.

## Body

Entry default is the word at 0x8485C4 = ACTION_DONE; either side being
unusable sets the word at 0x8485CA = ACTION_ERROR and takes 0x4C89FD (the
common return tail). Dispatch on the two m_objectType fields (giver at
+0x4, receiver via the parameter): both TYPE_CONTAINER (0x11) → 0x4C87AE;
both TYPE_SPRITE (0x31) → 0x4C8439; a sprite/container mix falls to the
two mixed walks; anything else (AIBase, Door, ...) is an error side.

Sprite walk (giver side, all four walks share the loop shape): NUM_SLOT
51 iterations (byte 0x85BD87), skipping slot 10 = SLOT_FIST (byte
0x85BD83), NULL items, and items whose `GetFlagsFile() & 4` is clear —
GetFlagsFile reads the ITM file header, so an empty-resref CItem reads
flags 0 and stays. Container walk (giver side): the item count is read
once (`movsx word [this+0x5BA]`), GetItem(0) (0x4802B0) NULL burns that
index (count still decrements), and RemoveItem(0) (0x481EB0) runs only
after the add message is queued; the loop condition is a signed jl.

The four walks, in dispatch order:

- sprite → sprite (0x4C847A-0x4C860F): FeedBack block first
  (0x4C84BF-0x4C84F3) — GetCharacterPortraitNum (0x5AF4E0) on the
  receiver's m_id, 0xFFFF skips the block, FeedBack 0x5C2630(3, 0, TRUE)
  with word 0x8518C2. Then a heap CItem staging copy (0x4E7900), a
  CMessageRemoveItem (vtable 0x848C04) carrying the giver's slot, a
  default-constructed CMessageAddItem (CItem 0x4E7840, vtable 0x848BE8 at
  0x4C85AC) whose m_item is then filled by the FULL CItem::operator=
  (0x464130, at 0x4C85B2) from the staging copy — charges ride along —
  AddMessage 0x4F7500(msg, FALSE), virtual delete (0x4C85DF). Because the
  removal is a message, the giver's m_items array is NOT mutated on this
  path.
- sprite → container (0x4C8614-0x4C87A9): no FeedBack. CMessageRemoveItem
  as above, then CMessageContainerAddItem (vtable 0x848F60 at 0x4C8710)
  with SetResRef (0x4E8350(copy+0xC, 1)) — i.e. the partial fill:
  resref + use counts + wear + flags — m_slotNum 0x7FFF (0x4C8745) and
  m_bCompressContainer 0. Delete at 0x4C8775.
- container → sprite (0x4C87E8-0x4C8907): FeedBack block as in the first
  walk. CMessageAddItem (vtable 0x848BE8 at 0x4C8892) with the partial
  fill straight from the list's pItem (no staging copy — the item is
  about to be removed), AddMessage, then RemoveItem(0) (0x4C88E7). The
  container's list empties synchronously.
- container → container (0x4C890C-0x4C89FD): CMessageContainerAddItem
  (vtable 0x848F60 at 0x4C8979), partial fill, m_slotNum 0x7FFF
  (0x4C89AE), compress 0, delete, then RemoveItem(0).

The partial fill is exactly the in-tree CMessageAddItem ctor
(src/CMessage.cpp:9958) and the CMessageContainerAddItem field stores, so
the port builds the messages with those ctors rather than re-spelling the
field writes.

## Callers

In tree: ExecuteAction case 295 (src/CGameAIBase.cpp, 0x451D7F-0x451DE8)
— the resolver 0x45C290 yields the giver (a NULL result takes 0x451451's
ACTION_ERROR before bShare is set), the actee resolves via
GetActee2 + 0x40CCA0 (NULL → plain release test 0x44E1DE, with bShare
TRUE so the tail releases the giver), then 0x451DB6 calls
`giver->TransferInventory(actee)` with `mov esi,eax` assigning the return
to the action result, followed by the actee's ReleaseShare
(THREAD_ASYNCH byte 0x851873, INFINITE). Wired in commit 74b8ab1b;
recorded in 44DC10-arms-84z.md.

## Test

tests/test_ai.cpp [ai][data] "ai: ExecuteAction 295 TransferInventory
hands the actee the whole inventory" (commit ffb39645) drives the arm
through ExecuteAction for sprite→sprite (full-copy charges, fist slot 10
and empty-resref items stay, slots not mutated, remove messages carry the
giver's ids and the add messages carry giver→receiver), sprite→container
(slotNum 0x7FFF, no compression), container→sprite (synchronous drain,
head-first order, plus the container's own RemoveItem echo messages), and
container→container direct; the error sides (AIBase giver, AIBase
receiver) answer ACTION_ERROR with nothing queued.
