# 0x4F80B0 CMessageAddAction::UnmarshalMessage

The body is read from the complete annotated listing produced with the pinned
local vanilla exe (`md5 200f038bec3ed50a964d68b3f0f1f0e7`) and the pinned
annotator:

    ~/.local/share/iwd2r/parity-venv/bin/python -I tools/parity/annotate.py 0x4F80B0

The listing runs to `0x4F83B7` (775 bytes), as `functions.tsv` records. The
local labelled Ghidra project is not provisioned, so no Ghidra decompile is
pasted here; the branch and field evidence below cites the listing address.
The wire format is the mirror of `MarshalMessage` (0x4F7AE0); see
`docs/evidence/4F7AE0.md` for the field table and vtable 0x847B24.

## Stream position

`cnt` starts at `CNetwork::SPEC_MSG_HEADER_LENGTH` (0x85E670 holds 3). The
first eight payload bytes are the target's remote ids; the payload itself
starts with the same fields `MarshalMessage` wrote. The function never reads
`dwSize` while parsing; it asserts `cnt == dwSize` at the end (source line
4799), so every reader below advances `cnt` by exactly the width it consumed.

## Fields the wire does not carry

The unmarshaller (like the original) never reads `CAIAction::m_internalFlags`
and never reads the `CAIObjectType` location fields (`m_nLocationType`,
`m_ptCenter`, `m_nRadius`, `m_rect`). It constructs the temporary object with
`m_nLocationType = CAIOBJECTTYPE_LOCATION_TYPE_NONE`, so `Set` into the action
leaves the action's location fields untouched and `m_internalFlags` keeps its
constructor value (0 for the decoder's `CMessageAddAction`). The native tests
keep those fields at their constructor defaults and say so.
