## Notes

The deny lifecycle lives in Ghidra's `local_29c` (the exe's stack copy of
`m_nGameSprite`, `[esp+0x34]`): captured at entry from `[ecx+0x4e2]`, denied in
the entry loop, and released by the common exit `ReleaseDeny(local_29c)` at
`LAB_00616fa5` (0x616FC7).

Import changes the sprite id, and the exe refreshes its copy before re-denying:
case `0x14` (our case 20) releases `local_29c`, calls `ImportCharacter`
(0x616B6F), then reloads `local_29c = *(undefined4 *)(in_ECX + 0x4e2)` —
`mov esi,[ebp+0x4e2]; mov [esp+0x34],esi` at **0x616BAB** — before the re-deny
loop (0x616BD8). `ImportCharacter` (0x613B20) replaces the chargen sprite, so
the id moves 0x10001 → 0x10003 (same array slot 1).

Ours kept the function-entry local (`INT nGameSprite = m_nGameSprite;`,
src/CScreenCreateChar.cpp:5375) for the final release at src:5874. After the
import the stale 0x10001 is DELETED, and `ReleaseDeny`'s DELETED path returns
without decrementing slot 1's deny count — the 0x10003 deny from src:5676
leaked, and the Appearance button's Render spun in `GetShare(..., INFINITE)`,
freezing the main thread. The task-52c logging run (runs/20261030-204042)
showed exactly the unpaired pair: `GetDeny id=65539` (0x50FD32, src 5676) /
`ReleaseDeny id=65537 rc=2 DELETED` (0x50FB67, src 5874).

Fix: reload ours to match — `nGameSprite = m_nGameSprite;` after
`ImportCharacter` in case 20 (src/CScreenCreateChar.cpp), so the final release
targets the imported id like the exe's 0x616BAB reload. Verified by
runs/20261030-210239 (a shortened scenarios/pending/chr_druid_cast.txt): `checkpoint named` reached, exit 0.
