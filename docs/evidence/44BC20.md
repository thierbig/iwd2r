Read against the disassembly FUN_0044bc20: a length above 0xFFFFFFFD calls 0x7F9AC2 (_Xlen, std::length_error) - the VC6 Dinkumware max-size guard. The first branch family covers shared storage (m_pData non-NULL and the refcount byte at m_pData[-1] neither 0 nor 0xFF): length 0 decrements the refcount, calls Tidy(FALSE) and returns FALSE; otherwise it detaches by growing (Grow, 0x44BE10). Length 0 on unshared storage returns FALSE either after Tidy(TRUE) when bTrim is set, or leaving an owned buffer logically empty (m_nLen = 0, m_pData[0] = 0) when it is not. Returns TRUE whenever the caller may write. The 0x20 small-buffer threshold, the 0xFFFFFFFD cap and the trim-flag semantics were each matched against the instruction stream; the old export carried an Assign-style name but takes a size and trim byte, as the header comment records.
