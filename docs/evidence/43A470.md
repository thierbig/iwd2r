# 0x43A470 CBaldurMessage::OnSendAreaMapNote

Read-only evidence from the MD5-pinned original via
`python3 -I tools/parity/annotate.py 0x43A470` and the Ghidra decompile
below; Ghidra names the function `FUN_0043a470`.

## Identity and calling convention

Member of CBaldurMessage in the original's Baldur/CMessage.cpp, dispatched
by 0x4EE020's `AREAMAPNOTE` (A = 65) `/` `n` (110) arm (0x4F4xxx).
`__thiscall`, `ret 0xc`: `(INT nMsgFrom, BYTE* pByteMessage, DWORD dwSize)`;
the receiver ignores nMsgFrom.

## Dependency: the 0x47B330 "Add stub"

The survey's G17 note said the pair "call the Add stub at 0x47B330". **That
is stale: 0x47B330 is not a stub in this tree.** `CGameAreaNotes::Add`
(src/CGameAreaNotes.cpp, labelled `// 0x47B330`, with the five-line wrapper
0x47B090 keeping its own label) is ported in full -- the session send on the
client, the TLK override on the host, the list update through 0x47B150, the
map-screen button/grid path and the delete-on-empty-text arm. It calls the
ported `SendAreaMapNoteToServer` (0x43A210) and `AnnounceAreaMapNote`
(0x43A380), so both rows land against real code; no NOTE or half-port is
needed. The stale comment above `SendAreaMapNoteToServer` is corrected in
this commit.

## Body

One guard: `m_bConnectionEstablished`, else FALSE. The body then decodes
the sender's payload after the 3-byte header:

    {BYTE areaLen; char area[]; WORD startX; WORD startY;
     DWORD noteLen; char note[]; DWORD dwFlags; STRREF strRef}

and calls
`CGameAreaNotes::Add(sArea, startX, startY, sNote, dwFlags, -1)` on
`GetArea(sArea)->GetAreaNotes()`.

**Original wire quirk (kept):** the senders write a trailing STRREF, but
both receivers read only the flags and pass **-1** as the text reference --
`Add` re-resolves the note text through the TLK override itself -- so the
wire's STRREF is never read on receipt.
