## Notes

The port is `CBaldurMessage::ObjectControlSuggestion` in `src/CMessage.cpp`,
plus the new wire constant `MSG_SUBTYPE_OBJECT_CONTROL_SUGGEST = 115`
(0x84CF9C). It keeps the session/host guards, the GetShare retry, the two
remote ids read before ReleaseShare, the self `ObjectControlRequest` call, the
remote-owner and unknown-player refusals, the 8-byte
`{DWORD m_remotePlayerID; DWORD m_remoteObjectID}` packet sent with
`SEND_GUARANTEED` as OBJECT 79/115 to the suggested player's location, and the
TRUE answer after the send.

`ObjectControlRequest` (0x430980, 599 bytes) is **not ported**; the self case
calls the existing stub, which answers FALSE (the TODO stays on the stub).

Proof: `tests/test_network.cpp`, `[msg][network]`, no `IWD2_DATA`, 24
assertions: a zeroed `CBaldurChitin`/`CInfGame` with a placement-new
`CGameObjectArray(10, 10)` and one heap `CGameObject` (`m_remotePlayerID = 3`,
`m_remoteObjectID = 4`). The test drives the closed-session and non-host
guards, the allow path (`STATIC_MESSAGE_BUFFER` = `0xFF, 79, 115, 3, 0, 0, 0,
4, 0, 0, 0`), the remote-owner refusal (3), an unknown player (9), a missing
object and the self stub path. It bites: against the old stub body the send
assertions fail (no packet, FALSE).

A live-session/object oracle case and the `ObjectControlRequest` port remain
follow-ups.

**Parity note (0x430720 asm).** The Linux gate's three callees are the inlined
`CreateBuffer`/`DestroyBuffer` (`operator_new` 0x430879 / `operator_delete`
0x4308CC) and the local `sPlayerName`'s destructor (`CString_Destruct`
0x4308DC). The send at 0x4308BE pushes the address of the local CString
(S+0x10, the `GetPlayerName` target); `SendSpecificMessage` (0x7A84F0) takes
it by reference, and the callgraph has no CString copy constructor, so the
original does not copy the player name and the port must not add one. The
waiver records the three.
