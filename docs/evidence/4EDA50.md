# 0x4EDA50 CLUAConsole::~CLUAConsole

The destructor of the debug console's command buffer, `CLUAConsole`, 90
bytes (0x4EDA50-0x4EDAAA). New class declaration in src/CLUAConsole.h and
the destructor in src/CLUAConsole.cpp; ported in commit (see report).

## Naming

Not named by any string; the object identifies it. The Lua console edit's
Enter handler 0x77BF30 (strings "Lua Edit" 0x8B9710, "String0" 0x8B971C)
constructs a stack object at ebp-0xB8 — frame proof: the prologue's three
SEH pushes, `sub esp,0xC0` and four register pushes put the VC6 state byte
at [esp0+0xD8], so "ebp" = esp0, and the EH pad 0x842E91 runs
`lea ecx,[ebp-0xB8]` into this destructor. The dispatcher call at 0x77C3F3
(`lea ecx,[esp+0x28]` with one pending push = esp0+0x24 = ebp-0xB8) hands
that same object to 0x5838A0 — the console command dispatcher whose
established tree name is `CLUAConsole` (docs/followups.md:197: "The Lua
console's Enter (0x77BF30, `CLUAConsole` 0x5838A0) is not ported"). Hence
the class name; the destructor is its only member in the tree.

## Body

SEH-wrapped scalar destructor, `mov esi,ecx`, then the three non-trivial
members destroyed in reverse declaration order, each with the EH state
byte set just before the call:

- 0x4EDA6D `lea ecx,[esi+0x24]` → 0x7FB9C1 at 0x4EDA78 (state 1): the
  token store — the exe's CStringArray-family dtor (vtable 0x85FD00),
  whose per-element loop 0x7FB9FF runs the CString dtor on every token
  before freeing the buffer. The dispatcher's arms fetch text arguments
  through 0x65F8F0 with this+0x24 as the store (SETGLOBAL arm 0x583D3D).
- 0x4EDA7D `lea ecx,[esi+0x10]` → 0x7FB93A at 0x4EDA85 (state 0): the
  parsed value table — the exe's CArray<DWORD>-family dtor (vtable
  0x85FCE0), buffer free only. The arms read their DWORD arguments through
  the data pointer at this+0x14 (SETGLOBAL's dwValue).
- 0x4EDA8A `lea ecx,[esi+0x4]` → 0x7FCC1A at 0x4EDA95 (state -1): the
  plain CString at +0x4.

The DWORD members at +0/+8/+0xC/+0x38/+0x3C (all zeroed by the Enter
handler at 0x77C384-0x77C38C and 0x77C37C-0x77C383) are trivial. The tree's
class declares the same members (CDWordArray, CStringArray, CString), so
the empty destructor body carries the identical destruction implicitly —
the same port shape as `CMessageMoveGlobal::~CMessageMoveGlobal` (0x4670C0),
whose NOTE this port follows. No vftable is stored anywhere in the listing:
CLUAConsole has no base class and no virtuals (unlike CMessage), so the
tree's class is plain.

## ecx / calling convention

thiscall, caller-cleaned: plain `ret` at 0x4EDAA9, not `ret 4` — there is
no deleting-destructor wrapper (unlike CMessageMoveGlobal's 0x4670A0)
because the object never passes through delete; it is a stack local.

## Callers

None in tree. The only exe reference is not a call at all: the unwind pad
0x842E91 of the Enter handler 0x77BF30 (`push 0x842EC5` catch thunk at
0x77BF32; the handler's FuncInfo is 0x89DDA8) loads
`lea ecx,[ebp-0xB8]` and jumps here on the exception path. The handler's
normal epilogue destructs the same three members inline (0x77C408, 0x77C419,
0x77C42A) — two spellings of one destruction, so no call site and no TODO
references this address (grep over src/ and tests/ finds none). The Enter
handler and the dispatcher are deliberately unported (docs/followups.md).

## Test

None: the body is pure member destruction of a class whose only
construction sites sit inside the unported Enter handler, and the console
layer has no test harness (no dispatcher). The pinned facts above — the
member layout and roles, the destruction order with each call address, the
state-byte steps, and the caller-cleaned `ret` — are verified against the
listing.
