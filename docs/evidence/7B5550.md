## Notes

- **The timer class is unrecovered and declared here as `CWarpTimer` in `src/CWarp.h`**, per the
  maintainer's ruling on issue #40: name, virtual's name and every field's meaning are ours
  (`#guess`), and only the layout is the binary's. Nothing in the exe constructs one and IEex names
  no such class (report-T84 §2–§3 has the exhaustive scan: no `CObList::NewNode` caller reaches
  `lTimers`), so `lTimers` is empty in every run and the empty-list return is the only behaviour the
  original can be observed to show.
- The layout, exactly as the disassembly reads it: `+0x04` set fires on every update; `+0x08`,
  `+0x0C`, `+0x10` (the owning `CWarp`) and `+0x14` (the timer's `POSITION` in that owner's
  `lTimers`) all non-zero let it remove itself after a fire; `+0x18` is the period and `+0x1C` the
  accumulator of `10000 / TIMER_UPDATES_PER_SECOND`. The walk takes the next node before it touches
  the current one, so a self-removal is safe; the port takes the next POSITION first for the same
  reason.
- The class's virtual is at vtable+0xC in the original because release MFC `CObject` has three
  virtuals (`GetRuntimeClass`, the deleting destructor, `Serialize`). Our `compat/mfc_list.h`
  `CObject` declares only the destructor, so in this tree it sits at +0x4; every call is by name, so
  behaviour is the same, and the data layout (+0x04 onward) is unaffected.
- `CWarpTimer::Update` is declared pure virtual: the binary implements and constructs no timer, so a
  body would be invented; the test's subclass supplies it.
- Proof: `tests/test_warp.cpp` (`[warp]`, 7 cases, 32 assertions) drives a synthetic `lTimers`
  through both branches, the accumulator/remainder, the four-field removal guard (one field cleared
  at a time), a removal mid-list, a NULL entry, and the owner's list actually losing the node. With
  the stub the same tests fail 21 of 32 assertions.
