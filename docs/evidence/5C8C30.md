## Callers and callees

- The DropItem helper calls it at `0x7227BA`. The two arguments are the
  carried bag's `cResRef` (`CItem + 0x0C`) and the requested item's resref;
  `ret 8` independently confirms the two 32-bit reference arguments.
- Store calls are `CStore` construction/destruction and `SetResRef`,
  `GetNumItems`, `GetItemId`, `GetItem`, `RemoveItemExt`, `Marshal`, and
  `InvalidateStore`. Session calls are `DemandServerStore`,
  `GetServerStore`, `ReleaseServerStore`, `DemandResourceFromServer`,
  `CNetwork::CloseSession`, and `CMessageHandler::AddMessage`.
- The original constructs the demand/remove/release messages inline; the
  port uses the already recovered `CMessageStoreDemand`,
  `CMessageStoreRemoveItem`, and `CMessageStoreRelease` constructors. The
  disassembly's vtables `0x848F7C`, `0x848F44`, and `0x848F28` respectively
  identify those message types.

## Notes

Ported as `CItem* CInfGame::RemoveItemFromBag(const CResRef& cResBag,
const CResRef& cResItem)`, the required callee of `DropItemFromBag`. The code
range is `0x5C8C30-0x5C92F8` (the last instruction is `ret 8` at
`0x5C92F5`; `0x5C92F8-0x5C92FF` is padding, and a different function starts
at `0x5C9300`). A default `CItem` temporary is constructed at entry.

### Without an open session

A `CStore(cResBag)` is scanned in increasing index order. `GetItemId` and
`GetItem(nIndex, tempItem)` both run before the resref comparison. On the
first match, the function allocates a default `CItem`, fills it with
`GetItem(nIndex, *pItem)`, removes one item with
`RemoveItemExt(cResItem, pItem->m_flags, -1, 1, NULL)`, marshals the bag to
`m_sTempDir`, and returns the new item. No match returns NULL; importantly,
there is no Marshal on that path.

### With an open session

The host demands the server store with save-to-disk TRUE and loads it. A
client loads its local copy and, when that copy is absent or lacks the
`STORV9.0` signature, demands resource type 1014 with all three trailing
flags TRUE. Failure closes the session with TRUE and returns NULL; success
reloads the store and records that a release message is owed.

The store scan again fills `tempItem` before each comparison. On a match a
new `CItem` is filled from the matching line. A client that has not already
demanded the store first queues `CMessageStoreDemand(cResBag, -1, -1)` and
sets the owed-release flag. Both sides queue
`CMessageStoreRemoveItem(cResBag, cResItem, pItem->m_flags, -1, 1, -1, -1)`.
The host gets the server store, checks `pStore != NULL` (original
`InfGame.cpp` line `0x5831` = 22577), and removes one item there. The client
instead invalidates its cached store. The host releases the server store; a
client with an owed demand release queues
`CMessageStoreRelease(cResBag, -1, -1)`. The new item is then returned.
`GetServerStore` and both release paths deliberately reload the object game
through `g_pBaldurChitin` (`0x5C8F9F`, `0x5C900A`, and `0x5C90D0`), rather
than using `this`; the initial `DemandServerStore` and offline Marshal remain
members of `this`. A singleton test cannot distinguish that qualification,
so it is checked directly against those instructions.

At the no-match tail the host still releases the demanded server store, and
a client queues release only when it demanded one. No remove message or
store invalidation occurs on that path. Neither path checks the allocation
against NULL before passing `*pItem` to `GetItem`; no such guard has been
invented in the port.

The data-backed DropItem action test executes the disconnected path and
checks both the returned item's arrival on the ground pile and removal from
the real bag store. `sp-host: RemoveItemFromBag removes one item from the
server store` additionally executes the null-provider host match/removal and
no-match cleanup, checks that the returned item has the requested resref and
one use, verifies the persisted store is empty, and checks that the server
store is no longer held. The non-host client, server-demand failure, and
message transport against a remote peer have not been run. This evidence
therefore remains `kind: read-only`, with the complete disassembly above as
the basis for those unexercised branches.
