## Notes

Ported from the Ghidra listing and the disassembly (0x757720-0x7579B2, 659 B, `ret`); executed by
`CGameSprite::ExecuteAction`'s case 224 (0x72A9A7-0x72A9B7 calls it and jumps on to the next action
with its SHORT). The engine-internal action 224 has no ACTION.IDS entry (the IDS skips 205-228);
ours names it after what it does: every equipped item whose ITM file flags carry 0x4 (the bit
`DropItem` and `DropInventory` test), the fist slot (10) excluded, is unequipped and given to a
party member.

The walk, arm by arm: the 51 slots (`CGameSpriteEquipment::NUM_SLOT`, the byte at 0x85BD87) from 0;
a slot is skipped when its item is NULL, when it is `SLOT_FIST` (10, the byte at 0x85BD83), or when
`GetFlagsFile() & 4` is 0. A taken item is `Unequip`ped and its slot cleared, then the party is
walked from its last member down (`CInfGame::m_nCharacters` at 0x3846, `m_characterPortraits[6]` at
0x382E - a party scan, not the object array), each id `GetShare`d with `THREAD_ASYNCH` and the
SHARED/DENIED answers retried; on `SUCCESS`, while this sprite's amulet slot
(`m_equipment.m_items[SLOT_AMULET]`) is empty, the item goes to `CInfGame::AddDisposableItem` and a
`new CMessageAddItem(*pItem, m_id, nId)` to the message handler (the same tail as `GiveItem`,
0x7618E0), after which no further member is tried; the share is always released. The function
returns `ACTION_DONE`.

Two readings the bytes force and the code keeps: the amulet test at 0x757853 reads
`m_equipment.m_items[0]` with no index (`mov eax, [esi+0x4ad8]`), so an equipped amulet stops the
handout; and the "one per item" flag is the stack local the scan sets on the way out (Ghidra's
`bVar4`).

The decompile above was drafted with Ghidra 12.1.4 from the labelled project on the box
(`tools/oracle.py evidence 0x757720 --force`); the re-draft matches it, bar the trailing spaces
Ghidra emits on blank lines. Ghidra still prints the function as `CGameSprite_B3AUTO_00757720`
because the box's checkout predates this port; the heading keeps the port's name.
