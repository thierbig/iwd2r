# 0x55B1B0 IcewindCProjectileWallTargetMap::GatherTargets

The wall target map's override of vtable slot 1 (0x84EEB0). The exe's vtable
table at 0x84EEB0 was read directly: slot 0 is the base Service 0x55A610
and slot 1 (0x84EEB4) is 0x55B1B0; the base table 0x84EEA8 slot 1 holds
0x55AD90. The override is reached virtually from Service 0x55A610 (the
call site `call [eax+4]` there), so it has no direct caller entry in
callgraph.tsv but is reachable in the live game.

Read against the complete annotated disassembly below (annotator run on
the pinned local vanilla IWD2.exe, MD5 200f038bec3ed50a964d68b3f0f1f0e7,
the same exe tools/parity/run.py uses; the Linux parity host was down, so
this is a local read-only run of the same tools/parity/annotate.py).

## Port

`src/IcewindCProjectileTargetMap.cpp`, `IcewindCProjectileWallTargetMap::GatherTargets`,
spelled with the same order as the binary:

1. Four polygon points, each `owner->GetPos() + m_corners[i]`. The binary
   calls the owner's virtual slot 0x1C (`GetPos`) once per corner
   (0x55B1CD-0x55B23E), reads the returned `CPoint` (x at +0, y at +4) and
   adds the corner dwords at this+0x3C/0x40, +0x44/0x48, +0x4C/0x50 and
   +0x54/0x58. The port keeps the per-corner calls.
2. The bounding `CRect` is the min/max over those four points: left at
   0x55B32C from [esp+0x10], top from [esp+0x14], right from eax and
   bottom from ecx (0x55B252-0x55B346). The binary computes them with
   pairwise `cmp`/`cmov`-style branches; `min(min(p0,p1),min(p2,p3))` and
   `max(max(p0,p1),max(p2,p3))` are the same values.
3. `CTypedPtrList<CPtrList, LONG*> inPoly(10)` (CPtrList_Construct
   0x7FB239 with block size 10, then the CTypedPtrList vtable 0x847B78),
   then a single `GetAllInPoly` call at 0x55B38A with exactly:
   `(bounds, poly, 4, CAIObjectType::ANYONE (0x8C7748), area + 0x40A, inPoly, FALSE)`.
   The seventh argument is `ebx` = 0 at 0x55B35F, i.e. front list only.
   The terrain pointer is the **area's** `m_visibleTerrainTable` at
   +0x40A (0x55B367 `add eax,0x40a`, where eax = [owner+0x12] = the
   owner's `CGameObject::GetArea()`), not the projectile's own
   `m_terrainTable` at +0xD0 that the base gather passes.
4. The map insert loop is the base gather's: the local map is constructed
   by 0x55BA60 at [esp+0x1C], every list id at node+8 is inserted with a
   default value, and the local map is copied into the caller's sret
   (0x55B970) before its teardown. The port returns the local
   `std::map<LONG, CPoint>` with `(id, CPoint(0, 0))`, as the base gather
   does; the mapped value is never read by Service.

`m_nRange`, `field_34` and `field_36` are not read by this function. The
wall length at +0x36 belongs to the parked corner setup 0x55B010.

## Notes

- **Corner setup evidence question.** The four corner offsets are written
  only by 0x55B010 (`CGameProjectileTargetMap`-adjacent, 414 bytes: it
  walks `GetDirection`, rotates the wall through IcewindMisc::sub_584610 /
  sub_5847B0 and stores the four points, then sets the byte at +0x3A to
  1). The survey found no caller and no reference to 0x55B010 anywhere in
  the exe (no direct call, no data reference, no vtable slot): callgraph.tsv
  has no row for it and no caller, and the string/pointer scan finds no
  address. It is therefore **not ported** and no corner setup is invented:
  the walls' ctors leave +0x3C..+0x5C uninitialised exactly as the exe's
  ctors do, and this gather reads those uninitialised offsets with the
  exact field order above. Whether the retail game ever arms them (an
  indirect call through a structure not in the key file, a removed
  feature, or an original bug) is an open evidence question for the
  coordinator. The byte at +0x3A that 0x55B010 would set is not read by
  this gather.
- The base gather 0x55AD90 and this function share the map type and the
  insert loop (same helper addresses), so the port uses the same
  `(id, CPoint(0,0))` map.
- Tests: `tests/test_wall_projectile.cpp`. The data-free case constructs
  the owner and a zeroed `CGameArea` with an empty front list (the gather's
  geometry and call path, empty result), and the `[data]` case uses a new
  game's AR1000 and the party member's position to check the polygon
  includes it for an axis-aligned and a diamond corner set and excludes it
  for a quad translated away. The min/max rect values are not separately
  observable through GetAllInPoly; the live case's diamond set is the case
  where the rect is larger than the quad and the polygon test is what
  keeps the member in.
- Untested: the exact corner values that 0x55B010 would produce (no
  callable setup in the original data), a live wall casting with corners
  from a real spell (none can be produced while 0x55B010 is unreferenced),
  and the CGameArea back list (this function passes FALSE).
- Not in scope: `CGameAIBase` 0x460000-0x467FFF (untouched), MAP/recovery
  generation (none), and no private STL routine was ported.
