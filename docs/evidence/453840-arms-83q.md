# 0x453840 CGameAIBase::EvaluateStatusTrigger, Task 83q arms

The dispatcher itself is 453840.md; this file records the six TotalItemCnt
arms Task 83q ported, in commits dba1e907 (0x40B5, 0x40B6), 26e8f338
(0x40B7, 0x40C1) and 2be9149f (0x40C2, 0x40C3). Register roles as in the
other arm batches: ebx = this, esi = bResult, edi = pObject2, the decoded
CAITrigger copy at [esp+0x38].

All six share one shape: triggerCopy.Decode(this); pObject2 =
triggerCopy.GetCause().sub_40CB20(this, CGameObject::TYPE_AIBASE, FALSE)
with the NULL case jumping to the early return-FALSE tail; then the
GetObjectType virtual (call [edx+4]) against the byte at 0x84C507
(TYPE_SPRITE) for the equipment walk, else against 0x84C502
(TYPE_CONTAINER) for CountItemExcept; then the compare of the count
against triggerCopy.GetSpecifics() (sete/setg/setl per arm) and jmp
0x45AD4C, the shared release tail that releases pObject2. No arm touches
pObject or bNoRelease.

## Notes

- The trio's plain-item test (0x458BC4-0x458C68) counts one iff the name
  is not "00FIST", its first seven letters are not "00MFIST", and
  GetFlagsFile() & 0x44 != 0x40 (`and eax,0x44; cmp al,0x40; je skip;
  inc ebp`). An earlier working note read 0x45B290 as strcmp==0 and
  called this branch dead; the neg/sbb/neg tail says otherwise, and only
  the differs reading makes TotalItemCnt answer "everything carried but
  the inherent fist". The unit test does not drive the fist conjuncts:
  the data directory has no FIST-named ITM to build the item from, and
  no seeded item's file flags land on 0x40-without-0x4; the conjuncts
  are listing-verified only.
- The exclude family skips the excluded resref before the stack test,
  passes the name (not "") to GetNumberOfItemsInBag, and counts a plain
  item one unconditionally -- no fist test, no name built.
- The container argument asymmetry is the one deliberate-looking
  irregularity: only 0x40C2 (0x45972a-0x459745) marshals GetString1()
  into CountItemExcept; 0x40B5/0x40B6/0x40B7/0x40C1/0x40C3 all push the
  "" literal. The unit test pins it from both sides (0x40C1 unchanged
  count vs 0x40C2 dropped count, same m_string1).
- The bag branch (item type 0x3A) is listing-verified only: seeding a
  real bag would need an ITM of that type plus game-side bag contents
  through GetNumberOfItemsInBag, which the walk would then have to
  resolve for a sprite the test fabricates; the branch is the same call
  the exclude family's container half exercises indirectly.
- Per the task's instruction the six arms repeat the walk in full rather
  than share a helper the exe does not have; the case comments say so.
- Tests (5681c517): 30 assertions, run alone under IWD2_DATA. The sprite
  half NULLs all 51 equipment slots of the CHARBASE sprite first so the
  walk's total is the seeded pair's alone (the suite leaks its fabricated
  objects by design; no destructor walks the nulled array).
