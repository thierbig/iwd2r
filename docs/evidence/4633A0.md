# 0x4633A0 CGameAIBase::CreateItem

Member of CGameAIBase in the original's CGameAIBaseActions.cpp,
`__thiscall` `SHORT CreateItem()`, 916 bytes (0x4633A0-0x463733).
Ghidra's CGameSprite_B3AUTO_004633a0 name is wrong: the function reads
`this` as a CGameAIBase (m_curAction at 0x476, m_id at 0x5C,
m_objectType at 0x4) and its caller loads the CGameAIBase pointer into
ecx.

Ported in two ranges, one commit each: faaf17ea (0x4633A0-0x463595: the
key-table probe for the ITM, the CItem construction with the usage
counts, and the party member's slot scan and full-pack pile drop) and
the range 2 commit (0x463596-0x463733: the non-party type dispatch —
the creature scan, the container hand-off, and the generic ground-pile
tail). The split is at 0x463596, the `cmp al, 0x31` m_objectType test
that opens the non-party half. The caller arm is the case 82 commit
(0x44EEAB-0x44EEB8 of CGameAIBase::ExecuteAction:
`mov ecx, ebx; call 0x4633A0; mov esi, eax; jmp 0x4526F7`, i.e.
`returnValue = CreateItem(); goto done`).

## Callers

Exactly one, the case 82 arm of CGameAIBase::ExecuteAction. The exe's
arm routes the result through the common done label (0x4526F7), not
the release tail, so CreateItem runs with no target share held —
unlike GiveItemCreate (case 160 family) it never dereferences a
pTarget, it acts on the executing object itself.

## Callees

No new callees: every call is in-tree — CAIAction::GetString1, the
CString/CResRef construction traffic, CDimm key-table FindKey (1005,
the ITM type, as GiveItemCreate), operator new and CItem::CItem,
CBaldurChitin::GetObjectGame, CInfGame::GetCharacterPortraitNum,
CInfGame::GetGroundPile, CGameObjectArray::GetDeny/ReleaseDeny, and
CGameContainer::PlaceItemInBlankSlot. All were ported before this
task. The exe has no FeedBack and no CMessageAddItem anywhere in this
function, unlike PlaceItem and GiveItemCreate.

## Notes

- The party check comes first regardless of type: a portrait match
  (GetCharacterPortraitNum(m_id) != -1) scans m_items[18..41] — the 24
  personal-inventory slots — forward for the first blank and stores
  the CItem there, ACTION_DONE.
- The full-pack asymmetry: a party member or non-party creature whose
  slots are all taken still hands the item to the ground pile beside it
  (GetDeny'd PlaceItemInBlankSlot with count 1 and 0x7FFF, then
  ReleaseDeny), but the action then returns ACTION_ERROR — dropping an
  item because there was no room is a failure, exactly as
  CGameAIBase::PlaceItem's full-pack drop returns FALSE. The generic
  object's pile path is the opposite: pile placed means ACTION_DONE,
  and only a missing pile or a failed deny returns ACTION_ERROR.
- A creature outside the party (m_objectType 49, TYPE_SPRITE) scans
  m_items[15..42] forward — the 15 equipment slots plus both packs,
  28 entries — while PlaceItem scans the same span backward; both
  orderings land in the first blank the iteration meets, the exe
  simply prefers the lowest index here.
- A container (m_objectType 17, TYPE_CONTAINER) takes the item straight
  through its own PlaceItemInBlankSlot(pItem, TRUE, 0x7FFF) and the
  action is DONE. Any other object type (a door, a trigger) drops to
  the ground pile path above.
- The CItem is built with wear 0 and flags 0, the three usage counts
  truncated to WORD from m_specificID/m_specificID2/m_specificID3, the
  same construction GiveItemCreate uses; PlaceItem's `m_flags |= 2`
  does not happen here.
