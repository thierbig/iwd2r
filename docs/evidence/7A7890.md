# 0x7A7890 CNetwork::FetchFrame

Imported in batch i058. First imported in batch i054 (commit
977231a0), parked after its Frida phase as "not exercised"
(commit 3e6e881d) and re-imported here as a requeue.

## Decompiled

The port is anchored on the exe bytes (see exemption). What the
exe does, in order:

1. Allocates a `MINIMAL_PACKET_SIZE` (0x80 = 128) byte buffer;
   if the allocation fails it returns NULL without touching either
   reference parameter.
2. Enters the cNetwork+0xF6A critical section (`field_F6A` here)
   and calls IDirectPlay4::Receive through `m_lpDirectPlay`
   (the first CNetwork member, cNetwork+0x0) as a COM stdcall
   `Receive(&from, &to, 0, pData, &dwDataSize)`, starting with
   `dwDataSize` = 0x80.
3. On `DPERR_BUFFERTOOSMALL` (0x8877001E) it deletes the buffer,
   reallocates to the size Receive reported and retries; a failed
   realloc becomes `DPERR_NOMEMORY` (0x8007000E).
4. Leaves the critical section. On any non-`DP_OK` result it
   zeroes the caller's `dwSize`, deletes the buffer and returns
   NULL; on success it writes `dwSize` and `dpIDFrom` (the
   sender) and returns the buffer.

## Port

```cpp
// 0x7A7890
BYTE* CNetwork::FetchFrame(PLAYER_ID& dpIDFrom, DWORD& dwSize)
{
    BYTE* pData = new BYTE[MINIMAL_PACKET_SIZE];
    if (pData == NULL) {
        return NULL;
    }

    // NOTE: iwd2r: The original calls the CNetwork vtable slot `+0x64` (the
    // DirectPlay `Receive` method on m_lpDirectPlay, COM stdcall) in a loop
    // inside this critical section — `Receive(&dpIDFrom_local, &to_local, 0,
    // pData, &dwDataSize)` — reallocating pData on DPERR_BUFFERTOOSMALL
    // (0x8877001E, DPERR_NOMEMORY 0x8007000E on a failed realloc) and
    // returning the frame on DP_OK. DirectPlay is gone, so no frame can be
    // received and the function always takes the exe's failure path: the
    // caller's dwSize is zeroed, the buffer is deleted and NULL is returned.
    EnterCriticalSection(&(g_pChitin->cNetwork.field_F6A));
    LeaveCriticalSection(&(g_pChitin->cNetwork.field_F6A));

    dwSize = 0;
    delete pData;

    return NULL;
}
```

Added in `src/CNetwork.cpp` between `CNetwork::SlidingWindowTimeouts`
and `CNetwork::HandleSystemMessage` — address order (0x7A77D0 <
0x7A7890 < 0x7A7980); declared in `src/CNetwork.h` after
`SlidingWindowTimeouts`.

DirectPlay is not part of this tree (no `dplay.h`, no `DPID` — the
tree's `typedef DWORD PLAYER_ID;` at `src/CNetwork.h` is the
surrogate), so the Receive loop is removed. The port keeps the
allocation, the early NULL return and the critical-section pair —
the FrameSend convention (commit 8ab9c1df) — and always takes the
exe's failure path, which is the only reachable outcome with no
transport: `dwSize = 0`, buffer deleted, NULL returned, exactly the
exe's 0x7a7952-0x7a7971 sequence. The success path's two writes
(`dwSize = dwDataSize`, `dpIDFrom = from`) are unreachable with the
call gone and are documented in the NOTE instead.

## Fork comparison (rule 1)

WillScarlettOhara's body (@e8dd16a7) is the port's basis and matches
the exe statement for statement — allocation, early NULL return,
EnterCS, the Receive/BUFFERTOOSMALL retry loop with the NOMEMORY
substitution, LeaveCS, the `hr != DP_OK` split and both return
paths. Differences, all resolved toward the exe:

- His `DPID from; DPID to;` locals are the exe's L1/L2 stack
  slots (from = L1 at E+4, to = L2 at E+8 — confirmed by the
  push order feeding `call [edx+0x64]`: &L0, esi, 0, &L2, &L1,
  ebx). The port has no `dplay.h`, so the two locals and the
  loop that fills them are documented in the NOTE.
- His `g_pChitin->cNetwork.m_critSect` is cNetwork+0xF6A — the
  exe builds `add eax,0x18bc` (g_pChitin+0x18BC = cNetwork+0xF6A);
  the port uses the tree's name `field_F6A`.
- His failure-path ordering (`dwSize = 0; delete pData; return
  NULL;`) is the exe's 0x7a7952-0x7a7969 order exactly.
- His `PLAYER_ID&`/`DWORD&` reference parameters mirror the
  exe's `ret 0x8` pointer args; the port relies on the compiler's
  reference passing instead of the manual stack pop.

## Notes

The early NULL return (0x7a78a5-0x7a78ab) deliberately writes
neither reference — a caller that ignores the NULL return and reads
`dwSize` keeps its previous value. The failure path always writes
`dwSize = 0`, so a NULL return with a zeroed `dwSize` is the
"transport said no" signature; the port's unconditional failure
path preserves that contract.

Stack arithmetic for the two exit paths: after `pop edi; pop ebx`
(0x7a7931-0x7a7932) esp = E-4, so `[esp+0x18]` = E+0x14 = the
second reference argument (&dwSize), `[esp+0x14]` = E+0x10 = the
first (&dpIDFrom), `[esp+0x4]` = E = L0 (dwDataSize), `[esp+0x8]`
= E+4 = L1 (from). Both paths read their outputs from those same
slots; the fork's reference writes are their direct equivalents.

`ret 0x8` at both exits pops the two pointer arguments callee-side
— the __thiscall-with-stack-refs convention; the port's C++
references make that implicit.
