## Class identity

`CMessage51` by its subtype (the tree's convention for the message classes
whose original C++ name is unrecovered, like CMessage95/CMessage120; BG2
calls the class CMessageSetTarget). Its layout, from the ctor 0x4F6170, the
marshal/unmarshal pair and Run:

The vtable's slots: 0x4B2340 (the shared empty scalar deleting destructor,
not claimed by the tree), 0x453510 (GetCommType, the fold of every getter
returning BROADCAST), 0x40A0E0 (GetMsgType, MSG_TYPE_CMESSAGE), 0x4F61A0
(GetMsgSubType, a 13-byte folded `mov al, byte [0x84CF0A]` returning subtype
51 -> CBaldurMessage::MSG_SUBTYPE_CMESSAGE_51), 0x509100, 0x509730 and
0x509B80.

Construction is **receiving only**: the dispatcher 0x4EE020 is the class's
only construction site (twice: once on its stack at 0x4F1867, once on the

constructs a CMessage51, so the marshal arm below is dead in the game.

## Body

`__thiscall void MarshalMessage(BYTE** pData, DWORD* dwSize)`, 1578 bytes,
`ret 8`.

1. GetShare the target (retry SHARED/DENIED), read its m_remotePlayerID
   (+0x62) and m_remoteObjectID (+0x66), and -- for the search arm only --
   its area's resref (`m_pArea->m_resRef`, +0x12 -> +0x1F0) as a CString.
   A failed share leaves `*dwSize = 0` and writes nothing (0x509673).
2. Size: the point arm is 0x12. The search arm computes
   `len + 0x54 + 8 * (party + targets + points)` at 0x509228 and asserts it
   fits STATICBUFFERSIZE.
3. Write the header, then the arm (the wire format below). Every object id
   becomes its remote pair; the target points are written raw; the five
   trailing LONGs end the payload.
4. The closing `UTIL_ASSERT(cnt == *dwSize)` is at 0x5096E1.

Two defects of this dead arm are kept verbatim and marked in the port:

- The size formula (base 0x54) is one byte short of the bytes the body
  writes (base 0x55: the area-name length byte and the name start at 0x13
  and 0x14), so the exe's own closing assert would fire. The port reports
  the count it writes; the bytes are the exe's.
- The source pair shares `m_pSearchRequest->m_sourceId` (0x5093A8) but
  releases `this->m_sourceId` (0x509405), so the request's share leaks and
  the message's own id is released unshared.

## Wire format (from the pair)

Payload (the 3-byte SPEC_MSG_HEADER is not included):

- +0x00 the target's remote pair: PLAYER_ID m_remotePlayerID, LONG
  m_remoteObjectID (0, 0xFFFFFFFF when the id does not resolve);
- +0x08 m_frontList;
- +0x09 the arm flag: 0 = point, 1 = search request;
- point arm (+0x0A): CPoint m_ptTarget.x, .y; total 0x12.
- search arm (+0x0A): request m_sourceSide, m_nPartyIds, m_nTargetIds,
  m_nTargetPoints (4 bytes), BOOL m_removeSelf (4), m_frontList (1), the
  area name length (1) and its bytes (+0x14), the 16-byte m_terrainTable,
  BOOL m_pathSmooth, BOOL m_collisionSearch (both 4), BYTE
  m_collisionDelay, BOOL m_exclusiveTargetPoints (4, unaligned at +0x2D);
  then the request's source id as a remote pair, m_sourcePt (8), the party
  id pairs (8 each), the target id pairs (8 each), the target POINTs (8
  each, untranslated), and the five trailing LONGs m_minNodes, m_maxNodes,
  m_minNodesBack, m_maxNodesBack, m_bBump (BOOL). Each id pair is the
  object's (remote player, remote object) ids or (0, 0xFFFFFFFF) when the
  object array misses.

The unmarshal resolves every pair through CGameRemoteObjectArray::Find and
rebuilds the CSearchRequest; an unresolvable *target* pair rejects the whole
message (FALSE), while an unresolvable source/list pair stores
INVALID_INDEX (source) or drops the count on a miss (lists). The area name
is resolved back with CInfGame::GetArea and the request's m_searchBitmap is
that area's CSearchBitmap (or the bare member offset when GetArea misses,
as the original's NULL+0x76C does).
