# 0x7B362D CVidBitmap::BltBmp8To16

The function has no body of its own in the binary: `CVidBitmap::RenderDirect` (0x7B3190, its own
evidence in `7B3190.md`) inlines the 8-bpp to 16-bpp blit in its 16-bpp branch. **0x7B362D is that
arm's first instruction** and the range 0x7B362D-0x7B3735 is the whole arm, so the label in
`src/CVidBitmap.cpp` is this address rather than a function entry: the inlining is the compiler's
choice, the port keeps the function. It is reached from RenderDirect's 8-bit dispatch at 0x7B35A7
(`m_nBitCount == 8` and `cVideo.m_nBpp == 16`); there is no call site of its own.

## Notes

- **The source carries no `// 0xADDR` marker for this function.** 0x7B362D is not a function
  entry (it is `RenderDirect+0x49D`), so a marker there fails the parity markers check
  ("nothing calls 0x7B362D; inside 0x7B3190 CVidBitmap::RenderDirect+0x49D"). The tree's
  convention for an inlined body is `// NOTE: Inlined.` with the address in the prose
  (`C2DArray.cpp`, `CAIScript.cpp`, ...), and that is what the source does now: the arm at
  RenderDirect+0x49D (0x7B362D) through +0x5A5 (0x7B3735) is named in the NOTE, and this file
  stays keyed by the arm's address. `tools/check_evidence.py` only tracks labelled functions, so
  it no longer requires this file for the port; it is kept as the arm's evidence and cites the
  oracle run below.
- **The port** (`src/CVidBitmap.cpp`, `BOOL CVidBitmap::BltBmp8To16`): the
  palette is realized into `rgbTempPal` at 16 bpp exactly as the 32-bit sibling does
  (`SetPalette(pRes->GetColorTable(), pRes->GetColorCount(), TYPE_RESOURCE)` then
  `Realize(rgbTempPal, 16, dwFlags | 0x800000, &m_paletteAffects, 255)`), and each pixel is the
  low WORD of the realized entry, which is what `mov dx, word ptr [ebx + 4*eax]` reads. The three
  paths are the compiled ones:
  - **width below 2**: one pixel per row (0x7B371D), a do-while, so a zero-width blit still writes
    one pixel and consumes one source byte - the same quirk as `BltBmp24To16`'s single-pixel path;
  - **odd width**: the leading pixel (0x7B36E8) then `width >> 1` pairs, each pair one dword store
    with the second pixel in the high word (0x7B3708);
  - **even width**: `width / 2` pairs, no leading pixel.
  Rows go bottom-up: after a row the surface pointer steps back by `lPitch + 2 * width` bytes from
  the post-row position (0x7B3710/0x7B36D5), the arithmetic equivalent of
  `pSurface += -bmpSize.cx - lPitch / 2` in WORDs.
- **The even width's pair count is a byte shift in the binary** (`shr byte ptr [ebp+0x14]` at
  0x7B36B4; Ghidra models it as `CONCAT31((int3)(uVar2 >> 8), (byte)uVar2 >> 1)`) while the odd
  path shifts the whole dword (0x7B36E2). Below 256 the two are identical - and every bitmap the
  game blits is below that - but at and above it the byte shift keeps the untouched high bytes and
  counts far too many pairs, reading past the source row and writing past the surface row. The port
  halves the whole width instead (identical below 256) rather than reproduce the overrun; the NOTE
  in the source says so. This is the only difference from the bytes.
- **Proof**: `tests/test_vid.cpp` (`[vid]`, 25 assertions) pins the three paths on a 4x2 canvas in
  both 5-6-5 and 5-5-5: the even pairs and the bottom-up row order, the odd leading pixel plus its
  pairs and the untouched pixel right of the blit, the sub-2 one-pixel-per-row path, and pure red
  packing to 0xF800 in 5-6-5 and 0x7C00 in 5-5-5 (other entries are compared against
  `CVidImage::rgbTempPal` so the palette's own realization rounding stays out of the assertion).
  With the stub the test fails 23 of its 25 assertions.

## Oracle

`vid/blt_bmp8to16` (`oracle/cases/vid.cpp`): the arm has no address to call, so the case calls the
original `RenderDirect` itself with an 8-bit `CResBitmap` (the members `Parse` would set are filled:
`bParsed`, `nColors = 256`, the RGBQUAD table - pure red, green, blue and 253 random entries - and
the `BITMAPINFOHEADER`), `bDemanded = TRUE` so `Demand`/`Release` never run, and a synthetic video
mode whose one surface is a fabricated `IDirectDrawSurface`: its `Lock` (+0x64) returns the locked
rect's first row in the canvas and the canvas pitch, its `Unlock` (+0x80) does nothing - all that
`CVidMode::LockSurface` (0x799FA0) and `UnLockSurface` (0x79A820) call. 8-bit bitmaps 1..32 wide
(width 1 the single-pixel path, 2 and other even widths the pairs, odd widths above 1 the leading
pixel plus pairs) and 1..32 high, drawn upward from the last row of a 64x40 16-bit canvas of random
bytes with RenderDirect's own `nDataJump`, on 5-6-5 and 5-5-5 alternating; the whole canvas and the
result compare.
