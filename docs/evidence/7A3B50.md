# 0x7A3B50 CNetworkWindow::ReceiveCall

## Decompiled

No driver bundle row carries this function — it is a dependency reached
from bundle row 0x7A7670 (`CNetwork::SlidingWindowReceive`), which calls
it once per player on the sliding-window slot
`&cNetwork.m_pSlidingWindow[i]`. The port is anchored on the exe bytes
(see exemption). What the exe does, in order:

1. Enters the cNetwork+0xF52 critical section and sets
   `m_bSomethingHappened` = TRUE. A local byte (v1) starts FALSE.
2. Kind 3 is a system message: straight to
   `AddToIncomingQueue(GetPlayerID(m_nPlayerNumber), m_idLocalPlayer,
   pData, dwSize)`, v2 stays TRUE, the payload is not deleted.
3. Otherwise it decodes `nFrame` (bytes 1-2) and `nAck` (bytes 3-4).
   - Kind 0 (data): NAKs an unexpected in-order frame via
     `FrameSend(2, 0)` when `m_bNoNak`; on the three-way wraparound
     window test it stages the payload in `m_pIncomingBuffers[0]`
     (v1 = TRUE) and drains it:
     `AddToIncomingQueue`, `m_bNoNak = TRUE`, buffer cleared,
     `m_nFrameExpected++` / `m_nTooFar++` (both wrap 0xFFFF → 0), and
     the ack timer armed
     `m_nAckTimer = m_nPacketTimeout + GetTickCount()`, clamped
     against `CNetworkWindow::MAX_TIMEOUT_TICK_COUNT` (0 on overflow).
   - Kind 2 (ack): on the three-way test against
     `(m_nAckExpected, m_nNextFrameToSend, (WORD)(nAck + 1))` it
     resends the pending frame via `FrameSend(0, nAck + 1)`.
4. The ack drain loop — the same three-way test but against plain
   `nAck` — retires acked frames: `m_nNumBuffered--`, resend timer
   cleared, `m_pOutgoingBuffers[0].pData` deleted and NULLed,
   `.dwSize = 0`, `m_nAckExpected++` (0xFFFF → 0 wrap).
5. Leaves the critical section, runs the inlined `SetPlayerTimeout`,
   and deletes `pData` iff v2 is FALSE.

## Notes

The v1 flag is one stack byte: the prologue zero at 0x7a3b64 executes
while the EnterCriticalSection argument (pushed at 0x7a3b63) is still
on the stack, so with five pushes live `[esp+0x17]` is the same byte
that becomes `[esp+0x13]` once the stdcall callee pops its argument —
and it is exactly the byte written TRUE at 0x7a3c63 (buffer accepted)
and reloaded into `bl` at 0x7a3d9e. The fork's `v2 = v1` at the end of
the else branch is exe-equivalent: on the kind-3 path the exe jumps
straight to the exit with `bl` still 1 (v2 = TRUE, no delete), and on
every other path the reload observes the same value the else branch
computed.

The kind-2 sign dance at 0x7a3cfa-0x7a3d09 is dead code: `x =
(WORD)(nAck + 1)` is at most 0x10000, bit 31 never sets, and the `jns`
is always taken. `x` = 0x10000 only when `nAck` = 0xFFFF, and the
16-bit window compares plus FrameSend's `WORD [esp+0x18]` read reduce
it to 0 — exactly `(WORD)(nAck + 1)`.

The two window tests intentionally differ: the kind-2 resend test uses
`(WORD)(nAck + 1)` (an ack of frame n retires frame n, so the resends
start at n+1) while the drain loop tests plain `nAck` — the fork only
has the plain-`nAck` shape in both places.
