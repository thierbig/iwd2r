## Notes

- The count a 226 carries in m_specificID is spent once per 2DA row that
  yielded anything from anyone (bTookSomething is set per member and
  read per row), not once per item: a row that drains three personal
  copies and a bag stack still spends one. A 220 walks with `remaining`
  pinned at -1, so it never stops early and never reaches the fallback.
- The fallback fires only when a 226 took nothing at all anywhere
  (`remaining == m_curAction.m_specificID` after the walk): the 2DA's
  default cell names an item, uppercased, whose resource must exist in
  the key table (type 1005) before a single zero-count copy is placed
  with feedback. RNDTRES's default cell is `*`, which names no item, so
  the shipping 226 that matches nothing places nothing.
- A missing 2DA is not an error: the CResHelper/CResRef chain quiets the
  miss (CDimmKeyTable::FindKey returns NULL, C2DArray::Load skips), the
  row walk runs zero times, and the action still returns ACTION_DONE
  having touched no one.
- The personal-copy take is exactly TakePartyItem's: clear the member's
  slot through a CMessageRemoveItem keyed (slot, taker id, member id),
  sweep the quick buttons for abilityNum 0/1/2 on that slot, and hand
  the copy to PlaceItem with feedback on. The bag copies differ: they
  arrive as one freshly created stack of `taken` items, placed without
  feedback, because the drained originals die inside the bags.
- GetShare failure (member id resolving to nothing) returns
  ACTION_NORMAL -- the action stays running and the engine re-enters it
  -- and does not ReleaseShare, matching the original's early return.
