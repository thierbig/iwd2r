# 0x518560 CMultiplayerSettings::sub_518560

## Disassembly reading

`llvm-objdump` of the vanilla exe, 0x518560-0x518575 (22 bytes,
`__thiscall`, no arguments):

```
518560: xor eax,eax
518562: xor edx,edx
518564: cmp byte ptr [ecx + edx + 0xac], -1
51856c: je  51856f
51856e: inc eax
51856f: inc edx
518570: cmp edx, 6
518573: jl  518564
518575: ret
```

It counts the entries of `field_AC` (settings+0xAC, `unsigned char[6]`) that
are **not** the byte `0xFF` (-1). `field_AC` is the "character slot this player
is viewing" array set by `sub_518580` and cleared to -1 by `sub_518650`.

## Callers

0x437950 (the leave-area-Lua permit handler) and 0x438BF0 (the leave-area-name
permit handler), plus 0x5AC110 `CInfGame::CanSaveGame`, 0x74C0D0
`CGameSprite::LeaveArea` and 0x74CDB0 `CGameSprite::LeaveAreaName`.

## Notes

The earlier port compared `field_AC[index] != -1`. Because `field_AC` is
`unsigned char`, the element promotes to `int` 255 and `255 != -1` is always
true, so the function counted all six slots even when every one was cleared to
-1. That made 0x437950 always take the "remote player is in the inventory
screen" branch and deny every leave-area-Lua request. The comparison is now
`!= 0xFF`, matching the byte compare in the disassembly; the existing callers
get the intended counts as well.

Proof: the 0x437950 unit test sets the array to six `0xFF` values and gets the
allow answer 1, then sets one real slot and gets the deny answer 0.
