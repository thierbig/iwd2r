## Notes

**Gate.** `m_nServiceProvider == 0 || m_idLocalPlayer ==
pSprite->m_remotePlayerID` (local or owning player) still requires
`GetGameSave()->m_cutScene == 1 && cNetwork.m_bIsHost == 0` (a
non-host inside a cutscene) to do the work; everything else calls
finish() and returns (src/CMessage.cpp:14629, De Morgan of the exe's
compound condition). finish() = TYPE_SPRITE ->
`sub_75F3D0(field_85 & 1)` (:14597) + `ReleaseDeny` (:14629 region).

**field_108 re-capture ladder** (bits tested in the exe's order, each
arm re-captures from the sprite when its bit is CLEAR):

- 0x400 area (m_sAreaString; "NO_AREA" sentinel at :14640 via CResRef
  operator= + CopyToString), 0x2 position, 0x100 sequence, 0x200
  facing, 0x4 state, 0x1 path group - `new LONG[m_nPath]` copy whose
  result overwrites the sprite's old m_pPath with no delete: the exe
  leaks the old array by design and the port reproduces the overwrite
  (this is why parity flags operator_new 0x7FC95B but no
  operator_delete), 0x8 HP (else re-capture, MoveToFront on
  resurrect, :14691), 0x800 flags.

**NO_AREA arm** (:14702): RemoveFromArea under m_bInAreaTransition,
visible-area teardown, single-machine party-slot loop i<6 with
GetShare retry, connected CINFGAME_MAX_AREAS loop,
UpdatePersonalItemStatus (:14765), finish.

**Constants.** Tile math divides by 16 (x) and 12 (y); the path grid
is 320 wide - last path node -> tile `node % 320, 320 - node/320 - 1`
(:14941 region), fallback `pt/16, pt/12`; spawn square ->
`(16*ptOpen.x + 8, 12*ptOpen.y + 6)`; AddToArea uses LIST_FRONT;
`SEQUENCE_PATH = 10` is the exe's constant at ds:0x85bbbd (:14941);
animation base 0x6000, gender==2 adds 0x10 (:14877).

**Jump tables.** 0x50ee98 (7 entries, race) and 0x50eeb4 (11 entries,
class) become the statics at :14871-:14872:
`RACE_BITS[7] = { 0, 1, 1, 2, 3, 2, 5 }`,
`CLASS_BITS[11] = { 0x100, 0x300, 0, 0, 0x100, 0x100, 0x100, 0x100,
0x300, 0x200, 0x200 }`, or'ed onto 0x6000. The rebuild is guarded by
gender in {1,2}, race in [1,7], class in [1,11] - out-of-range skips
the rebuild but not the spawn.

**The m_colors[7] vs 8-iteration loop finding.** The 0x8000
spellStates phase resets mirror/stone-skin and then runs an
8-iteration color loop reading sprite bytes 0x5C8..0x5CF into
SetColorRange(0..7) (:14793-:14796). But `m_colors` is BYTE[7] at
0x5C8 - the byte at 0x5C8+7 = 0x5CF is the adjacent member
`m_effectVersion`. Reading `m_colors[7]` literally would be an
out-of-bounds read (UB) while the exe plainly passes that 8th byte.
Resolved as `(i < 7) ? m_colors[i] : m_effectVersion` -SetColorRange
receives the exact byte the exe passes, with no OOB access.

**CWarp/CBaldurEngine slot calls.** The closing pair is virtual-slot
traffic, not a member call: load pActiveEngine, push m_targetId,
call [vtable+0x108] = CWarp::UpdateCharacterStatus (CWarp.h:178),
then at 50ee16 call [vtable+0xEC] = CWarp::UpdatePersonalItemStatus
(CWarp.h:171) - NOT the engine's +0x1C54 member. Ported as
`static_cast<CBaldurEngine*>(g_pBaldurChitin->pActiveEngine)->
UpdateCharacterStatus/UpdatePersonalItemStatus` (:15098-:15099),
CBaldurEngine being CWarp's base; in-tree static_cast precedent
src/CItem.cpp:1405/1446, src/CBaldurChitin.cpp:1567/2532. The
NO_AREA block makes the same UpdatePersonalItemStatus slot call at
:14765.

**Named-area path** (area string != NO_AREA): generalState 0x800
base-stat clear, 0x8000 spellStates incl. the color loop +
ClearColorEffectsAll, 0x10000 skills + field_2FF, 0x1000 fadeSpeed,
0x4000 translucent, 0x2000 visualEffects 32-iteration loop (i==24
InitBlur, i!=25 reset + field_9088[i].Stop()). Then three arms:
already-in-area or FindKey(resRef, 1010) == NULL -> skip; the
LEAVEAREALUA CAIAction arm (ClearActions(FALSE) / m_interrupt /

arm builds a dead `sOldAreaName` CString (assigned from the old

**Four path arms** (named creature, FindKey(sScriptName)): the

**Move-scale recompute.** `nDist = (LONG)(sqrt((double)(dy*dy*16/9 +

`(dy*4/3*1024*scale)/nDist` - the exe's Hypotenuse helper 0x7E8034
returns the double (st0), fadd 0.5 at ds:0x848dd0, __ftol 0x7E812C;
its <<10 and the 0x55555556 magic-division for dy*4/3 are the same
arithmetic the spelled expression performs.
