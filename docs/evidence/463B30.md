# 0x463B30 CGameAIBase::TakePartyItem

Member of CGameAIBase in the original's CGameAIBaseActions.cpp,
`__thiscall` `SHORT TakePartyItem()`, 1,530 bytes (0x463B30-0x464129).
Ghidra's CGameSprite_B3AUTO_00463b30 name is wrong: the function reads
`this` as a CGameAIBase (m_curAction at 0x476, m_id at 0x5C) and its
caller loads the CGameAIBase pointer into ecx.

Ported in three ranges, one commit each: 04461a9e (0x463B30-0x463E17:
the action dispatch reading number/range from m_specificID, the party
loop with the GetShare retry, the 193 area-and-distance gate, and the
first personal take with its CMessageRemoveItem and quick-list sweep)
and the range 2 commit (0x463E18-0x464129: the 204 charge counting with
the stack split, the re-find loop with its per-action stop gates, the
bag drain, and the loop-exhausted verdict). The split is at 0x463E18,
the `mov eax,[esp+0x34]` numbered test that opens the count logic. The
caller arms are the ExecuteAction commit (cases 116/188/193/204 of
0x44DC10, 0x44EF37-0x44EF45: `mov ecx, ebx; call 0x463B30; mov esi,
eax; jmp 0x4526F7`, i.e. `returnValue = TakePartyItem(); goto done`).

## Callers

Exactly four switch arms sharing one code path: cases 116
(TakePartyItem), 188 (TakePartyItemAll), 193 (TakePartyItemRange) and
204 (TakePartyItemNum) of CGameAIBase::ExecuteAction. The arm routes
the result through the common done label (0x4526F7), not the release
tail, so TakePartyItem runs with no target share held — it acts on the
executing object itself and takes its own shares on the party members.

## Callees

No new callees: every call is in-tree — CAIAction::GetString1,
CInfGame::GetNumCharacters and GetCharacterId, CGameObjectArray
GetShare/ReleaseShare, CGameSprite::GetPos, CGameSprite
::FindItemPersonal, the CItem copy constructor and the six-argument
constructor, CItem::GetUsageCount/SetUsageCount/GetMaxStackable, the
CMessageRemoveItem and CMessageAddItem constructors,
CMessageHandler::AddMessage, CGameSprite::CheckQuickLists (three
calls, 2/slot/0-2), CGameSprite::TakeItemBags and CGameAIBase
::PlaceItem. All were ported before this task.

## Notes

- The action id is re-read live from m_curAction (word 0x476) at every
  gate, including after each take and after the bag drain; the render
  reads the member directly rather than caching a local.
- 116 and 193 return ACTION_DONE after the first personal take, inside
  the member iteration. 188 keeps re-finding (match increments past
  each copy) until the member has none left, then hits the bag gate
  outright. 204 decrements number per non-stackable copy and subtracts
  the whole charge count of a stackable one, returning DONE at
  number <= 0.
- The 204 stack split: a stackable item with more charges than remain
  is reduced on the taken copy to the leftover count, that reduced copy
  is added back to the member through a CMessageAddItem, and the taker's
  PlaceItem still receives the same reduced copy — both sides keep the
  remainder. The quirk is the exe's (0x463E30-0x463EB3) and is kept
  as-is.
- The bag gate (0x463F54) sits inside the in-range branch, after the
  personal re-find loop: it fires while lastItem is still NULL (nothing
  personal was taken from anyone — bag takes never set lastItem), for
  188 outright, or while 204 still wants charges. It drains
  TakeItemBags(sName, number, -1) and hands the taker one freshly
  created stack of the taken count (new CItem(CResRef(sName), 1, 0,
  0, 0, 0), PlaceItem count = taken), not the bag's own copies.
- Consequence of the two rules above: a 116 whose item no member holds
  personally drains one bag copy from every in-range member yet ends
  with lastItem NULL — the action reports ACTION_ERROR after taking.
  Faithful to the exe.
- 193 measures squared grid distance (coordinates divided by the
  square size, Y by 12 and X by 16) between this sprite and the member
  and skips members over m_specificID squares away or in another area;
  out-of-range members release straight to the next portrait.
- A GetShare that never succeeds returns ACTION_NORMAL with the sName
  destructor unwinding; the loop-exhausted tail returns ACTION_DONE
  when anything was ever taken and ACTION_ERROR otherwise.
