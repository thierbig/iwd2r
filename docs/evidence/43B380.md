# 0x43B380 CBaldurMessage::OnDeleteAreaResult

Read-only evidence from the MD5-pinned original via
`python3 -I tools/parity/annotate.py 0x43B380` and the Ghidra decompile
below; Ghidra names the function `FUN_0043b380`.

## Identity and calling convention

Member of CBaldurMessage in the original's Baldur/CMessage.cpp, dispatched
by 0x4EE020's `DELETEAREA` (k = 107) `/` `r` (114) arm. `__thiscall`,
`ret 0xc`: `(INT nMsgFrom, BYTE* pByteMessage, DWORD dwSize)`.

**Survey correction:** the survey named this row "OnDeleteAreaResult (tally
+ GetDeleteAreaString)" with subtype `d` (100). The disassembly shows the
`r` (114) arm and the body is a **vote receiver**, not a tally: it records
one client's 'y'/'n' into the poll's per-player slot. Subtype 100 (`d`) is
the delete/no-delete *result* received by row 52's handler.

## Body

Guards: an established session and `m_bIsHost` true (the poll runs on the
host), else FALSE. Decodes `{BYTE areaLen; char area[]; BYTE vote}`. When
`m_bDeleteAreaPolling` (+0x73) is set and the decoded area equals
`GetDeleteAreaString()`, it maps `nMsgFrom` through
`CNetwork::GetPlayerID` and writes the vote into `m_pnDeleteAreaVotes[+0x7C]`
at the slot whose `m_pnDeleteAreaVoters[+0x82]` matches that player id. The
tally itself is `DeleteAreaBallotResult` (0x43xx, already in tree).
