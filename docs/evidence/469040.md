# 0x469040 CGameAIBase::GlobalBitGlobal

2,460 bytes, `CGameSprite_GlobalBitGlobal` in the Ghidra names (the
function is the CGameAIBase action handler dispatched on `this`, not a
CGameSprite-only body). No fork body exists for it.

## Identification

The CGameAIBase action handler for script action 248
(GlobalBitGlobal): combines a source variable into a destination
variable with a bitwise op. `m_curAction` string1 names the destination
and string2 the source, both `SCOPE:NAME`, uppercased, split at the
first colon; `m_specificID` picks the op (1 AND, 2 OR, 3 XOR; any other
value returns ACTION_ERROR (0xFFFE) without writing).

The source read: GLOBAL reads the game variables, LOCALS reads the
sprite's local variables through CGameSprite::GetLocalVariables()
without the sprite-type check the write side has, and anything else is
an area-scope lookup. The destination write: GLOBAL and LOCALS write
the game/sprite variable storages (LOCALS gated by
GetObjectType() == TYPE_SPRITE, same gate as SetGlobal), and anything
else (including the literal scope MYAREA) writes the variables of the
area named by the (possibly replaced) destination scope. Every
successful write posts a CMessageSetVariable.

Original quirks kept, each with a NOTE in the body:

- The source fallback tests the **destination** scope against MYAREA,
  not the source scope: a MYAREA destination also redirects the source
  lookup into the acting area (0x4692A1 reads the dest-scope slot while
  both GLOBAL/LOCALS source checks read the source-scope slot).
- The LOCALS **source** read is ungated; only the LOCALS **write** has
  the sprite-type gate.
- The MYAREA destination arm replaces the destination scope with the
  area's name, so the posted message carries the area name (as
  SetGlobal does).
- The area's name is read as a C string from the start of the area
  (its header's RESREF), as in SetGlobal.
- The not-found GLOBAL arm leaks its new'd CVariable and the not-found
  MYAREA arm deletes its heap copy after AddKey; both render as stack
  CVariables that outlive the AddKey copy, the SetGlobal house style.
- A missing source variable (or an unknown source scope with no
  matching area) leaves nSrc at 0 and the op still applies.

- Sole exe caller: the action dispatch at 0x4506A2 (case 248), plain
  `call; returnValue; goto done` -- wired to
  `returnValue = GlobalBitGlobal(); goto done;` in ExecuteActions.

## Tests

`tests/test_global_bit_global.cpp` drives the handler on the
finished-character probe through ExecuteActions with a real action 248:
AND/OR/XOR on existing and missing GLOBAL variables, the LOCALS write
through the sprite's own variables, the ACTION_ERROR return for an
unknown op, and the dest-is-MYAREA source redirection quirk. The
checker's strings column flags "p5E" at 0x84882C: that address is the
CMessageSetVariable vtable the message construction writes, not a
string.

No existing scenario exercises action 248: the parked scenarios do not
run scripts that use GlobalBitGlobal, and nothing else in-tree calls
the handler.
