## Notes

The host's pump for remote control changes: with the session open and owned
(`GetSessionOpen`/`GetSessionHosting`, 0x8CF6D8 + 0x1032/0x1033) it checks
the remote object array's pending count (`m_nControlsChanged`, the SHORT at
array +0x6, i.e. game +0x3760; the array is game +0x375A) and returns FALSE
when it is clear. Otherwise `MarshalControlChanges(&pData, &dwSize)` builds
the record - the SHORT count of changed areas with their entries, then the
SHORT count of control changes with `{PLAYER_ID old; LONG oldObject;
PLAYER_ID new; LONG newObject; BOOLEAN localControl}` each - **and consumes
the queue** (it deletes the nodes and zeroes both counts). A marshal that
answers anything but TRUE returns FALSE.

The buffer is broadcast as `OBJECT/67` to the empty player name with
`SEND_ALL_PLAYERS | SEND_GUARANTEED` (0x100 | 0x200), type 79
`MSG_TYPE_OBJECT` (0x84CF98) and the new subtype 67 `MSG_SUBTYPE_OBJECT_CONTROL`
(0x84CF9A) - the constant is new here (WSO has no names, T122 §3). The buffer
is freed with `operator delete` (it comes from `new BYTE[]`), matching the
exe.

**Return value:** the function has a single epilogue that zeroes EAX
(0x430D31), so it answers FALSE on every path, including after a successful
broadcast. The port mirrors that with a NOTE; all three callers ignore the
value.

`tests/test_ui_misc.cpp` ("msg: ObjectControl broadcasts the queued control
changes once", `[uimisc][msg][data]`) runs on the game's own remote object
array: it queues one change as `ChangeControl` leaves it, then a closed
session and a client answer FALSE and leave the queue, while the host's call
consumes it (`m_nControlsChanged` 1 -> 0, head and tail NULL), the answer
FALSE in every case. The null provider stops the send before the static
buffer, so the wire bytes stay read-only. **It bites**: with the stub 3 of
the 11 assertions fail (the consumption ones).
