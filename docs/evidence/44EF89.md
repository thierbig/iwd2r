# 0x44EF89 CGameAIBase::ExecuteAction cases 153-159

Seven arms of the `CGameAIBase::ExecuteAction` switch (0x44DC10) in the
original's GameAIBase.cpp, `__thiscall`
`int ExecuteAction()`. ChangeEnemyAlly 0x44EF89-0x44F1CB, ChangeGeneral
0x44F1CC-0x44F394, ChangeRace 0x44F395-0x44F55D, ChangeClass
0x44F55E-0x44F621, ChangeSpecifics 0x44F626-0x44F7EE, ChangeGender
0x44F7EF-0x44F9B8, ChangeAlignment 0x44F9B9-0x44FB80; the block ends at
0x44FB81 (case 160 starts 0x44FB82).

Ported in three ranges, one commit each: d685dd52 (case 153
ChangeEnemyAlly), 8aa58796 (cases 154-156 ChangeGeneral, ChangeRace,
ChangeClass), 01bb15dd (cases 157-159 ChangeSpecifics, ChangeGender,
ChangeAlignment). Tested in c756b178.

## Shared shape

All seven resolve the target identically:
`GetTargetShareType(CGameObject::TYPE_SPRITE)` with `bShare = TRUE`, and
an unresolved target still falls through to `returnValue = ACTION_DONE`.
The value written is `LOBYTE(m_curAction.m_specificID)`.

Six arms (153-155, 157-159) then share one body: copy
`pSprite->GetAIType()`, `m_liveTypeAI` and -- for 153 the sprite's
`m_startTypeAI`, for the others `m_liveTypeAI` again -- into three local
CAIObjectType copies, call the per-arm byte setter
(SetEnemyAlly/SetGeneral/SetRace/SetSpecific/SetGender/SetAlignment,
members m_nEnemyAlly +4, m_nGeneral +5, m_nRace +6, m_nSpecific +0x13,
m_nGender +0x14, m_nAlignment +0x15) on all three, write them back with
`SetAIType(typeAI, TRUE, FALSE)` (update live, not start),
`m_liveTypeAI.Set(...)` and `m_startTypeAI.Set(...)`, then destroy the
three locals and jump to the shared done label.

## Per-arm deltas

- **153 ChangeEnemyAlly (0x44EF89)**: the only arm whose start copy is
  taken from `m_startTypeAI` rather than `m_liveTypeAI`, and the only
  one that posts anything. After the write-back it builds a
  `CMessageSpriteUpdate(pSprite, pSprite->m_id, pSprite->m_id)` and:
  in single player (`GetServiceProvider() == SERV_PROV_NULL`) or when
  the sprite belongs to the local player
  (`m_idLocalPlayer == pSprite->m_remotePlayerID`), plain
  `AddMessage(message, FALSE)`; otherwise, only when
  `m_bConnectionEstablished == TRUE` and the game is in a cut scene
  (`GetObjectGame()->m_gameSave.m_cutScene == TRUE`),
  `AddMessage(message, FALSE, CMessage::BROADCAST_FORCED_OTHERS)`.
- **154 ChangeGeneral (0x44F1CC), 155 ChangeRace (0x44F395), 157
  ChangeSpecifics (0x44F626), 158 ChangeGender (0x44F7EF), 159
  ChangeAlignment (0x44F9B9)**: the shared shape verbatim minus the
  message, with the start copy sourced from `m_liveTypeAI` -- so the
  start type inherits the live type's other bytes rather than the
  sprite's stored start type.
- **156 ChangeClass (0x44F55E)**: a complete no-op. The original
  constructs three default CAIObjectType locals and destroys them again
  without calling a setter, SetAIType, or any message -- the ChangeClass
  IDS action has never worked. Ported with the three unused locals and
  a comment; no `m_nClass` write exists.

## Message routing

`CMessageSpriteUpdate::GetCommType()` returns BROADCAST_OTHERS, so with
`bForcePassThrough` FALSE the handler's Broadcast path reduces to
`delete message` in a single-player game (no other players to sync, per
docs/adr/0002-single-player-only.md; the original drops it the same
way). The EA write and the message post sit in the same conditional, so
the test's field assertions prove the message arm ran while the handler
queue stays empty.

## Callees

No new callees: GetTargetShareType (0x45BDD0), CAIObjectType default
and copy construction, `Set` and the per-field byte setters,
`CGameSprite::SetAIType` (vtable +0xBC), the CMessageSpriteUpdate
constructor (0x50C260), both `CMessageHandler::AddMessage` overloads
(0x4F7500, and the three-argument 0x4F7530 already ported at
src/CMessage.cpp:8013), `CNetwork::GetServiceProvider`,
`CInfGame::GetObjectGame` and the CGameSave member reads were all
already in-tree.

## Test

`ai: ExecuteAction changes allegiance and general, ChangeClass changes
nothing` in tests/test_ai.cpp (c756b178): ChangeEnemyAlly(255) then
ChangeEnemyAlly(200) through ExecuteAction -- the two distinct values
prove the byte follows the action on GetAIType(), m_liveTypeAI and
m_startTypeAI rather than coinciding with the fixture -- ChangeGeneral(4)
with the start copy's EA inherited from the live copy, ChangeClass(99)
leaving every field untouched, and the handler queue asserted empty
after the message-bearing run.
