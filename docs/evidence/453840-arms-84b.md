## 0x45D560 CGameAIBase::GetReaction

The Reaction trio's shared callee, ported whole in daf67713 (318 bytes,
`// 0x45D560` in src/CGameAIBase.cpp). The sprite's enemy-ally byte picks
the reputation band: EA_PC reads the game's reputation / 10
(CInfGame m_nReputation), anyone else the sprite's own derived
m_nReputation. The reaction byte is this AI object's reaction roll
(m_reactionRoll +0x590) plus the charisma column of the caller's rule
tables (m_tReactionModCharisma.GetAtLong(CPoint(CHR-1, 0)), the
sprite's derived m_nCHR) plus the reputation column
(m_tReactionModReputation.GetAtLong(CPoint(band-1, 0))), truncated to a
byte. A ranger caller (GetObjectType TYPE_SPRITE and the class mask bit)
whose race the sprite's hates (IsHatedRace over the sprite's AI type and
base file header) has four points taken off, floored at zero. The test
reads the byte back through this public getter rather than re-deriving
the tables.

## Arm notes

- The Reaction trio is one body spelled three times, one arm apart in
  the listing (0x4554D9 / 0x45554C / 0x4555C1): identical resolution,
  GetReaction, feedback and spill, sub/neg/sbb/inc where 0x403D has
  setg and 0x403E setl. The port shares the body and picks the compare
  by trigger ID, the way the NumCreature trio does. This finishes the
  family 83z opened (0x4019 Reputation / 0x401A ReputationGT) and 84a
  closed (0x401B ReputationLT).
- The NumDead trio is likewise one body spelled three times (0x456885 /
  0x456947 / 0x456A0D): identical name build and hash look-up,
  equality, setg and setl in turn. The miss path answering from the
  specifics alone (== 0, < 0, > 0) is the trio's own -- a missing
  dead-count global means zero deaths, so NumDead(0) holds and the
  inequalities follow its sign convention.
- The discarded sName.Left(32) (0x4568D5) looks like a truncation the
  engine meant to apply and dropped: the result is destroyed unread and
  FindKey takes the untruncated name. The port keeps the call as a
  no-op with a comment rather than silently dropping it.
- 0x4075's null-cause exit is the bare early epilogue 0x45AB7A
  (nothing released, FALSE), not the release tail -- the same asymmetry
  as the 0x4077/0x4078 NumItems pair 84a recorded. Its TRUE path runs
  through 0x456E7B, which releases pObject2 where the plain release
  tail 0x45AD4C also would; the net answer is the same either way.
- 0x40B0's null-sprite path answers TRUE (0x458636 into 0x45AD47, the
  tail that sets esi to 1 before releasing) -- the opposite of every
  other sprite-resolving arm in the function, which answer FALSE. The
  dead tests read the base block first (0x45864C) and the derived
  second (0x45865A); the port checks both either way round.
- 0x40F0's slot bound is checked above only: specifics >= 24 answers
  FALSE (jge at 0x45A68C), but a negative specifics passes and indexes
  before m_items -- a vanilla quirk the port keeps by indexing
  unchecked; the test deliberately does not drive it. The original
  reads GetSpecifics and GetEquipment twice each (0x45A692 / 0x45A6B9);
  the values cannot differ, so the port reads them once.
