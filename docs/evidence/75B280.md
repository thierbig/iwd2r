## Behavior established from the instructions

- The body ends with `ret` at 0x75BC66. Thus the requested end 0x75BC67 is
  exact: 0x75B280..0x75BC66 inclusive is 2,535 bytes (0x9E7); the next bytes
  are alignment and 0x75BC70 is the following PickLock function. There is no
  size correction.
- The new 12-byte object at 0x75B30D..0x75B33D receives vtable 0x84D130 whose
  Run slot (+0x1C) is 0x4FF670, identifying `CMessageEscapeArea(m_id, m_id)`.
  It is passed to `AddMessage(..., FALSE)` on every invocation, then
  `m_bEscapingArea` is set. Its BROADCAST_FORCED_OTHERS comm type consumes the
  message rather than locally queueing it in the single-player tests; the
  handler sets the flag directly as well. A party member is passed through
  `LeaveParty`; its result is ignored.
- EscapeArea (108) removes and returns DONE at action count 120.
  EscapeAreaDestroy (176) instead uses `specificID * 15`. Both remove and
  return DONE when `m_canBeSeen <= 0`. If string1 is empty, later processing
  stamps `m_expirationTime` with the world time, and, with no current path,
  clears the action's specificID2 (+0x530 at 0x75B4DF) - the edge-search
  state marker, distinct from the 176 delay parameter in specificID
  (+0x52C).
- The view rectangle is a `CopyRect` of CInfinity's rViewPort followed by
  `GetViewPosition` and `OffsetRect`. The sprite's FX rectangle and reference
  point come from `CalculateFxRect(..., m_posZ)` (assert line 2071). The
  original also calls and discards `GetHeightOffset`. A position outside the
  view (a PtInRect test followed by the four explicit comparisons) removes it.
- `bl` at 0x75B4FD..0x75B531 is TRUE exactly when `m_actionCount % 16 == 0`,
  then cleared if the action's saved destination (m_curAction.m_dest,
  +0x540/+0x544) is outside the view. After the transition-target
  attempt fails, the handler proceeds if this flag is set or if there is no
  path and no search request; otherwise it returns NORMAL. This polarity comes
  from the signed remainder sequence and `neg/sbb/inc`, not the C flags' usual
  visual shorthand.
- 0x75B533..0x75B61F calls the directly necessary helper 0x46C9E0 as
  `(m_id, GetVisualRange(), m_terrainTable, FALSE)`. The compiler leaves the
  helper's third/fourth arguments underneath the no-argument virtual
  GetVisualRange call. If a target id is returned, an eleven-argument
  CAIObjectType is built, its instance is set to that id, and
  GetTargetShareAIType(..., TYPE_AIBASE) plus MoveToObject run. The target is
  released when non-NULL. DONE and ERROR both become removal plus DONE;
  every other movement result becomes NORMAL.
- With specificID2 zero (0x75B644 reads +0x530; 0x75B802 re-tests it
  redundantly between the attempts), 0x75B652..0x75B94E makes two
  AdjustTarget attempts.
  The first chooses the nearer horizontal/vertical view edges, extended by
  the FX rectangle's width/height plus one. The second chooses the opposite
  horizontal and vertical sides. The area limits are signed SHORT nAreaX/Y
  divided by 16x12. Both blocks test their original quotient after changing
  world coordinates, then recompute the quotient. All four AdjustTarget calls
  use the sprite's current search square, personal space and tolerance 10.
- If those attempts fail (or specificID2 was nonzero), an outstanding path
  returns NORMAL. Otherwise 0x75B966..0x75BC3E scans the top/bottom rows in
  16-pixel x steps and then the left/right columns in 12-pixel y steps. Each
  successful AdjustTarget ends both loops without overwriting its adjusted
  search square. Search-square output does not replace the world point.
  Failure everywhere removes; success with empty string1 sets
  specificID2 = 1 (+0x530 at 0x75BBC0).
- The common movement tail removes when the adjusted goal square is already
  the sprite's square. Otherwise it stores the retained world candidate in
  m_curAction.m_dest (+0x540/+0x544, 0x75BC0D/0x75BC15) and calls
  MoveToPoint(candidate, 0) with the local candidate by reference. DONE and
  INTERRUPTABLE become NORMAL; other results, notably ERROR, propagate
  unchanged. The write lands in the action's dest, not the sprite's
  m_curDest, so MoveToPoint's own same-destination guard does not fire: when
  the candidate differs from m_curDest, MoveToPoint adopts it and starts a
  real asynchronous search request. The AR1000 test pins that request and
  its target point.
