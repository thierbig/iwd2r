# 0x43A7C0 CBaldurMessage::OnAnnounceAreaMapNote

Read-only evidence from the MD5-pinned original via
`python3 -I tools/parity/annotate.py 0x43A7C0` and the Ghidra decompile
below; Ghidra names the function `FUN_0043a7c0`.

## Identity and calling convention

Member of CBaldurMessage in the original's Baldur/CMessage.cpp, dispatched
by 0x4EE020's `AREAMAPNOTE` (A = 65) `/` `a` (97) arm. `__thiscall`,
`ret 0xc`: `(INT nMsgFrom, BYTE* pByteMessage, DWORD dwSize)`; nMsgFrom is
ignored.

## Body

One guard: `m_bConnectionEstablished`, else FALSE. The body decodes the
same payload as 0x43A470:

    {BYTE areaLen; char area[]; WORD startX; WORD startY;
     DWORD noteLen; char note[]; DWORD dwFlags; STRREF strRef}

sets `m_bInOnAreaMapNoteAnnounce` (CBaldurMessage +0x04) while it calls
`CGameAreaNotes::Add` on `GetArea(sArea)->GetAreaNotes()`, and clears the
flag afterwards. The flag is what keeps `Add`'s client branch from sending
the note back to the host, so the receiving machine applies it locally.

**Original wire quirk (same as 0x43A470):** the trailing STRREF is not read;
the handler passes -1 and `Add` re-resolves the note text through its TLK
override.
