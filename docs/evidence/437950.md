# 0x437950 CBaldurMessage::OnLeaveAreaLuaRequestToServer

## Disassembly reading

`llvm-objdump` of the vanilla exe, 0x437950-0x437D15 (965 bytes,
`__thiscall`, `ret 0xc`), read instruction by instruction (the box is off; there
is no Ghidra decompile for this function yet). Frame: after the prologue the
arguments are `nMsgFrom` at [esp+0x40], `pByteMessage` at [esp+0x44] and
`dwSize` at [esp+0x48]; `CString sPlayerName` is at [esp+0x10], the parsed
strings at [esp+0x14] (area name) and [esp+0x18] (parchment).

- Guards (0x437975-0x437998): `g_pChitin->cNetwork.m_bConnectionEstablished`
  (chitin+0x1032) and `m_bIsHost` (chitin+0x1033) must both be TRUE, else
  return FALSE.
- `GetPlayerName(nMsgFrom, sPlayerName)` (0x7A7240) at 0x43799E-0x4379AE; the
  requester is the reply recipient.
- Parse after the 3-byte header (`CNetwork::SPEC_MSG_HEADER_LENGTH`, the DWORD
  at 0x85E670): `{DWORD remotePlayerID (+3); DWORD remoteObjectID (+7);
  DWORD x (+11); DWORD y (+15); WORD direction (+19); BYTE parchmentLen (+21);
  char parchment[]; BYTE areaNameLen; char areaName[]}` (0x4379B3-0x437A61).
  The strings are built with `CString_ConstructWithLength` (0x7FA7F5).
  **There is no `cnt == dwSize` assert**: `dwSize` is never read and the two
  length bytes are trusted.
- `cGame->m_cRemoteObjectArray.Find(remotePlayerID, remoteObjectID, objectId)`
  (0x59B300) at 0x4379E2; a miss stores `CGameObjectArray::INVALID_INDEX`
  (0x851878).
- Feedback/deny (0x437A7D-0x437B3D): the default answer is 1. If
  `CMultiplayerSettings::sub_518560()` (0x518560, the number of players viewing
  a character) is > 0, the feedback is STRREF 26826 ("Cannot leave area while
  remote player is in inventory screen."); else if `sub_5186A0()` (0x5186A0,
  the number of players in the level-up screen) is > 0, it is STRREF 41398
  ("Cannot leave area while remote player is in the level up screen.").
  When a feedback is due and the object id is valid, it `GetShare`s the sprite
  (0x599A50, retrying SHARED/DENIED), calls `CGameSprite::FeedBack(..., 0, 0,
  -1, 0, 0, 0)` (0x7349A0) and `ReleaseShare`s it (0x599E70); the answer
  becomes 0.
- Paused game (0x437B49-0x437B60): `g_pBaldurChitin->m_pEngineWorld->m_bPaused`
  (baldur+0x1C88, screen world+0x13E) sets the response override to 4
  (0x84CFDA) and the answer to 0.
- Save/load mode (0x437B64-0x437B80): `m_gameSave.m_mode` (game+0x43E2) equal
  to 0x182 or 0x502 sets the answer to 0.
- (0x437B82-0x437BC3) When `m_multiplayerSettings.m_bHostPermittedDialog`
  (game+0x1C58 = settings+0xA6) is TRUE, or the answer is already not 1, the
  answer becomes 3 (0x84CFD9) while `m_bInHandleBlockingMessages`
  (baldur+0x488E = `m_cBaldurMessage`+6) is TRUE, else 0. Otherwise
  `cGame->GetArea(areaName)` (0x5B7510, with the second wire string) is
  checked: a loaded area answers 3.
- (0x437BCB-0x437BD3) A non-`-1` override replaces the answer.
- Reply (0x437BD5-0x437C6A): `CreateBuffer(1)`, the answer byte, and
  `SendSpecificMessage(sPlayerName, SEND_GUARANTEED (0x200 at 0x85E664),
  MSG_TYPE_LEAVEAREALUA (88 at 0x84CFD3),
  MSG_SUBTYPE_LEAVEAREALUA_PERMIT_REPLY (114 at 0x84CFD5), pMessage, 1)`
  (0x7A84F0).
- Transition (0x437C6D-0x437CBB): only when the answer is 1, copy the two
  strings and call `cGame->sub_5C3B20(objectId, x, y, direction, areaName,
  parchment)` (the 4001-byte `FUN_005c3b20`). The two by-value `CString`s are
  the area name (second wire string) and the parchment (first wire string), in
  that order.
- Return TRUE (0x437CE9); the NULL reply buffer path returns FALSE.

## Notes

The port is `CBaldurMessage::OnLeaveAreaLuaRequestToServer` in
`src/CMessage.cpp`, plus the new wire constant
`MSG_SUBTYPE_LEAVEAREALUA_PERMIT_REPLY = 114` (0x84CFD5). It keeps the two
entry guards, the payload layout, the remote-object Find, both settings counts
and feedback strings, the paused/save-mode/dialog/blocking/loaded-area answer
computation with the 4/3/0 codes, the 1-byte LEAVEAREALUA 88/114 reply, and the
`sub_5C3B20` transition call behind the code-1 gate.

The handler needed one callee fix: the already-ported
`CMultiplayerSettings::sub_518560` compared its `unsigned char` array against
`-1`, which is always true, so every slot was counted and the request was
always denied with the inventory feedback. It now compares against `0xFF`, as
the original's byte compare does (see docs/evidence/518560.md).

`sub_5C3B20` (4001 B, the actual area transition: area load, party move and the
LEAVEAREALUA 88/65 broadcast) is **not ported**; this branch declares it, adds
a no-op stub with `// TODO: 0x5C3B20` and calls it, so the permit handler's
decision and reply are complete and the transition becomes a drop-in later
(docs/evidence/5C3B20.md).

Proof: `tests/test_network.cpp`, `[msg][network]`, no `IWD2_DATA`:

- `... refuses without a session or a host` (the two entry guards);
- `... answers the permit request`: a zeroed `CBaldurChitin`/`CInfGame`/
  `CScreenWorld`, the remote array missing and the settings driven directly;
  checks the allow answer (reply `0xFF, 88, 114, 1` in
  `CNetwork::STATIC_MESSAGE_BUFFER`), the inventory feedback (0), the level-up
  feedback (0), the paused override (4), the save/load mode (0), the
  host-permitted dialog (0) and the blocking-message busy code (3).

The feedback `FeedBack` call, the loaded-area answer 3 and the transition need
a real sprite/area, hence the read-only kind.

for the Ghidra decompilation; port `CInfGame::sub_5C3B20`; a party/area fixture
for the feedback and loaded-area arms; structural parity.
