# 0x5820B0 CProjectileWallOfMoonlight::OnArrival

The shared arrival of the two stationary walls: the same address is slot
0x70 of both vtables, verified by reading the pinned exe (0x8514CC+0x70 and
0x851664+0x70 both hold 0x5820B0). It is reached virtually from
`CProjectileSingleTarget::AIUpdate` (0x578AB0, the `OnArrival()` call in
the arrival branch), so callgraph.tsv has no direct caller entry.

Read against the complete annotated disassembly below (local read-only run
of tools/parity/annotate.py on the pinned vanilla IWD2.exe, MD5
200f038bec3ed50a964d68b3f0f1f0e7; the Linux parity host was down).

## Port

`src/CProjectile.cpp`, identical bodies in `CProjectileWallOfMoonlight::OnArrival`
and `CProjectileWallOfFire::OnArrival` (the exe folds one function onto
both vtables; the two class methods carry the same 0x5820B0 marker, the
0x4016D0 precedent for ICF-folded duplicates):

1. `if (field_2B2 != 0) { field_2B2 = 1; field_1DE = TRUE; return; }`
   — the guard at 0x5820B7-0x5820BF and the early exit at 0x5821F6-0x58220C.
   Any non-zero value is treated as arrived, and the early exit rewrites
   the byte to exactly 1 and raises field_1DE. It does not touch the sound.
2. `m_loopSound.SetResRef(CResRef("ARE_P22"), TRUE, TRUE)` — the exe inlines
   the whole CResHelper<CResWave,4>::SetResRef body at 0x5820C6-0x5821B2:
   `cResRef != "ARE_P22"`, then if `pRes != NULL && cResRef != "" &&
   bLoading` a `CRes::CancelRequest`, then `GetResObject("ARE_P22", 4, TRUE)`;
   on a hit `pRes` is stored, `bLoading = TRUE`, `CRes::Request()` runs and
   `cResRef = "ARE_P22"`; on a miss both are cleared. The port calls the
   in-tree template one time, which is exactly that body (src/CRes.h).
   The request sequence and the ARE_P22 resource id are therefore
   preserved; no private STL/CRT routine is ported.
3. `m_loopSound.SetFireForget(TRUE)` (0x7A8F60, push 1), then
   `m_loopSound.SetChannel(15, reinterpret_cast<DWORD_PTR>(m_pArea))` —
   the exe pushes 0xF then `[esi+0xEA]`, which is the CProjectile shadow
   `m_pArea` (+0xEA), not CGameObject's +0x12 area; then
   `m_loopSound.Play(m_pos.x, m_pos.y, 0, FALSE)` — pushes bReplay=0,
   z=0, y=[esi+0xA], x=[esi+6], so m_pos at +6/+0xA.
4. Both ends latch `field_2B2 = 1` and `field_1DE = TRUE`.

Resource release is the in-tree `CSound`/`CResHelper` destructor, which
matches the exe's teardown of the loop sound (the 0x5803E0 / 0x581DD0
scalar dtors destroy this CSound first). This function releases nothing
itself and does not stop the loop on a second arrival.

## Callers

- No direct caller (callgraph.tsv has no row). Reachable through virtual
  slot 0x70 from `CProjectileSingleTarget::AIUpdate` 0x578AB0.

## Callees

- 0x78A990 `CResRef::CResRef`, 0x78AB40/0x78ABB0/0x78AC30/0x78AD40
  `CResRef` comparisons/assignments — the resref temporary and the
  inlined helper's traffic.
- 0x786DF0 `CDimm::GetResObject` — the ARE_P22 lookup (wave type 4).
- 0x77E370 `CRes::CancelRequest`, 0x77E610 `CRes::Request` — the inlined
  helper's cancel and auto-request.
- 0x7A8F60 `CSound::SetFireForget`, 0x7AA4B0 `CSound::SetChannel`,
  0x7A9DB0 `CSound::Play` — the four named calls in the body.

## Notes

- The bytes at +0x2B2 and +0x1DE are wall-class members: `field_2B2` is
  cleared by both wall ctors (0x5802B0 / 0x581CA0) and `field_1DE` is
  cleared by both (the moonlight ctor also clears +0x2A0, the fire ctor
  leaves it). The port keeps those member names and offsets as they were.
- The first arrival's loop is fire-and-forget on channel 15 of the
  projectile's own area pointer; the second arrival never re-plays it.
- Tests: `tests/test_wall_projectile.cpp`. A bare CChitin with a synthetic
  key table holding ARE_P22 (wave type) drives the full helper request
  path without the install: the first arrival leaves cResRef
  "ARE_P22", a live CResWave and bLoading TRUE; a second arrival keeps
  the same CResWave/resref; an already-arrived byte (7) is rewritten to 1
  and leaves the sound untouched. The Wall of Fire case repeats the same
  body assertion on its class. The mixer is not initialised (no audio
  device), so SetFireForget/SetChannel/Play take their early-return paths
  and the channel/loop side effects are not observed; a real mixer case is
  left to a follow-up.
- Untested: a live mixer's channel binding and actual looping playback, a
  failed-mixer/non-null GetResObject branch with a real ARE_P22 wave file,
  and the engine's virtual dispatch context (the tests call the function
  directly on a constructed wall).
- Not in scope: `CGameAIBase` 0x460000-0x467FFF (untouched), MAP/recovery
  generation (none), and no private STL routine was ported.
