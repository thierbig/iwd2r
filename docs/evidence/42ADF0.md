# 0x42ADF0 CBaldurMessage::OnResourceRequest

The host's receive of a client's resource hand-off (survey-121 row 2, PR group
G20).

## Identity / route

- The exe's receive dispatcher is `CMessageHandler::AsynchronousUpdate`
  (0x4EE020, ported). Its `MSG_TYPE_RESOURCE` (82) arm at 0x4F3BE7 keys on the
  subtype byte and indexes the jump table 0x4F4CBC through 0x4F4CD0: subtype
  0x43 (67) -> 0x4F3C38 -> **0x42ADF0 this function** (ret 0xC).
- The survey calls it OnResourceRequest; there is no export name (Ghidra
  `FUN_0042adf0`). It is the host-side counterpart of the ported
  `DemandResourceFromServer`/`sub_42A3F0` pair: the demand reply (subtype 82)
  carries host -> client, this request (subtype 67) carries client -> host.

## Port

`BOOLEAN OnResourceRequest(INT nMsgFrom, BYTE* pData, DWORD dwSize)`:

- Guard: `g_pChitin+0x1032` (session open) and `+0x1033` (hosting) must both be
  set; otherwise FALSE. It is the host's receive.
- Payload after the 3-byte spec header: `{BYTE nLength; char sResRef[nLength];
  UINT nType; DWORD nSize; BYTE data[nSize]}`.
- The data is copied into `CreateBuffer(nSize)` (the 0x4000 static buffer
  0x8D8FE4, else heap; NULL -> FALSE).
- Only `nType == 1015` (CResWorldMap) and `nType == 1014` (CResStore) are
  written: a `CResHelper<T, nType>` does `SetResRef(CResRef(sResName), TRUE,
  TRUE)` and `GetRes()->Write(CInfGame::m_sTempDir, pBuffer, nSize)`; every
  other type is accepted and dropped. The buffer is released and TRUE returned.

### Survey row 57 (0x43E190) resolution

0x42A3F0 (the demand's reply processor) is ported (src/CMessage.cpp), so the
dependency is available. 0x43E190 turns out not to be a separate handler or
helper to port: it is the out-of-line
`CResHelper<CResStore,1014>::SetResRef` instantiation (the store arm's
GetResObject/Request/CancelRequest/ReleaseResObject and CResRef comparisons),
exactly as docs/evidence/42A3F0.md records and as this function's store arm
shows. The tree's `CResHelper<T,nType>` template (src/CRes.h) provides that
method and the port of 0x42A3F0 already calls it for 1014, so row 57 is
covered by the template, not a port target (a bespoke port would duplicate a
compiler-generated template instantiation). No 0x43E190 evidence file is
needed; this note and 42A3F0.md's callee notes are the evidence.

## Callers

- 0x4F3C38, the subtype-67 arm of `CMessageHandler::AsynchronousUpdate`
  (0x4EE020). The network dispatch block is omitted in the port (single player,
  docs/adr/0002-single-player-only.md), so the handler is a callable method like
  every other receive handler in this layer.

## Callees

- 0x77E690 CRes::Write (through the two CResHelper instances)
- CResHelper<CResWorldMap,1015>/<CResStore,1014>::SetResRef and the CResRef
  shapes (see the waiver)
- 0x7FC95B/0x7FC984 operator_new/operator_delete (CreateBuffer/DestroyBuffer's
  heap branch)

## Notes

- fd row 2 identity confirmed: the type byte is the resource type of the
  records being handed over, and the destination is
  `CInfGame::m_sTempDir` (CInfGame+0x4208) - the same temp folder the demand
  reply processor (0x42A3F0) writes to for the bSaveToTemp case.
- The exe does not bounds-check `nLength`/`nSize` against `dwSize`; the port
  keeps that shape (the dispatcher owns the buffer size).
- There is no labelled exe constant for subtype 67 in the resource family (the
  dispatcher uses its jump table); tests spell the literal with a comment.
- Exe md5 200f038bec3ed50a964d68b3f0f1f0e7.
