## Notes

Ported from the Ghidra listing and the disassembly (0x780CF0-0x7810E7, `__cdecl`, the nine
arguments pushed right to left): the line-splitting loop of `CUtil::SplitString`, including its
double-byte (DBCS) handling.

With `g_pChitin->field_1A0` (the DBCS flag, CChitin +0x1A0, a #guess) zero the loop is the obvious
one: for every byte of the current line it checks for `\r`/`\n` (split there, `Mid(nIndex + 1)` to
the next line and `Left(nIndex)` to this one, the remainder condition at 0x78106C), remembers the
last space, measures `GetStringLength(Left(nIndex + 1), TRUE)`, and splits when the width passes
`nLineLength` (or reaches `nSuggestedSplitLength` at a space). With the flag set:

- a lead byte (`IsDBCSLeadByte`, KERNEL32, call at 0x780E04) is measured and advanced as a pair:
  `Left(nIndex + 2)`, and `nIndex += 2` (0x780DF8-0x780E25), so the loop never stops on a trail
  byte; the pair's frame is chosen by the trail byte inside `CVidFont::GetStringLength`
  (movzx at 0x792E12);
- the line budget loses 10 px: `nLineLength - 10` in the signed compare (0x780E60-0x780E80);
- at a split the line still breaks *before* the lead byte (`Mid(nIndex)`/`Left(nIndex)`), so the
  whole pair moves to the next line (0x780F54-0x780F93; the two copies of that code — one after
  the DBCS test, one after it — are the same operations).

The split pick is `bDivideWords || nSpace == -1 ? nIndex : nSpace` (0x780EE4-0x780F51). The
dismantled-byte reads (`GetAt(index)` past a one-character string when measuring a lead alone) are
the font's own behavior, not this function's. Nothing draws `rand()`.

The flag's off arm is the same on both sides; the on arm cannot be oracle-tested on a Western rig
(`IsDBCSLeadByte` uses the ANSI code page, so the original sees no lead bytes while our shim always
answers FALSE unless a test installs a table).

## Oracle

`util/split_string` (oracle/cases/ui_misc.cpp) covers the single-byte arm: a synthetic one-frame BAM
(5x7) parsed by our `CResCell`/`CVidFont`, the original's font and cell as zeroed blocks with the

`CVidFont::GetStringLength` (0x792D40) takes the BAM path; `bDemanded` is TRUE, so no resource
manager. The source and output CStrings are the original's own (constructor 0x7FCC88, length at
data-8). Fixed and random inputs sweep the empty/one-line/multi-line cases, `\r`/`\n`, spaces,
high bytes, `nLineLength` 0-40, `nMaxStrings` 0-5, `bDivideWords`, `bCheckRemainderForNewLine` and
`nSuggestedSplitLength`; the case compares the returned line count and every line.

The double-byte arm is the unit test `util: SplitString keeps a double-byte pair together and
budgets 10 px less` (tests/test_ui_misc.cpp): a 256-frame BAM makes frame 0x40 ('A') 100 px and
frame 0 5 px, and the compat lead-byte table (`iwd2r_SetTestLeadBytes`, platform/win32_stubs.cpp)
makes 0x81 a lead byte, so `\x81A` is one 100 px pair: with the flag on and a 5 px budget it moves
to the next line whole (`""`, `"\x81A"`), while a loop that stopped on the trail would break it into
`"\x81"`, `"A"`; the same test pins the 10 px budget with plain ASCII and the single-byte arm.
