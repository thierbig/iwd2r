## Notes

Identity: the survey's row 105 lists 0x50D290 as
`CMessageSpriteUpdate::MarshalMessage`, but the body and the vtable say
otherwise. Vtable 0x84D034 (subtype 57, CMessageSpriteUpdate) has
MarshalMessage at slot 0x10 = 0x50C550 (a function Ghidra did not export, so
it is absent from functions.tsv and from the survey) and UnmarshalMessage at
slot 0x14 = 0x50D290, the address documented here; slot 0x18 is Run
(0x50D6F0). The decompile reads the wire into the message: it resolves the
target through the remote object array (a failed Find returns FALSE and
leaves the message untouched) and decodes the field-group mask at +0xB,
then only the groups the mask marks present, in the exe's order: area name
(0x400), sequence (0x100), position (0x2), facing (0x200), general state
(0x4), the 256 spell states (0x8000), base/derived skills and field_106
(0x10000), fade speed (0x1000), translucency (0x4000), the 32 visual
effects (0x2000), hit points (0x8), base-stat flags (0x800), the AC and
field_64..field_6A block (0x10), enemy/ally/morale (0x40), level-up and the
HP/CON bonus (0x80), the portrait icon list (0x20, count then ids), and the
path/current path/destination/move scale (0x1); every path ends with the
sprite's bool byte at field_85. No dwSize check exists in the body (the
decompile ignores the argument).

Not executed: no received message reaches it in the single-player build; the
test calls it directly with a hand-built packet. No oracle case or replay.

The Marshal half (0x50C550, ~3.4 KB) is not ported: it is a differential
encoder that compares the message against CGameSpriteLastUpdate,
the sprite's 0xFC-byte last-sent shadow record, and writes only the groups
that differ, updating the shadow as it goes. The tree's CGameSpriteLastUpdate
declares only its last member (m_bFullUpdateRequired), so porting it needs
that class modelled first; this is a follow-up row.
