# iwd2r

iwd2r (Icewind Dale 2 Resurrected) is a cross-platform decompilation project of the Icewind Dale II engine. It builds natively on Linux, Windows and macOS (Apple silicon), runs the original simulation underneath, and is meant to grow a high-fidelity renderer with a runtime toggle back to the classic 2D look and the IWD2EE mod built in.

**Want to help?** The recovery runs as batches of functions measured against the original game; [Contributing: running the recovery pipeline](#contributing-running-the-recovery-pipeline) lists what you need (a Windows 11 PC with the game, WSL2, and Claude Code for the workers, on an Anthropic subscription or on Z.ai's cheaper GLM plan), how a batch is cut, checked and landed, and the house rules. Readings of single functions, oracle cases for the rows no scenario reaches, and new game scenarios are the easiest places to start.

## What this repository does not contain

- No game content.
- No original binary.

Bring your own copy of Icewind Dale II: Complete from GOG. The DRM-free GOG version is the reference. That is all a player needs: IWD2EE is part of iwd2r's own source, and its edits to the game's files are applied on the player's machine.

### Roadmap

In this order, because each step is what makes the next one verifiable:

1. The engine runs the game correctly: project 3 to its end, every function checked against the original before anything is changed.
2. Absorb the parallel recovery (project 7), and use the two independent recoveries to cross-check each other.
3. Presentation ([the HD plan](docs/hd-plan.md)): the SDL3 GPU presenter draws the world from an atlas, fog as a texture, HD UI and sprites from packs the player installs in `override/`, zoom, and later lighting over the same pre-rendered scenes, with the original look one toggle away. A 2.5D remaster in the Pillars of Eternity sense, not a 3D one.
4. Native IEex layer and Lua API (project 5), so IWD2EE runs without an injected DLL.
5. Fixes to original bugs, 3e rule corrections and additions, and quality-of-life features, each as a switchable option so vanilla stays available for comparison. WeiDU mods and the `override/` folder keep working as they do today.

Where the recovery stands (October 30): about 1,650 game functions (roughly 500K bytes of code) have no port yet; the other unrecovered functions the Recovery status counts are statically linked MFC and C runtime code, which our platform layer replaces rather than ports. They are worked in three streams at once: the import of the parallel recovery's bodies (above), areas taken by contributors (the next ones: the video layer's largest unported functions, then the multiplayer message layer), and batches of the small functions. Verification against the original runs behind them, scenario by scenario.

Engine sites that still truncate pointers to 32 bits on 64-bit targets are listed for project 3 in [docs/64bit-cast-sites.md](docs/64bit-cast-sites.md).

## Build

Requires CMake 3.28. Presets: `linux-gcc`, `linux-clang`, `macos-clang`, `windows-msvc-x64`, `windows-msvc-x86`.

Ubuntu packages:

```
build-essential cmake ninja-build clang pkg-config libasound2-dev libpulse-dev libx11-dev libxext-dev libxrandr-dev libxcursor-dev libxfixes-dev libxi-dev libxss-dev libxkbcommon-dev libdrm-dev libgbm-dev libgl1-mesa-dev libegl1-mesa-dev libwayland-dev libdecor-0-dev libudev-dev libdbus-1-dev libpipewire-0.3-dev
```

Windows: Visual Studio 2022 and CMake.

macOS (Apple silicon): the Xcode command line tools (`xcode-select --install`) for clang, and `brew install cmake ninja`. The engine builds and its tests pass there, with and without game data (macOS 27 on arm64, reported by contributors; `tools/gates.sh` builds the Linux presets only). Playing on macOS has not been tried beyond the tests, and the verification pipeline (the oracle, replays, Windows Sandbox and the batch driver) still needs Linux or WSL and a Windows host; macOS can build the vanilla game copy from GOG's installers ([below](#building-the-copy-from-gogs-installers)).

SDL3, miniaudio and Catch2 are fetched by CMake at pinned versions.

```
cmake --preset linux-gcc && cmake --build --preset linux-gcc && ctest --preset linux-gcc
```

On macOS, the same three commands with `macos-clang`.

## Run

### Play

From WSL, one command syncs the working tree to a Windows checkout, builds it with MSVC and opens the game window on the desktop. Each worktree has its own checkout: `%USERPROFILE%\iwd2r-build` for the `first` worktree, `%USERPROFILE%\iwd2r-build-<worktree folder>` for any other, or `$IWD2R_WIN_CHECKOUT` when set:

```
python3 tools/play.py
```

To try it at your desktop resolution with the UI drawn at 2x, the world at 1x, TrueType text and sound:

```
IWD2R_DESKTOP_OK=1 python3 tools/play.py --sound --resolution desktop --scale 2 --set "Program Options/World Scale=1" --set "Program Options/Text Renderer=scalable"
```

`IWD2R_DESKTOP_OK=1` is the opt-in for a window on your desktop: without it `play.py` refuses, because the agents that drive the game run it headless or in a sandbox, where a stray click would land in their run. The run needs the vanilla copy that `python3 tools/oracle.py vanilla` builds from a GOG install (see below).

An automated check on Linux, headless, driven by an input script that takes screenshots:

```
python3 tools/play.py --linux --headless --script scenarios/options.txt
```

Options are flags, never INI edits: `--windowed` (default) or `--fullscreen`, `--resolution W|desktop` (default 800), `--scale 1|2|3|4|auto` (the `Scale` key), `--set "Section/Key=Value"` for anything else (`--set "Program Options/Height=1080"` for the height), `--frames N`, `--data PATH`, `--shot-presented` (each screenshot also writes `NAME-presented.png`, the frame as the presenter drew it, through `IWD2R_SHOT_PRESENTED`). They reach the engine through `IWD2R_INI_OVERRIDE`. Each run writes `runs/<YYYYMMDD-HHMMSS>/` with `log.txt` (the game's output), the screenshots, `ini-backup/` and `summary.txt`. Every `*.ini` in the install is backed up before the run and restored byte-identical afterwards, also on Ctrl-C, because the engine rewrites `icewind2.ini` on exit. Script commands (`wait`, `click`, `rclick`, `move`, `key`, `type`, `shot`, `quit`, `origin`) are documented in `platform/script.h`; the starter scenarios are in `scenarios/`. Click and move coordinates are in the original's 800x600 UI by default (`origin ui`): at larger sizes the UI is centred, and the engine (or the real-input driver) adds the centring offset, so one scenario clicks the same buttons at every resolution; `origin screen` switches to screen pixels.

The game data is a vanilla copy by default, because the project verifies against vanilla first: Linux runs read `${IWD2R_HOME:-~/.local/share/iwd2r}/game` (as `tools/gates.sh` does), and Windows runs (the host build and `--vm windows`) read `%USERPROFILE%\iwd2r-oracle\game` (`$IWD2R_WIN_HOME/iwd2r-oracle/game` from WSL, default `/mnt/c/Users/<your user>`; see `tools/winhome.py`), the verified copy that `python3 tools/oracle.py vanilla` builds and marks with `vanilla.ok`. Make the Linux copy from it with `rsync -a --exclude temp --exclude cache --exclude tempsave --exclude mpsave --exclude ScrnShot /mnt/c/Users/<you>/iwd2r-oracle/game/ ~/.local/share/iwd2r/game/`. When the copy is missing, `play.py` stops and says how to make it. Your own install (for example one with IWD2EE) is never the default: point a run at it with `--data PATH` or `IWD2_DATA`, which take precedence.

#### Building the copy from GOG's installers

Without a Windows install, macOS and Linux build the same copy straight from GOG's installers:

```
python3 tools/oracle.py vanilla-gog ~/Downloads/icewind_dale_2_complete_en_v2_01_16618.pkg
python3 tools/oracle.py vanilla-gog "$HOME/Downloads/setup_icewind_dale_2_2.01_fixes_(77030).exe"
```

The `.pkg` needs macOS's `pkgutil`, or `xar`, `gzip` and `cpio`; the Windows installer needs `innoextract` (`brew install innoextract`, `apt install innoextract`) with its `-1.bin` beside it. It writes `${IWD2R_HOME:-~/.local/share/iwd2r}/game` (`--game DIR` for another folder, `--rebuild` to replace the copy), leaves out the installer's redistributables, support files, caches and GOG extras, names the exe `iwd2.exe`, points `icewind2.ini`'s `[Alias]` paths at GOG's install path (the engine re-roots every drive path into the data root, `platform/fs.cpp`) with `Resolution=800`, and writes `vanilla.ok` only after the checks `oracle.py vanilla` makes pass, naming the installer and its SHA-256.

#### Desktop runs

A run that would open a window on your desktop (`--windowed`, `--fullscreen`, or a Linux run with a display) refuses unless `IWD2R_DESKTOP_OK=1` is set. Automated runs use `--headless`, `--vm linux` or `--vm windows` instead, so an agent's run never steals focus from you. To play yourself:

```
IWD2R_DESKTOP_OK=1 python3 tools/play.py --windowed --data "/mnt/c/Games/Icewind Dale II" --sound
```

#### Real-input runs (`--vm`)

`--vm` runs the same scenario files with genuine operating-system input in an isolated display, so nothing appears on your desktop: mouse and keyboard events travel OS → SDL → window shim → engine, as a player's do, and the in-engine script (`IWD2R_SCRIPT`) stays off.

```
python3 tools/play.py --vm linux --script scenarios/options.txt
python3 tools/play.py --vm linux --suite --jobs 3
python3 tools/play.py --vm all --suite
```

- `--vm linux` builds `linux-gcc`, starts `Xvfb :N` (N from 90 up) at the output size (the requested resolution; its height from `--set "Program Options/Height=H"`, else 4:3 for 800, 1024, 1600 and 2048, else 16:9; `--resolution desktop` is 1920x1080), runs the game windowed on it with the X11 video driver and drives it with xdotool (`tools/realinput.py`). One-time setup: `sudo apt-get install -y xvfb xdotool imagemagick`.
- `--vm windows` runs each scenario in a fresh Windows Sandbox (`tools/winsandbox.py`, `tools/sandbox/driver.ps1`): the worktree's MSVC build (with the MSVC runtime DLLs copied next to `iwd2r.exe`), a copy of the game data in `%USERPROFILE%\iwd2r-vm\game`: by default the vanilla copy `%USERPROFILE%\iwd2r-oracle\game`, never the install. `%USERPROFILE%\iwd2r-vm\game.source.json` records the source path and the SHA-256 of its `vanilla.ok`; a cache from another source (an older cache copied from the install, a rebuilt vanilla copy, or `--data` pointing elsewhere) is deleted and copied again from scratch, a changed `CHITIN.KEY` of the same source is resynced with rsync, and the check runs before every scenario under the sandbox lock, the copy also holding the vanilla copy's `vanilla.lock`; the source folder is never mapped, networking off. The driver uses `SendInput` and captures the screen with System.Drawing. One-time setup, in an admin PowerShell, then reboot: `Enable-WindowsOptionalFeature -Online -FeatureName Containers-DisposableClientVM -All`. Only one sandbox runs at a time, so `--jobs` does not apply, and each scenario holds `%USERPROFILE%\iwd2r-vm\sandbox.lock`, so a run from another worktree waits.
- `--vm all --suite` runs the suite on Linux, then on Windows when the sandbox is available, and prints both tables.
- `--suite` runs every `scenarios/*.txt`; `--jobs N` (default 1) runs that many Linux scenarios at once, each on its own display and CPU core and in a private view of the install (links to its files, with its own `cache`, `temp`, `tempsave` and INI copies, since parallel games would otherwise race on them); `--timeout S` bounds every scenario, else a scenario's own header line `# timeout: S` (walk_and_talk's is 420), else 180 s. The host waits for the sandbox that long plus 120 s.

How commands map to input: `click`/`rclick`/`move` move the real pointer to the game coordinates (UI coordinates plus the centring offset, times the scale: the window's client area is the game screen scaled up) and press the button for 2 frames; each phase of a click or key (the move, the press, the release) also lasts until the engine has read the mouse buttons again (at most 1 s), because the engine reads only "down" and "pressed since the last read" once per AI update, and a release and the next press with no read between them would look like one press (a lost double click); `key` presses a real key; `type` types real key strokes; `wait N` lasts N/30 s and until the engine has presented N frames, so slow screen loads do not desynchronise the script; `shot NAME` captures the display (`NAME-screen.png`, the OS view with the engine-drawn pointer) and the engine's framebuffer (`NAME.png`), with `--shot-presented` also the presenter's output (`NAME-presented.png`: the window-sized frame after scaling, region composition and the filter; at `Scale=1` with the nearest filter it is byte-identical to `NAME.png` under either presenter); `quit` closes the window as a window manager's close button does (`WM_DELETE_WINDOW` on X11, `WM_CLOSE` on Windows) and confirms the engine's "quit?" message box with Return. The framebuffer shots and frame counts come from a small control channel: with `IWD2R_CONTROL_DIR` set, the engine answers `shot-NAME.req`, `frames.req`, `input.req` (its mouse-button reads) and `state-NAME.req` (a state dump, `checkpoint-NAME.json`) files in that folder once per presented frame and after each mouse-button read; it injects no input. At every `checkpoint NAME` line the drivers ask for that state dump.

What lands in `runs/<YYYYMMDD-HHMMSS>/` (one subfolder per scenario with `--suite`, under `linux/` and `windows/` with `--vm all`): `driver.log` (every action with timestamps), `log.txt` (the game's output), `script.txt`, `actions.json` (the parsed scenario), both kinds of screenshots and `summary.txt`; Linux runs add `xvfb.log` and `ini-backup/`, Windows runs `run.wsb`. A suite writes `suite.txt` with the table (scenario, exit code, duration, screenshot count). The exit code is the game's, 124 on a timeout, or non-zero when the driver failed; a scenario that exits 0 but did not write every `shot NAME` as `NAME.png` (and `NAME-presented.png` with `--shot-presented` on Linux) fails with code 1 and "missing shot NAME", and so does one without a state dump at a checkpoint or whose dumps disagree with `scenarios/NAME.expect.json`: what the original reached at each checkpoint (the screen, the character generation choices, the area, the dialog and the doors), made from the original's replay dumps with `python3 tools/realinput.py expect scenarios/NAME.txt runs/<stamp>/original` (`checkpoints.txt` lists every difference). In Windows Sandbox the driver disables the logon task whose console window took the foreground about 30 s after logon, and fails the run when another process takes the foreground from the game while the scenario runs; Xvfb, the game and the sandbox are closed on every exit path, including Ctrl-C.

#### Pending scenarios

`scenarios/pending/` holds scenarios our engine cannot finish yet, such as a milestone's exit scenario before it passes (M3's `first_fight.txt` was one until it matched the original). They are recorded in the original (`python3 tools/oracle.py replay record scenarios/pending/NAME.txt`) and run by path, but `--suite` takes only `scenarios/*.txt`, and the integration gate compares only those. A pending scenario moves to `scenarios/` when it passes, with its `NAME.expect.json`.

#### Parallel work streams

`tools/worktree.sh new <stream>` creates the worktree `~/iwd2-re-worktrees/p3-<stream>` (`$IWD2R_WORKTREES`) on branch `p3/<stream>` from `first` and prints its path; `tools/worktree.sh done <stream>` removes it and deletes the branch once the branch is merged into `first`, and refuses otherwise. Each worktree builds on Windows in its own folder (`%USERPROFILE%\iwd2r-build-p3-<stream>`). Shared resources are locked (`tools/filelock.py`): the Ghidra project (one headless run at a time), the vanilla copy's replays and its build (`%USERPROFILE%\iwd2r-oracle\replay.lock`, `vanilla.lock`) and Windows Sandbox; a command that has to wait says so after 5 seconds.

#### The batch driver

Recovery and adjudication run as batches of 20 functions through one program, `tools/wave.py run` ([docs/wso/README.md](docs/wso/README.md), "Running the batches"). Per batch it cuts a branch and worktree from `first`, triages the rows that need no reading, renders a brief with a context bundle per function, runs one headless worker, runs the mechanical checks (one fix round), dispatches a reviewer only when a verdict could change engine code or a seeded draw picks the batch, runs the gate, fast-forwards `first`, pushes both refs and appends a templated ledger entry. Workers come in pools that run the same work: `--pool glm:1` (GLM Flash through the `claude-glm` wrapper), `--pool claude=claude:sonnet:1` (Claude), or both on the same queue, each with a credit cap. One gate runs at a time (`.gates.lock`); a 429 parks the driver with its work committed.

The rules are code, not prose. The close refuses a verdict for the fork or for neither that rests only on reading the decompile; every verdict carries its case id and the gate reports how many rest on an oracle case, a replay checkpoint, a trace or a reading. A worker that cannot decide a row leaves it under `## Undecided`; the driver moves it to `docs/wso/probe-list.json`, and `tools/wave.py resolve` records it once a probe or a ruling settles it. Transcript checks refuse a sandbox launch outside the house runners and a whole-file read of a bundled function. Exceptions (a second failed check, a second blocking review, a worker without a report) go to one human-watched session where rulings are made and recorded in the ledger; nothing asks the worker to decide policy.

Changes to the tooling itself go through a written spec and plan under `docs/superpowers/`, then subagent-driven development: one implementer per task, a reviewer on a stronger model after each, fix rounds with scoped re-reviews, and a whole-branch review before the merge and gate.

Everything a pipeline run needs on the machine — the sandbox, the game copies, Frida, the worker pools, the locks — is listed under [Contributing: running the recovery pipeline](#contributing-running-the-recovery-pipeline).

### Manual

Point the engine at your install with `IWD2_DATA`:

```
IWD2_DATA=/path/to/Icewind\ Dale\ II ./build/linux-gcc/iwd2r
```

On Windows (Command Prompt, then PowerShell):

```
set IWD2_DATA=C:\Games\Icewind Dale II
$env:IWD2_DATA = "C:\Games\Icewind Dale II"
```

Alternatively, place a link named `IWD2` next to the executable or at the repository root. The directory must contain `CHITIN.KEY`. The engine writes saves, cache and INI files into it exactly as the original does.

Screen size, in the `[Program Options]` section of `icewind2.ini`:

- `Resolution` is a width in pixels, such as the 1366 IWD2EE sets, or `desktop` for the primary display's native size.
- `Height` (optional, an iwd2r key) is the height. Without it, 800, 1024, 1600 and 2048 take their original 4:3 heights (600, 768, 1200, 1536) and any other width takes the desktop's aspect (1366 on a 1920x1080 desktop is 1366x768).
- `Scale` (optional, an iwd2r key, default 1) is 1 to 4 or `auto`: the engine runs at the requested size divided by the scale, and every frame is scaled up with nearest-neighbour filtering, windowed and fullscreen; the mouse is mapped back. `auto` picks the largest factor that keeps the engine's height at least 720 (1920x1080 runs at 1; 2560x1440 at 2, inside 1280x720; 3840x2160 at 3, inside 1280x720). With `World Scale` it is the UI's scale only.
- `World Scale` (optional, an iwd2r key, default the value of `Scale`) is 1 to 4 or `auto` (1 when `Scale` is 2 or more, else `Scale`); a value above `Scale` is taken as `Scale`, so the UI is never smaller than the world. The engine runs at the requested size divided by `World Scale`, so the world is drawn at that scale, while the UI panels keep their pixel size and are shown at `Scale`. On the world screen the bottom panels get a band `max(Scale, World Scale) / World Scale` times their height and the world viewport ends above it; every other screen (start, character generation, inventory, options and the rest) shows its 800x600 UI centred. The UI scale is lowered where the UI would not fit, never below `World Scale`, with a line on stderr: on the world screen to the largest scale at which the 800-pixel-wide panels fit the width and the 284-row dialog band the height (1920x1080 at `Scale=3` shows them at 2), on the other screens to the largest at which 800x600 fits (1920x1080 at `Scale=2` shows them at 1, 2560x1440 at 2). The mouse is mapped per region, so clicks land where the panels are shown; in fullscreen the regions are letterboxed like the whole frame. `Resolution=2560`, `Scale=2`, `World Scale=1` gives the world at 2560x1440 with the UI at twice its size.
- `Presenter` (optional, an iwd2r key, default `classic`) is what shows the frames: `classic`, SDL's 2D renderer with one texture scaled nearest-neighbour; `gpu`, the SDL3 GPU presenter on Vulkan, which draws the world and the UI regions at their own scales and applies `Scale Filter`; or `auto`, which behaves as `gpu` (kept for INIs that name it). Before the game creates a GPU device in its own process it runs itself as `iwd2r --probe-gpu` in a child process (start the GPU presenter offscreen at 1x1: a Vulkan device, every filter's pipeline and one frame drawn; print `probe-gpu: ok <driver> <device>` or `probe-gpu: unavailable <reason>`, exit 0 or 1; a crash in the child prints `probe-gpu crash: ...` on stderr), because a broken Vulkan stack (Windows Sandbox's) can crash the process that loads it even when the device creation fails; only a clean `ok` lets the game create its device. A probe that fails, crashes or runs past 10 s, or a device that cannot be created, falls back to `classic` with one line on stderr (`presenter: gpu unavailable (...), using classic`; `(probe: ...)` for the probe), and so does a device lost again after its one rebuild per run. After such a loss the game stays `classic` for the rest of the run: a new window (Alt+Enter) or the hotkey does not start `gpu` again. The probe runs once per session; the Ctrl+Shift+R hotkey reuses its verdict. `IWD2R_GPU_PROBE=skip` creates the device without the probe and `IWD2R_GPU_PROBE=fail` forces the fallback (for tests). At `Scale=1` with `nearest` the two presenters show the same pixels. Windows Sandbox has no Vulkan, so `gpu` and `auto` show `classic` there.
- Ctrl+Shift+R switches the presenter between `classic` and `gpu` while the game runs and prints the one now active on stderr (`presenter: gpu`); the engine does not see the key. When `gpu` cannot start it stays on `classic`; switching goes through the same child-process probe (its verdict kept for the session), so a Vulkan driver that crashes when probed cannot take the game down; the first switch to `gpu` in a session runs the probe, which takes about 150 ms (up to its 10 s limit on a broken driver).
- `Scale Filter` (optional, an iwd2r key, default `nearest`) is how the GPU presenter (`Presenter=gpu`) scales the frame: `nearest`; `sharp` (nearest at texel centres, linear within one output pixel of each texel edge); `smooth` (bilinear); `fsr`, AMD FidelityFX Super Resolution 1.0 (EASU edge-adaptive upscaling, then RCAS sharpening); or `nis`, NVIDIA Image Scaling (a directional 6-tap scaler with adaptive sharpening). Both upscalers are spatial and run on any Vulkan GPU; NVIDIA supports NIS from 1x to 2x, so its quality at `Scale` 3 or 4 is outside that range and untested; their licences are in `docs/THIRD_PARTY.md`. A region shown at one frame pixel per window pixel (the world at `World Scale=1`, or everything at `Scale=1`) is drawn with `nearest` under `fsr` and `nis` too, so the native-resolution picture is never sharpened. The classic presenter always uses nearest; it ignores `Scale Filter` and `Sharpness` (a line on stderr says so when the INI sets them under `Presenter=classic`).
- `Sharpness` (optional, an iwd2r key, default 0.5) is 0 to 1, how much `fsr` and `nis` sharpen: 0 is none, 1 the most. For `fsr` it is RCAS's linear amount (RCAS counts stops below its maximum: 1 is 0 stops, 0.5 one stop, 0 off); for `nis` it is the SDK's own 0 to 1 sharpness. Any other value uses 0.5 with a line on stderr.
- `Text Renderer` (optional, an iwd2r key, default `classic`) is `classic`, the original's bitmap fonts drawn into the engine's frame and scaled up with it, or `scalable`, which draws the text with TrueType faces at the window's resolution over the presented frame, so it stays sharp at any `Scale` and filter. Line breaks, widths, clipping and every layout keep the bitmap fonts' metrics (each character sits in the cell the bitmap glyph would have used), so only the picture changes: the engine's state, its random numbers and replays are the same in both modes. The faces are Crimson Pro Bold for the running text and captions (the NORMAL and TOOLFONT fonts), Marcellus and Marcellus SC for the carved headings (STONEBIG, STONESML, STONESM2) and Uncial Antiqua for the uncial lettering (REALMS), all under the SIL Open Font License (`docs/THIRD_PARTY.md`); light text gets a thin dark outline like the bitmap fonts' border. Drop caps and symbol fonts keep their bitmaps, and so do the tooltips (they are drawn into the FX surface, which is composited onto the screen later; stderr says so once). With `Font Name` or `Double Byte Character Support` set (the original's own TrueType path) the text stays as it was. Both presenters draw it. Screenshots (`NAME.png`) are the engine's frame, which then lacks the text; `--shot-presented` shows it (`NAME-presented.png`).
- `Text Font Scale` (optional, an iwd2r key, default 1) is 0.5 to 2, a multiplier on the scalable text's size for reading comfort; characters wider than their cell are narrowed to fit it.
- Ctrl+Shift+T switches the text between `classic` and `scalable` while the game runs (for comparing them) and prints the one now active on stderr (`text: scalable`); the screen redraws its controls in the other mode at once. The engine does not see the key.
- Development aids for the scalable text (environment variables, not INI keys): `IWD2R_TEXT_FONT_<RESREF>=<file.ttf>[@<size factor>]` draws one bitmap font (`IWD2R_TEXT_FONT_NORMAL`, `IWD2R_TEXT_FONT_STONEBIG`, ...) with a TrueType file instead of its bundled face, for comparing candidate faces without a rebuild (stderr names the file it loaded); `IWD2R_TEXT_DEBUG=1` prints one stderr line per font, colour and flags combination the capture sees: the colours it chose, the cap height and baseline it measured, and a sample string.
- The engine's screen must be at least 800x600; anything smaller is refused at start-up with a message.

At 800x600, 1024x768, 1600x1200 and 2048x1536 the layout is the original's (1600 and 2048 draw the UI double size). At any other size the 800x600 UI is centred, the stone borders are tiled over the margins, the world view spans the screen above the bottom panels and the world screen's panels sit bottom-centre. Override any key for one run with `IWD2R_INI_OVERRIDE="Program Options/Resolution=800"` (entries are `Section/Key=Value`, separated by `;`).

The game window is the engine's screen times `World Scale` (`Scale` unless set); with `Full Screen=1`, or when that is as wide as the desktop (the original's rule), it is letterboxed onto the desktop. Like the original, iwd2r pins itself to one CPU core at start-up, so expect one busy core.

Headless smoke run, which prints a framebuffer hash:

```
SDL_VIDEO_DRIVER=dummy SDL_AUDIO_DRIVER=dummy IWD2R_SMOKE_FRAMES=300 ./build/linux-gcc/iwd2r
```

## Verification

GitHub Actions is disabled while the parallel streams push often (`gh workflow disable CI`; `gh workflow enable CI` turns it back on). `tools/gates.sh` runs the same steps locally, with `--windows` for the Windows builds, and every integration into `first` runs it.

The oracle checks our engine against the original game's own code. The original `iwd2.exe` runs for real on Windows; ours runs next to it; the results are compared. A function counts as done only when it compiles, matches the original, and has an evidence file. The design is in [docs/superpowers/specs/2026-10-12-iwd2r-verification-harness-design.md](docs/superpowers/specs/2026-10-12-iwd2r-verification-harness-design.md) and the reasons for its runtime in [ADR 0003](docs/adr/0003-oracle-runtime.md). Parked items are in [docs/followups.md](docs/followups.md).

`tools/ghidra/setup.sh`, `oracle.py evidence` and `check_evidence.py` work on Linux and WSL. The runner, the vanilla copy and the replays need a Windows host with your own copy of the game, driven from WSL. Nothing from the game is committed. Results go to `runs/<YYYYMMDD-HHMMSS>/`, which is not committed either.

- **Ghidra.** `tools/ghidra/setup.sh` installs pinned Ghidra, Node.js and REA under `~/.local/share/iwd2r/`, with no sudo. `tools/ghidra/make_project.py` builds the labelled project: our `// 0xADDR` names first, then IEex's.
- **Vanilla copy.** `python3 tools/oracle.py vanilla` copies your install to `%USERPROFILE%\iwd2r-oracle\game`, runs IWD2EE's uninstaller there, and checks that `iwd2.exe` has the vanilla MD5. Your install is never changed. `--rebuild` starts over.
- **Function oracle.** `python3 tools/oracle.py build` builds the 32-bit runner. `python3 tools/oracle.py run` maps the vanilla exe into it and calls the original's functions and ours with the same inputs. `--file NAME` runs one case file from `oracle/cases/`, `--seed` and `--iterations` set the sweep, and `--selftest` checks the loader. It writes `runs/<stamp>/oracle.json` and exits 1 on any mismatch or crash.
- **Replays.** `python3 tools/oracle.py replay record scenarios/chargen_replay.txt` plays a scenario in the original with a recorder DLL and writes state dumps. `replay compare` plays it in both engines with the same seed and compares every `checkpoint` line field by field, and also every periodic dump (`frame-N.json`, every `--dump-every` frames) both sides wrote, so a state that diverges between two checkpoints fails too. Our engine runs a deterministic replay mode when `IWD2R_STATE_DUMP` names a folder. Screens compared are listed in `oracle/replay/screens.json` (`chapter`, `connection`, `create_char`, `single_player`, `world`); `oracle/replay/known_differences.json` lists accepted differences (an entry's `checkpoint` is a checkpoint name, `frame-N` for one periodic dump, or `*` for every dump). Both commands run the original inside Windows Sandbox, one fresh sandbox per recording (about 20 s more per run), so the game never takes the focus on your desktop and a stray click cannot land in a recording; `tools/sandbox/replay-driver.ps1` runs the injector there and the results come back to the same `runs/<stamp>/` folders. The original needs DirectPlay, which the sandbox ships only as stub files: the driver copies the host's 32-bit DirectPlay files (read from `C:\Windows\SysWOW64` through a read-only mapping) over the sandbox's stubs at logon, inside the sandbox only, so DirectPlay must be enabled on the host as it is for the original game. `--host` runs the original as a window on your desktop instead, for debugging the recorder. Antivirus software flags the injector (it injects a DLL into another process); with replays in the sandbox, only the function oracle's runner still runs on the host. The `rand()` call trace for divergence hunts is described in [docs/rand-trace.md](docs/rand-trace.md).
- **Evidence.** `python3 tools/oracle.py evidence 0x5845D0` drafts `docs/evidence/5845D0.md` from the Ghidra project. `python3 tools/check_evidence.py --base origin/main` fails when a changed function has no evidence file. Each file states its kind: `oracle`, `replay`, `read-only` or `trace`, and the gate reports the counts. See [docs/evidence/README.md](docs/evidence/README.md).
- **Structural parity.** `python3 tools/parity/run.py --base iwd2r/main` checks every changed function against the binary: its callees in the call graph, the string literals it references (the `strings` column, YELLOW only while its noise is measured: about 3 in 20 YELLOWs is a real mismatch today), its vtable slots, the class layout and member offsets, the address markers, plus the source lints. It runs as a gate step; the exe-based columns need the vanilla exe and the venv from `tools/parity/setup.sh`, and skip cleanly without them.
- **Annotated disassembly.** `python3 -I tools/parity/annotate.py 0x7C3140` prints one line per instruction of the function at that address (end = its `functions.tsv` size, `--end`/`--exe` override), naming each direct call/jmp target — the tree's `// 0xADDR` marker first, else the export's name, else `?` — and showing the string literal (or labelled global) any immediate or displacement points into the exe's data at, so an asm-vs-body comparison sees `" :  "` where the source must not say `" "`. Same dependencies and clean-skip behavior as the parity columns.
- **Differential Frida tracing.** `tools/frida/` hooks the same function in the original and in ours over the same scenario, records one trace per side, normalizes pointers and timestamps away and diffs the rest. The deciding case for functions that are not pure. See [docs/frida-tracing.md](docs/frida-tracing.md).

The "done" rule: every function you change under `src/` that carries a `// 0xADDR` comment needs an evidence file with an oracle case or a written reason for none. CI enforces it.

CI runs the parts that need no game data: the PE loader tests (`[pe]`), the VC6 `rand` tests (`[rand]`), the oracle generator tests (`[oracle]`), the state dump and replay tests (`[dump]`), `tests/test_tools.py` and the evidence check. The runner itself needs the vanilla exe, so it runs only on your machine.


## Contributing: running the recovery pipeline

The batch driver described under [Run](#run) runs on one Windows host driven from WSL. This section lists what a contributor needs to run that pipeline themselves; [docs/wso/README.md](docs/wso/README.md) stays the reference for the tools' behavior and every key of their state files, and [docs/evidence/README.md](docs/evidence/README.md) for the evidence files themselves.

### What you need.

- **Claude Code**, the `claude` CLI (2.1 or later), on the WSL side. Claude Code is the harness: every worker, reviewer and fix round is a headless Claude Code session (`claude -p`) that the driver orchestrates. Which model answers inside it is your choice: Anthropic's models through a normal Claude subscription or API key (`--pool claude:N`, nothing else to install), or Z.ai's GLM models through the GLM Coding Plan (`--pool glm:N`, the default here because it is cheaper; it needs the small wrapper described under Workers).
- **A Windows 11 Pro host with Windows Sandbox enabled, and WSL2 (Ubuntu).** The repository and the tools live on the WSL side; the sandbox, the oracle runner and the game run on the Windows side. One-time sandbox setup, in an admin PowerShell, then reboot: `Enable-WindowsOptionalFeature -Online -FeatureName Containers-DisposableClientVM -All`.
- The original needs DirectPlay; the sandbox ships only stub files, so the host must have DirectPlay enabled, as it is for the original game.
  The driver copies the host's 32-bit files over the sandbox's stubs at logon, inside the sandbox only.
- **A legal copy of Icewind Dale II.** The tools expect the original `iwd2.exe` at `${IWD2R_HOME:-~/.local/share/iwd2r}/vanilla/iwd2.exe` (`IWD2R_HOME` moves the whole user-local home) — `VANILLA_EXE` in `tools/oracle.py`, overridable on `run` with `--vanilla`. Its MD5 is checked against `oracle/loader/vanilla.json`, so a modified exe never becomes the oracle's truth.
- **A second copy of the game for the oracle.** `python3 tools/oracle.py vanilla` builds that copy at `%USERPROFILE%\iwd2r-oracle\game` from your install:
  - IWD2EE's uninstaller runs there, the vanilla `iwd2.exe` MD5 is verified, and the marker `game/vanilla.ok` records success — your install is never changed;
  - `--rebuild` starts the copy over;
  - `python3 tools/oracle.py run` then copies the vanilla `iwd2.exe` into the build it measures.
- The sandbox never sees your install either: `tools/winsandbox.py` keeps its own game copy at `%USERPROFILE%\iwd2r-vm\game`, filled by default from the vanilla copy, with the source and the copy's hash recorded in `%USERPROFILE%\iwd2r-vm\game.source.json`.
- **Python 3** — `python3 --version` on the WSL side. The tools import only the standard library, always run as `python3 -I`, and declare no version floor beyond your distribution's Python 3.
- **The Linux build presets** — CMake, gcc and clang, ccache optional — exactly as the [Build](#build) section describes; the gate below uses them. Engine tests always run under a memory cap (`systemd-run --user --scope -q -p MemoryMax=8G -p MemorySwapMax=0 --`), so give WSL that much headroom plus the two builds.
- **Frida inside the sandbox**, for the differential trace phase:
  - `C:\Python314\python.exe -m venv %USERPROFILE%\iwd2r-frida\venv`
  - `%USERPROFILE%\iwd2r-frida\venv\Scripts\python.exe -m pip install frida==17.24.1` (measured on Python 3.14.8; provisioning is in [docs/frida-tracing.md](docs/frida-tracing.md))
  - `tools/frida/probe.py` maps that venv, read-only, into the sandbox.
- **Ghidra, only for new decompiles.** `tools/ghidra/setup.sh` installs the pinned Ghidra 12.1.4 ([tools/ghidra/versions.json](tools/ghidra/versions.json)); evidence front matter records `ghidra_version: 12.1.4`.
- **The `rea` MCP server in `.mcp.json` is optional.** It gives an interactive Claude Code session Ghidra-backed function lookups while exploring; nothing in the pipeline depends on it. The batch workers never load it (the driver starts them with `--strict-mcp-config` and no MCP config), and every decompile in `docs/evidence/` comes from the headless Ghidra scripts under `tools/ghidra/` (`tools/oracle.py evidence`, `tools/ghidra/export_decompiles.py`).
- **Rough sizes.** The sandbox VM alone is 4096 MB (`MEMORY_MB` in `tools/winsandbox.py`), on top of the two Linux builds a gate runs and the host's own work; the gate timings below were measured on a 24-core box, so plan for that class of machine.

### What is not in the repo and why.

- **The game and its exe.** Nothing from the game is committed (see [License](#license)); every path above lives on your machine.
- **The WSO fork tree.** Recovery adopts bodies from `WillScarlettOhara/iwd2-re` at one pinned sha — `DEFAULT_FORK_BASE` in `tools/wave.py`, currently `e8dd16a750966af53f24daaf49dcb4fb13594c13` — reachable through the read-only `wso` remote.
  The fork's tree is untrusted: it is read only through git plumbing that never checks it out — `git show <sha>:<path>` and `git ls-tree <sha>` — never executed, never named as a `wso/` ref.
- Adopted code carries an `Imported-From: WillScarlettOhara/iwd2-re@<sha> (MIT per author, 2026-10-17)` trailer, so every absorbed line stays traceable to that one commit.
- **Any credential.** No GLM or Anthropic token, key or account name is ever committed or written into a brief; the worker wrapper reads them from the environment, as the next subsection describes.

### The worktree layout.

- `first` is the integration branch and lives in its own worktree, the main one. Every batch and every stream lands in it by fast-forward; the driver does the pushing.
- Batch branches `p3/wso-<id>` — `b<NNN>` for wave 1, `i<NNN>` for imports, `p<NNN>` for probes — each get a worktree of their own, cut at `<main worktree>-worktrees/p3-wso-<id>`, the shape `git worktree list` in `tools/wave.py` expects:

```
git worktree add -q -b p3/wso-<id> <main worktree>-worktrees/p3-wso-<id> <first commit>
```

- A branch that already exists but has no worktree takes `git worktree add -q <path> <branch>` instead.
- Hand streams use `tools/worktree.sh new <stream>` — `~/iwd2-re-worktrees/p3-<stream>` on branch `p3/<stream>`, cut from `first` — as [Parallel work streams](#parallel-work-streams) describes.
- Numbered integration branches `p3/integrate-N` hold a plan's task work between those merges.
- Each worktree builds on Windows in its own folder, so parallel batches never share a build tree:
  - `%USERPROFILE%\iwd2r-build` for the `first` worktree, `%USERPROFILE%\iwd2r-build-<folder>` for the others, `IWD2R_WIN_CHECKOUT` overriding.

### Workers: Claude Code is the harness, the model is your choice.

Workers are headless Claude Code sessions whatever model runs inside them; the pool you pass to the driver picks the model.

- **Anthropic models** (`--pool claude:N`): the `claude` CLI logged into an Anthropic account or given an API key. Nothing else to install.
- **Z.ai GLM models** (`--pool glm:N`, the default): the same Claude Code sessions, pointed at Z.ai's Anthropic-compatible endpoint by a wrapper named `claude-glm` on `PATH`. The wrapper is not in the repo; to work with the driver it must:

- keep its own config dir, `~/.claude-glm` (`CLAUDE_GLM_CONFIG_DIR` moves it), mirroring `~/.claude` — the driver reads worker transcripts from `<config dir>/projects`, and worker config must never land in your interactive one;
- point `ANTHROPIC_BASE_URL` at `https://api.z.ai/api/anthropic` and put the GLM Coding Plan's token in `ANTHROPIC_AUTH_TOKEN`;
- map the model the driver names in `CLAUDE_GLM_MODEL` — `glm-5.3-flash[1m]` — onto the plan's models;
- run like `claude -p <brief> --output-format json`; the driver adds `--dangerously-skip-permissions` and `--max-turns 400`, and sets the batch worktree as the working directory.

The driver scrubs the launching session out of every worker's environment and sets `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` for all of them. A `claude-glm` pool keeps the wrapper's variables — `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `API_TIMEOUT_MS`, and the `ANTHROPIC_DEFAULT_*`, `CLAUDE_GLM_*` and `CLAUDE_CODE_SUBAGENT_MODEL` prefixes. Any other wrapper gets its model as `--model <model>` instead, plus `--setting-sources project,local`, `--strict-mcp-config` and `ENABLE_CLAUDEAI_MCP_SERVERS=0`.

Two `claude-glm` launches race on the wrapper's re-link of `~/.claude` into `~/.claude-glm`: apply `patch ~/.local/bin/claude-glm < tools/claude-glm.lock.patch` (an `flock` on `~/.claude-glm/.relink.lock`; needs util-linux `flock`) before running two workers.

A pool is written `NAME=WRAPPER:MODEL[:WORKERS]`, where `WORKERS` defaults to 1, or as the short form `NAME[:WORKERS]` of a known name: `glm` is `claude-glm:glm-5.3-flash[1m]` on every queue, and `claude` is `claude:sonnet` on `wave1` and `probes` but `claude:haiku` on `import`. Without `--pool` the driver runs one pool, `glm=claude-glm:glm-5.3-flash[1m]:2`; reviews default to `sonnet` on a `claude` pool and `glm-5.3-flash[1m]` on a `glm` one, and `--reviewer-model NAME=MODEL` overrides that. A contributor can point the pool at any wrapper that speaks the same protocol — the pool spec decides, not the repository. The grammar above is the driver's own `--pool` help, quoted; the per-queue defaults live in `tools/driver.py` beside it.

### Running a batch with the driver.

From the `first` worktree:

```
python3 -I tools/wave.py run --queue import --pool glm:2 --budget-glm 30000 --max-batches 4
python3 -I tools/wave.py run --queue probes --pool glm:1 --budget-glm 10000 --seed 2026-10-22
```

- `--queue` is `wave1` (the default), `import` or `probes`; `--pool` repeats, once per pool.
- `--budget C` caps credits over all pools, `--budget-NAME C` caps one pool; credits price GLM turns only.
- `--max-batches N` stops starting batches once N have started, letting the in-flight ones finish.
- `--seed S` is the review sample seed, `2026-10-22` by default; `--worker-timeout SECONDS` bounds a worker at 3 hours by default.
- `run --dry-run --state COPY.json` runs one batch with a fake worker — the way to watch a cycle without spending credits.
- The Frida phase runs after an import worker by default (`frida_default` in `docs/wso/truth-calibration.json`); `--frida` and `--no-frida` override it, and `remeasure` re-traces what closed without it.
- Exit codes:

  - 0 — done, or a budget stop;
  - 1 — an exception or a halt: a launch failure, an auth or billing error, or the breaker (three batch exceptions in a row whose worker produced no transcript);
  - 3 — parked (a 429);
  - 4 — stalled.

The queue's truth is the committed state file under `docs/wso/`: `wave-state.json`, `import-state.json` or `probe-state.json`. The driver's own bookkeeping is untracked scratch under `.superpowers/sdd/2026-10-17-wso-integration/driver/`, with each batch's briefs, reports and review diffs in `driver/<id>/`:

- `status.json` tracks `wave1`, `status-import.json` tracks `import`, `status-probes.json` tracks `probes`;
- the keys worth reading are `current`, `running`, `pools`, `stopped`, `stalled`, `halted` and `exceptions`;
- never commit that folder, never edit it by hand.

- An exception — a second failed check, a second blocking review, a worker without a report — waits in `exceptions`. Read it there, and clear it only with `python3 -I tools/wave.py run --clear <batch>`, never by editing the file: the next run retries that batch before any new cut, plain `--clear` re-checking its last report and `--clear <batch> --rerun` re-running the worker. A batch interrupted at the `close`, `record` or `push` stage goes straight back to that stage on its recorded work.
- The reserved key `first` — the base tests went red — is lifted with `--clear first`.
- A stopped driver leaves its in-flight batches recorded in `running`; the next run resumes them, the worker re-entering with a `Resume:` preamble.
- Locks, so two drivers never collide:
  - the sandbox lock `%USERPROFILE%\iwd2r-vm\sandbox.lock` — one sandbox at a time, across all worktrees;
  - the landing lock `<git common dir>/iwd2r-landing.lock` — one per repository, held over a batch's merge into `first`, its gate and its landing.
- The driver appends a templated `## driver <id>` entry to the plan's ledger, `.superpowers/sdd/2026-10-17-wso-integration/progress.md` — untracked scratch, never committed — and pushes `first:main first:first` to the `iwd2r` remote itself.

### Doing a batch by hand.

The coordinator's loop, one command each; everything below also has a section in [docs/wso/README.md](docs/wso/README.md).

- `python3 -I tools/wave.py next [--queue import|probes] [--include-uncovered]` — pick, cut and triage the next batch, 20 rows by default: branch, worktree, triage and a rendered brief. Wave-1 rows come from `docs/wso/disagreements.json`; an import batch takes covered rows first, and `--include-uncovered` keeps the rest.
- The brief templates are the worker's whole job description, and `python3 -I tools/wave.py brief <id>` re-renders one:
  - wave 1: [docs/wso/brief-template.md](docs/wso/brief-template.md)
  - imports: [docs/wso/import-brief-template.md](docs/wso/import-brief-template.md)
  - probes: [docs/wso/probe-brief-template.md](docs/wso/probe-brief-template.md)
- `python3 tools/oracle.py evidence 0x5845D0` — write the draft evidence file for a function, front matter and decompile included.
- `python3 -I tools/wave.py selfcheck --batch <id>` — run in the batch worktree when the work is done; fix every line it prints until it says `selfcheck: OK`.
- `python3 -I tools/wave.py verdict <batch> <address> fork|ours|neither <case>` — record one wave-1 verdict with its deciding case.
- `python3 -I tools/wave.py close <batch> [--kind import|probes]` — check and land a batch: verdicts, evidence lines, a clean tree, an unmodified gate, then fast-forward `first`.
- `python3 -I tools/wave.py resolve <address> fork|ours|neither <case>` — a probe-list row into its batch.
- `python3 -I tools/wave.py undecide <batch> <address> fork|neither <reason>` — the reverse: a batch row onto the probe list.
- `python3 -I tools/wave.py unpark <address> [<address> ...] [--reason TEXT]` — a parked import row back to the queue.
- `python3 -I tools/wave.py coverage [--scenarios a,b] [--chunk N] [--addresses FILE]` (and `coverage --pending`) — measure which functions of the original exe each scenario exercises, into `docs/wso/coverage.json`.
- `python3 -I tools/wave.py recompare [--tip SHA] [--no-fetch]` — queue what the fork's tip adds, for coverage to measure; `scorecard` tallies the waves into `xrec-report.md`.
- `python3 -I tools/wave.py remeasure --read-only-measured` — a Frida-only pass over closed rows, re-tracing them on a `p3/remeasure-<stamp>` branch.

Never edit by hand what the tools own: `docs/wso/*-state.json`, `docs/wso/*-list.json`, `docs/wso/coverage.json`, `docs/wso/triage.json`, the driver status files, and the generated `docs/MAP.md` (wave-1 brief rule 11). A contributor writes code under `src/`, evidence under `docs/evidence/`, and the park files `docs/wso/import-parked/<ADDRESS>.json`.

### The gate.

`tools/gates.sh --base first` runs locally the steps CI runs, in order:

- the `linux-gcc` build with its tests;
- the `linux-clang` build with its tests;
- structural parity against the base;
- the tool tests, `tests/test_tools.py`;
- the subsystem map (`tools/gen_map.py --check`), recovery status (`tools/re_status.py --check`) and replay fields (`tools/gen_fields.py --check`);
- the shader blobs when `tools/shaders.py` exists, and the decompiler evidence check (`tools/check_evidence.py --base`).

When every path the branch changed against `--base` is on the script's allow-list (docs, tools, README — the list is in the script), the build, test and parity steps print `skipped (docs-only change against BASE)` and the summary says `gates: docs-only fast path`; `--full` forces the full gate, and `--windows` adds the Windows builds. One gate runs at a time: an exclusive `flock` on `.gates.lock` at the main repo root, shared by every worktree — a second gate waits, or with `--no-wait` names the holder and exits 3.

On a 24-core box the full gate takes about 9 minutes, a docs-only one about 1.

### What a verdict is.

- Sides: `ours`, `fork` or `neither` — whether our recovered body, the WSO fork's adopted body, or neither is right for a function.
  A wave-1 batch's report carries one line per row; the probe queue and the parked rows are the two ways a row leaves undecided.
- Evidence kinds: `oracle`, `replay`, `read-only` or `trace`. A `fork` or `neither` verdict needs a case that ran something — an oracle case, a replay checkpoint or a trace; a reading of the decompile, and a dump reading, decides only `ours`.
  `close` refuses anything else unless a recorded ruling allows it (`--allow-dump RULING --ledger PATH`).
- The Frida phase: after an import worker, the driver measures the rows whose evidence is a reading plus an exemption by differential tracing — the same function hooked in the original and in ours over the same scenario ([docs/frida-tracing.md](docs/frida-tracing.md)) — and rewrites the evidence `kind:` to `trace`. Bodies it measured are then frozen.
- The probe list: rows no worker could decide wait in `docs/wso/probe-list.json` until a probe batch (`p<NNN>`) or a `resolve` settles them; a probe batch's worker adopts the fork body and the Frida phase decides.
- Parked rows: import rows a batch dropped land in `docs/wso/import-parked/<ADDRESS>.json` with what they need; `unpark` returns them to the queue.

The full format of an evidence file, and every key of a state file, are in [docs/evidence/README.md](docs/evidence/README.md) and [docs/wso/README.md](docs/wso/README.md) — this section is the tour, not the reference.

### House rules for anyone (human or model) touching a batch.

- Never amend or rewrite history on a shared branch, and never push (import brief rules 8 and 9). The refused commands are listed and enforced — `reset`, `rebase`, `revert`, `restore`, `clean`, any `stash`, `commit --amend`, `filter-repo`, `push`, `branch -d/-D/-f/-M/-C`, `checkout -B`, `switch -C`, `checkout -- <path>`, `checkout <sha> <path>` and a bare `git checkout <path>`.
  The allowed list is `add`, `commit`, `status`, `diff`, `log`, `show`, `ls-tree`, `merge-base`, `rev-parse`, `blame`, `checkout -b`, `checkout <branch>`, `switch -c`.
- Never wait for the coordinator — report what you have and return (wave-1 brief rule 15; the import and probe briefs say the same, their rules 10 and 14).
- Bodies the Frida phase measured are frozen: a parity red against one is waived in the evidence (`parity_waiver: "<reason>"`, wave-1 brief rule 6), never edited away.
- Kept rows stay under `## Kept`: base-body rows kept as ours are listed there, one line `kept <0xADDR> <reason>`, never also under `## Imported`.
- The fork is read at the pinned sha only, through `git show` and `git ls-tree`; never a `wso/` ref, never checked out, never executed (wave-1 brief rules 8 and 9).
- No desktop windows from automation: the game runs in the sandbox (wave-1 brief rule 12).
  A desktop launch needs the human's explicit `IWD2R_DESKTOP_OK=1`.
- At most two sandbox launches per attempt, through `tools/play.py` and `tools/gltrace.py`, until `--new-attempt "<why>"` records a fresh attempt.
- The sandbox save reset touches only the oracle game copy, `%USERPROFILE%\iwd2r-vm\game`, never a real install.

## Deviations from the original

- Multiplayer is removed permanently: DirectPlay and the multiplayer screen are deleted, and the engine runs the original's single-player null-provider path.
- The OpenGL 3D video mode is inert: OpenGL calls are no-ops, and a failed 3D init falls back to 2D with a line on stderr instead of a dialog.
- Movies are skipped: Bink is not loaded, and a later project may decode them with FFmpeg.
- IME text composition is inert.
- GDI (TrueType) text is inert.
- Fullscreen presents as a borderless window scaled to the desktop with aspect preserved. Windowed, the window's client area is the game's whole screen, so it is game-sized rather than a desktop-sized popup.
- The single-instance check is removed: two copies can run against the same install, where the original refused to start a second.
- On Windows the executable is a console program for now, so a console window appears alongside the game window.
- The version resource is built in: the game name, version (`2, 0, 1, 0`, shown as v2.01 in the options screen) and build number come from strings compiled into iwd2r rather than from an `.exe` resource, and PrivateBuild names the iwd2r version and commit.
- Arbitrary resolutions beyond the original four (800, 1024, 1600, 2048), `Resolution=desktop`, the `Height` key and the `Scale` key are an IWD2EE-style extension; the layout at other sizes follows IEex's generalisation of the original table (src/ScreenLayout.cpp). On exit the engine writes `Resolution` back as the INI had it rather than the engine's width.
- Positioned 3D sounds play centred without distance attenuation when the 3D-sound option is on, because the DirectSound 3D interfaces are no-ops.
- The assert-time thread suspension is cooperative only: a thread can suspend itself but cannot freeze others.
- The speaker-portrait click in world dialog panels, which forwarded to the multiplayer screen, is now a no-op.
- File fields that hold pointers: where the original stores a heap pointer in a 32-bit field of an area or game file record during a save, a 64-bit build stores a handle instead (`compat/marshal_ptr.h`: `MarshalPtr`, `UnmarshalPtr`, reset at the start of each `SaveGame`). The original overwrites those fields on load, so the saved bytes mean nothing either way (ruling M1-6).
- Shutdown waits for the AI thread (`WaitForMainAIThread`, src/CChitin.cpp, bounded to 10 s): ours returns from WinMain into C++ destructors, where the original's `ExitProcess` killed the thread first.
- In the deterministic replay mode only (`IWD2R_STATE_DUMP`), the AI thread waits after an object's update until the path search that update queued is done (`ReplayWaitForSearch`, src/CGameArea.cpp, with a real-time deadline), so search results do not depend on thread scheduling. Normal play does not wait.
- The start screen is the original's connection screen with its multiplayer entry hidden.
- `C2DArray::LoadText` has no counterpart in the original. The original parses 2DA text only inside `C2DArray::Load` (0x402B70), after fetching it through its resource manager; ours splits that parse into `LoadText`, unchanged, so the tests and the oracle's table cases can build tables from text without a resource manager. `Load` calls it, so the engine's behaviour is the same.
- The drawing entry points of the `CVid*` classes (`CVidCell::Render`, `CVidTile::Render`, `CVidFont::TextOut`, `CVidMode`'s line, rectangle, ellipse, recticle, outline, polyline, erase and fade functions, `CVidInf`'s `BK*` and `FX*` functions and `RenderFlash`, `CVidMosaic::Render`, `CVidBitmap::RenderDirect`, and the viewport fill in `CInfinity::RenderMessageScreen` in `src/CInfinity.cpp`; the list and the helpers left alone are in `src/render/api.h`) start with one line the original does not have: a guard that hands the call to an installed render backend and returns when the backend handled it (the two inlined fade functions instead end with a line that reports the fade level). It lets later renderers draw the same calls another way (larger textures, a GPU) without changing the decompiled bodies. With no backend installed, the default, every guard falls through and the bodies draw into the back buffer exactly as before. Each guarded function's evidence file carries the exemption "render API dispatch guard".
- The drawing code that project 4 ported from stubs or checked against the original (the 32-bpp paths, palettes, polygon fills) follows the original's machine code where the decompiled source we started from had it wrong, so these functions differ from upstream iwd2-re, not from the original: `CVidPoly::FillConvexPoly`'s edge walk and last clip row ([docs/evidence/7C0F40.md](docs/evidence/7C0F40.md)), `CVidPalette::GetTint` returning 0xFFFF for the combined global and affect tint ([7BF430.md](docs/evidence/7BF430.md)), `CVidMode::ApplyBrightnessContrast`'s byte complement and int gamma scale ([795E00.md](docs/evidence/795E00.md)) and `CVidPalette::RealizeResource`'s grey, add and tint stages ([7C04B0.md](docs/evidence/7C04B0.md)). Each was found by an oracle case that compares the original's function with ours.
